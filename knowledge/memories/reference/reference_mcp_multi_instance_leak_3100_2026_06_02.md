# MCP :3100 multi-instance leak → fleet-wide connect failure

**Symptom:** operator reports "no one can connect to the MCP server." `:3100` flaps (intermittent `200` / connection-refused) so the whole 26-chat fleet's `mcp__prism__*` calls fail.

**Root cause:** 11 orphaned `node dist/index.js` MCP-server instances (~700 MB each, ~7.8 GB total, ~62 min old) all racing to bind `:3100`. Only one OS process can bind the port; the rest fully initialize (load every engine → 700 MB) but can't take the port and **hang instead of exiting**. The duplicates accumulate because repeated restart kicks — the per-prompt MCP auto-reconnect hook **and** the supervisor — re-spawn `dist/index.js` whenever `:3100` looks down, without first reaping stale instances. A flapping server triggers a kick every prompt → instances pile up → more contention → more flapping (positive feedback loop).

**Fix (verified this session):** `Stop-ScheduledTask 'PRISM MCP Server'` → kill ALL `mcp-server-supervisor.mjs` + `dist/index.js` → confirm `:3100` has no listener → `Start-ScheduledTask 'PRISM MCP Server'` → wait ~25–30 s for engine load → verify `http 200` + exactly **1** `dist/index.js` + Watchdog `Running`. Clearing the contention is what lets a single instance bind cleanly and hold. Net: 7.8 GB reclaimed, single stable server.

**Reaping caveat (learned the hard way):** selective reap (kill stale, keep the listener) is **race-prone** — the live listener PID can die between the `Get-NetTCPConnection -LocalPort 3100` lookup and the kill loop (the server was already flapping), so `listener` resolves to `0`, nothing gets excluded, and you kill the live one too (took :3100 fully down for a beat). When the server is flapping, prefer **full-clear + clean-restart** over selective reap. Always protect a chat's own stdio MCP server via the ancestry-to-`claude.exe` walk (LiveClaude). Pairs with [[reference_mcp_sdk_single_transport_invariant_2026_05_25]] (a *distinct* in-process "already connected to a transport" bug). Follow-up worth doing: have the supervisor/reconnect **singleton-guard** — reap any stale `dist/index.js` before spawning a new one.

**Second occurrence (golf 2026-06-02, recurring [[feedback_golf_owns_reaper|fleet-hygiene]] tick) + REFINED RULE.** A 5-min hygiene tick saw **2** `dist/index.js` with `/health=200` (latency had crept 0.097s → 1.87s under fleet load) and tried to **dedup** by reaping the "non-listener." `Get-NetTCPConnection -LocalPort 3100 -State Listen` returned **empty** (listener mid-flap at that instant), so the reap loop excluded nothing and killed **both** instances → :3100 went fully DOWN. Recovered via full-clear+restart (kill all server + supervisor → `Stop`/`Start 'PRISM MCP Server'` → poll ≤105s); converged to 1 instance + 200 in ~15s — the bind-fail-fast preflight (FIX1+2, commit 2167e22cc8) working exactly as designed. **REFINED RULE: when `/health=200`, two instances is BENIGN — the bind-fail-fast preflight self-converges 2→1 within ~15s on its own. NEVER reap-to-dedup on a healthy port: there is nothing to fix (pure downside), and the `-State Listen` lookup races to empty mid-flap so you kill the live listener. Act ONLY when `/health≠200` (refused/timeout), and then ONLY via full-clear+restart, never selective reap.** The supervisor + watchdog both respawning is what produces the transient 2nd instance; the unified single-flight lock (staged FIX4/6, `mcp-server-3100.lock`) is the real fix — until it ships, just let bind-fail-fast converge.

**Third occurrence + ROOT CAUSE (golf 2026-06-02, same session): bootstrap is ~50s, and restarting a BOOTING server is the flap engine.** After the 2nd-occurrence outage, :3100 stayed DOWN with 1–2 instances for 96s+ across several restart attempts. Diagnosis settled it: `:3100` was **FREE** (not TIME_WAIT), and a clean foreground `node dist/index.js` (TRANSPORT=http PORT=3100, Watchdog disabled) reached **health=200 in ~50s undisturbed**. The server is NOT broken — it just needs ~50s to load **64 dispatchers / 1718+ actions / ~700 MB engines**, and the uncoordinated restarters (Watchdog task + supervisor + per-chat auto-reconnect) kept killing/respawning before boot finished, **resetting the 50s clock every time → perpetual DOWN**. The per-chat auto-reconnect is single-flight (O_EXCL across fleet) so it is NOT the main competitor — the **Watchdog** is. **RULE: NEVER restart a server that is mid-boot. If `/health≠200` but a `dist/index.js` process EXISTS → it is bootstrapping (~50s); WAIT up to 90s, do not touch. ONLY restart when `/health≠200` AND zero `dist/index.js` processes exist — and then: `Disable-ScheduledTask 'PRISM MCP Server Watchdog'` → `Stop`+`Start 'PRISM MCP Server'` → wait 60s undisturbed → verify 200 → `Enable` Watchdog.** Fleet chats reconnect automatically: once :3100 is 200, each chat's per-turn `mcp-connectivity-check`/`maybeReconnect` hook reconnects on its next prompt — you cannot force another chat's client from outside, only keep the server steady. Durable code fix (needs 3-of-3 scrutiny, post rate-limit): Watchdog + supervisor + reconnect must share `mcp-server-3100.lock` (staged FIX4/6) AND treat "process exists but not yet healthy" as "booting → leave alone", not "down → respawn".
