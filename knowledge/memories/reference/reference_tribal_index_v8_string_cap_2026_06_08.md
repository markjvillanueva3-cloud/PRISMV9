2026-06-08 (slot golf, synergy /goal, gap #5 root cause — supersedes the "83.7% coverage" framing in [[reference_wiki_tribal_embed_pipeline_blocked_2026_06_08]]).

**The wall:** `state/shared/tribal-embed-index.json` reached **536,988,127 bytes**, crossing **V8's hard maximum string length** `0x1fffffe8` = **536,870,888 bytes (≈512 MiB)** by 117,239 B. Any consumer doing `JSON.parse(fs.readFileSync(INDEX_PATH, "utf8"))` now throws `Cannot create a string longer than 0x1fffffe8 characters` **before JSON.parse ever runs**. This is the *string-length* limit, NOT the heap — `--max-old-space-size=8192` does NOT help (that was the correct fix earlier today at 533MB when the read SUCCEEDED but the parsed object-graph OOM'd; the index then grew past the string cap, a different + harder wall).

**Blast radius (silent, fleet-wide):** the LIVE cosine reranker `.claude/scripts/tribal-rerank.mjs:76` (PSN leg #5 / tribal injection, fired on every UserPromptSubmit via `tribal-by-domain-inject.mjs`) does the exact string-read → tribal injection returned NOTHING in every chat with no error surfaced. The wiki embedder's read (`embed-wiki-into-tribal-index.mjs:349`) was also blocked. ~20 read-only audit scripts read the index the same way (still to be wired).

**Fix (commit `182788232a`):** `scripts/lib/load-tribal-index.mjs` — `loadTribalIndex(path, fs)` reads the index as a **Buffer** (Buffers have no string cap, MAX_LENGTH ≈ 2-4GB), then: fast-path `JSON.parse(buf.toString())` when under cap (byte-identical to prior code, so every under-cap index is unaffected); when over cap, parse the small head metadata + walk the `"entries":[...]` array with a minimal brace-aware JSON boundary scanner (string+escape+depth state) and `JSON.parse` each small entry individually. Read-only — zero index-mutation risk. Wired into tribal-rerank.mjs + embed-wiki read. 8/8 loader tests (deepEqual-vs-JSON.parse oracle on adversarial braces/quotes/`\\`-escapes/Windows paths) + 23/23 embedder. LIVE: loader reads the real 537MB/33,639-entry index in 3.4s, 0 corrupt; rerank returns real mill hits (score 1.03).

**KNOWN-REMAINING — the WRITE side is still blocked (next unit):** `atomicWriteJSON` does `fs.writeFileSync(tmp, JSON.stringify(obj))` — `JSON.stringify` of a >cap object ALSO throws the same error. So the embedder can READ the index now but **cannot append new entries** (the write stringify exceeds the cap). The monolithic-single-JSON-blob architecture is at end-of-life. The real fix is **index sharding** (split into N shard files each < cap; writers append to the active shard; readers concat across shards via an updated loadTribalIndex). Until sharding lands, gap #5's coverage % cannot grow — but the live READ regression (PSN leg #5) is fully restored. The empty-text skip-guard (`isEmbeddable()`, same commit) is necessary-but-not-sufficient: it stops one FM-only/orphan stub from aborting an all-or-nothing chunk, but only matters once the write path is unblocked by sharding.

**SECOND MANIFESTATION — the fail-OPEN clobber that DESTROYED the brain (commit `a3e6d3ca97`):** the cap read-failure had a worse downstream effect. `.claude/scripts/tribal-embed-index.mjs` `readIndex()` did `JSON.parse(readFileSync(idx,"utf8"))` with a **fail-OPEN catch that returned a fresh empty `{entries:[]}`** on any parse error (it even logged "starting fresh"). When the 537MB index threw the cap error, an `--add`/`--update` invocation — almost certainly an auto-embed hook firing on a wiki-file Write (this session's own doc-reflect wiki lesson is the lone surviving entry) — loaded an EMPTY base, spliced the one file, and `writeIndex()`'d it → **clobbered the 537MB / 33,639-entry brain down to a 1-entry 16KB stub** (signature: no `wikiEmbeddedAt`, fresh `generatedAt`, 1 entry). PSN leg #5 then ran on 1 entry. The 537MB version is gitignored (no git history) and rename-replace bypassed the recycle bin → **the 33,639-entry version is gone**. Recovery: restored the surviving **4,162-entry** baseline (2026-05-20) from slot worktrees (sierra/whiskey/zulu-obsidian, all identical, gitignored independent copies). The lost ~29K delta is DERIVED (re-embeddable from on-disk wiki/mem/tribal once write-side sharding lands). **Fixes:** (1) `readIndex` now cap-safe-loads AND FAILS LOUD if the file exists-but-won't-load (never empty-then-clobber); (2) `writeIndex` clobber-guard refuses a >50% shrink over a populated index unless `PRISM_TRIBAL_ALLOW_SHRINK=1` — alone would have blocked the 33,639→1 write; (3) loader post-walk closing-`]` assert (torn-file fail-loud). 7/7 guard tests + 10/10 loader. **Lesson:** a fail-OPEN read (`catch → return empty`) on a corpus that is then re-written is a silent-total-destruction vector — `catch` on an EXISTING file must fail loud, never "start fresh". This index was ALSO clobbered 2026-05-22 ([[reference_tribal_index_keyscheme_clobber_2026_05_22]]) — third time's the guard.

**SECOND CEILING — default-heap OOM at ~150MB (found 2026-06-09, commit `bee977a004`):** re-embedding to restore the brain grew the index 65MB→168MB (10,555 entries), and the LIVE `tribal-rerank` then **OOM'd on the default ~2GB node heap** — PSN leg #5 went dark AGAIN (heap OOM, not the string cap). `loadTribalIndex` lets the reranker READ the bytes, but its `JSON.parse` builds a full object graph (N × 768 floats) that exceeds default heap above ~150MB. So the index has a **second ceiling (~2GB heap @ ~150MB) BELOW the 512MiB string cap** — and the heap flag is a NECESSARY companion to the loader fix: the original 537MB index would have OOM'd the reranker too (the clobber-to-small masked it). FIX: `tribal-by-domain-inject.mjs` spawns rerank with `NODE_OPTIONS=--max-old-space-size=8192`. **ARCHITECTURAL DIRECTION (the real fix):** parsing a growing JSON index PER PROMPT does not scale (at 537MB ≈ 3-4s + multi-GB heap per prompt × 26 slots → inject TIMEOUT_MS starts failing). **STOP growing `tribal-embed-index.json` toward 537MB.** The brain belongs in **Qdrant** (already up: prism_engines/skills/formulas) as a tribal collection queried per-prompt — NOT a JSON file parsed per-prompt. The full ~33K "restore" should target Qdrant, not the JSON file; the 10.5K JSON index is a fine working size until the Qdrant migration. This supersedes the earlier "re-embed fully into the JSON index" plan.

**BLAST-RADIUS AUDIT (verified, not assumed):** audited the 4 sibling embedders that read→splice→write the index for the SAME fail-OPEN clobber pattern. Result: **the clobber bug was ISOLATED to `tribal-embed-index.mjs`** (now fixed). `embed-cited-tips-into-tribal-index.mjs` `loadIndex` returns `{entries:[]}` ONLY when the file is absent (legit bootstrap); its read at line 188 has no catch → throws on a cap error → fail-loud. `embed-engines` (191), `embed-knowledge-store` (303), `embed-all-wiki` (196) all do a bare `JSON.parse(readFileSync(...,"utf8"))` with no fail-open catch → throw → `main().catch` → exit, NO write → no clobber. They are cap-FRAGILE (cannot READ a >512MiB index — they throw, correctly fail-loud) but NOT clobber vectors. Wiring their reads to `loadTribalIndex` is part of the future WRITE-side sharding unit (their own `JSON.stringify` writes also throw at >cap), not an urgent standalone fix. So: the only fail-OPEN-then-write data-destruction path in the tribal stack was the one fixed in `a3e6d3ca97`.
