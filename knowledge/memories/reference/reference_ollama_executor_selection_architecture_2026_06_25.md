**Ollama offload model-selection architecture** (slot:alpha, 2026-06-25, traced while continuing the "max potential ollama utilization" /goal after shipping [[reference_ollama_routing_roster_sync_2026_06_25]] cheapest-model-select). Verified by reading the 3 files end-to-end. This exists so a future session does NOT (a) re-derive this 3-read trace or (b) hastily force a risky `--model` change that reverses a deliberate design.

**THREE disconnected model-selection layers (verified file:line):**
1. **`scripts/lib/model-routing-policy.mjs::routePrompt`/`ollamaSafeClassModels`** — MATRIX-AWARE (consumes `ollama-capability-matrix.json`); now picks the CHEAPEST matrix-proven model per class (the fix shipped this session). **Consumer: `.claude/hooks/model-tier-advisor.mjs` ONLY** — an ADVISORY UserPromptSubmit hook that RECOMMENDS a tier / names a model. It EXECUTES nothing. The matrix proves only DETERMINISTIC classes (classify/extract/format via `BATTERY_TO_CLASS`).
2. **`.claude/hooks/lib/ollama-cost-router.mjs::routeModelForTask`** — STATIC/tier-based (category -> TIER_PREFERENCES -> first-installed), MATRIX-BLIND, with `BLACKWELL_CEILING` promoting balanced->strong->gpt-oss:20b on the 96GB host. **Consumer: `.claude/hooks/ollama-task-offloader.mjs:609`** (the real auto-offload directive emitter).
3. **`scripts/ask-ollama.mjs::runRequest` (~L1026-1047)** — LOADED-FIRST (warmth-aware): explicit `--model` wins; else prefer a SUBSTANTIAL model ALREADY warm in VRAM (avoid cold-load + eviction thrash on the shared Blackwell); else resolver; else `DEFAULT_MODEL=qwen2.5-coder:32b`. This is the ACTUAL executor of the offloader's `ask-ollama <mode> <file>` directive (U-ASK-OLLAMA-LOADED-FIRST).

**KEY FINDING -- the auto-offloader path is CORRECT-AS-IS, not a bug (R12 honest):** `ollama-task-offloader.mjs` computes `route.model` (L614, cost-router) but its IMPERATIVE auto-exec directive (`buildOffloadDirective` L435) deliberately emits `node scripts/ask-ollama.mjs ${mode} <file>` with **NO `--model`** -- `route.model` is used only in the SOFT-suggestion text (L444) + telemetry (`modelTier`). This is INTENTIONAL + sound: the offloader hook has no `/api/ps` warmth info, so it correctly lets `ask-ollama`'s warmth-aware loaded-first pick the model at exec time. Do NOT "fix" this by forcing `--model route.model` -- that reintroduces the exact cold-load thrash loaded-first exists to avoid (R7 conflict; R8 don't-reverse-a-deliberate-design).

**THE REAL "max potential" gap + why it is R13-BLOCKED:** the only genuine lever is `ask-ollama` loaded-first preferring the BIGGEST warm model (`OFFLOAD_LOADED_PREFERENCE`) rather than the CHEAPEST-SUFFICIENT warm one. But `ask-ollama`'s modes (explain/summarize/triage/viz/rerank/ask/codegen) are GENERATIVE -- NOT the deterministic classify/extract/format classes the matrix proves -- so "sufficient" (is 7b good enough for summarize?) has NO matrix proof. Its quality basis is exactly the **GPU-blocked stress-test data** the operator goal calls for ("stress test ollama llms to see what the hardest task each llm can do before diminishing returns"). Building the executor selection NOW = inventing per-mode quality thresholds without measurement (violates R13 logical-order: consumer atop an unproven dependency).

**CORRECT NEXT UNIT (do on a fleet-idle GPU, in this order):** (1) run the per-mode stress battery solo-per-model on an idle box -> a measured `mode -> minimum-sufficient-model` table (NOT guessed); (2) keep the cheap tier (1.5b+7b ~6GB) co-resident warm alongside 32b (all fit 96GB) via prewarm; (3) make `ask-ollama` loaded-first prefer the cheapest WARM model that clears the mode's measured threshold (reuse `modelCostRank` shipped this session), `DEFAULT_MODEL` floor unchanged; (4) optionally pass the offloader's `route.model` as a soft HINT once warmth + threshold agree. The cold-load-vs-warm tradeoff means step (2) prewarm is the enabler that makes cost-appropriate AND warm COINCIDE -- without it, forcing the cheap model cold-loads.

**Lesson:** "route to the cheapest model" splits into MATRIX-PROVEN classes (deterministic -- safe to auto-downshift, done this session) vs GENERATIVE modes (quality is a measurement, not a proof -- blocked on stress data). Don't conflate them; don't reverse a warmth-aware loaded-first design on an unmeasured "cheaper is fine" assumption (R7/R8/R13).

**RESOLVED VERDICT (2026-06-25, after the stress-frontier landed + a thorough R8 read of the executor): the cheapest-warm reorder is NOT safely buildable with current data -- DO NOT make it.** Reading `scripts/ask-ollama.mjs` confirmed BOTH `OFFLOAD_LOADED_PREFERENCE` (`[gpt-oss:120b, qwen2.5-coder:32b, qwen3-coder:30b, deepseek-r1:32b, gpt-oss:20b, deepseek-r1:14b, qwen2.5-coder:14b]`) and `CODER_LOADED_PREFERENCE` (`[qwen2.5-coder:32b, qwen3-coder:30b, qwen2.5-coder:14b]`) are BIG-FIRST and OMIT qwen2.5-coder:7b/1.5b entirely. That omission is NOT a bug -- `scripts/ask-ollama.test.mjs:98` pins a DELIBERATE QUALITY GATE: "only a TINY coder warm (1.5b, not in preference) -> resolver's better pick is COLD-LOADED (quality gate) ... chat-capable but BELOW the offload quality bar." The design CONSCIOUSLY prefers to cold-load a substantial model over using a too-small warm one -- quality over VRAM-savings, the OPPOSITE of cheapest-warm. The stress-frontier ([[reference_ollama_stress_frontier_2026_06_25]]) proves the cheap coders suffice for EASY single-difficulty tasks per category, but `ask-ollama`'s modes (summarize/explain/triage/codegen) serve ARBITRARY-difficulty production requests; the frontier gives NO evidence that 7b matches 32b on a HARD summary or a HARD codegen. Weakening a tested quality gate on easy-only data is the R7-override / R12-claim-without-proof / R13-consumer-on-unproven-dependency anti-pattern. **WHAT WOULD UNBLOCK IT (a future unit):** difficulty-STRATIFIED quality data WITHIN each mode (does 7b match 32b on HARD summarize/codegen, not just the 6 trivial battery functions?) + a generative-QUALITY metric (not exact-match -- e.g. an LLM-judge or reference-overlap score for summaries). Until that exists, the loaded-first design stays as-is. This is a measured DECISION (do not change), not a deferral. (Also confirmed: with the fleet keeping 32b warm at 54.7GB, a cheap-model-last-resort addition would be DEAD anyway -- 32b is always the warm pick -- so even the "safe" minimal add has no live effect; the lever genuinely requires prewarming the cheap tier AND a quality-gated preference change, both of which need the stratified data.)
