In the golf /yolo zombie-watch, a single `Get-CimInstance Win32_Process` snapshot of parent-dead `node.exe`/`bash.exe` **wildly over-counts zombies**. Observed 2026-06-13 across consecutive ticks (session 02a2de10): parent-dead orphans = 6 → 568 → 98 → 6 → 83 → **6 again seconds later**. The `bash -c "portable-node …"` / `tsx` hook-wrapper processes are short-lived — every active chat fires many hooks per prompt, each spawning a bash→node pair that exits within seconds. A census catches a burst mid-teardown, so the raw "parent-dead" number is **transient churn, not accumulation**.

**The honest zombie metric = defunct-childless:** an orphan is a TRUE reapable zombie only if its parent is dead **AND it has no live child process** (for a bash wrapper: its `portable-node` child already exited → the wrapper is a defunct remnant). Build `$childrenOf` from every `Win32_Process.ParentProcessId`; a bash-wrapper orphan NOT present in `$childrenOf` is defunct. One whose node child is still alive is an **active hook mid-run — never kill it** (that is the false-positive the 2026-06-11 reaper hardening, commit `de66545dbe`, exists to prevent).

Across this entire session every tick measured **defunct-childless = 0** — i.e. 0 true zombies despite raw counts up to 568, and the reaper correctly reaped 0 each sweep. The 15-min zombie-watch cron prompt was updated to headline defunct-childless, not raw parent-dead.

**BASH-STORM spike variant (2026-06-13 ~09:30Z, same session):** the SAME noise principle appears at the `bash.exe` layer at much larger scale. A snapshot caught **node+bash=1154→1222** (normal busy ~135–217); decomposed it was **node=173 (normal) + bash=1049 (the spike)**. The bash wrappers are the `bash -c "portable-node hooks/*.mjs"` MSYS layer — a *synchronized hook storm* (this chat's tick + 2 active peers + Stop hooks all firing at once) crests the count, then it self-drains (1049→532, node 173→81 in ~2 min) as each live `claude.exe` parent collects its finished wrappers. **Correlate: `stop-regression-bundle` "N gate(s) NOT evaluated (timeout/crash)" escalating 1→4→6→8** rides the same crest — Stop hooks time out under the wrapper load, NOT a hook bug. Ground truth stayed healthy throughout: node+bash RSS ~14.5 GB, **sysRAM 52–54%** (no pressure). An intermediate "bash-PARENT-DEAD=13" count still resolved to **TRUE-ZOMBIE=0** under the strict `(parent-dead AND childless AND portable-node-wrapper AND not-protected)` intersection re-guard — the parent-dead bashes mostly have live `claude.exe` parents (teardown-pending, parent will reap) or self-exit between snapshots. **Rule: a 1000+ bash count alone is NOT a leak and NOT reapable** (live-parented wrappers killed mid-hook can corrupt a hook write); only escalate if the count stays ~1000+ across consecutive ticks (then it's a parent-not-collecting leak). Headline defunct-childless / strict-intersection, never the raw bash count.

**`stop-close-own-bg-tasks.mjs` false-positive corollary (same bash-storm root):** during a hook storm the **R14 Stop hook can BLOCK with "you left N run_in_background Bash task(s) running"** (observed N=19, all `bash.exe`, ~11s old, same parent claude.exe) when you ran **zero** `run_in_background` Bash calls. The hook heuristic counts `bash.exe` descendants of your claude.exe as un-closed background tasks, but synchronous hook wrappers (and a crashed peer chat's briefly-orphaned wrappers) look identical. **Verdict procedure: run `TaskList` — if it shows 0 owned background Bash tasks (only your TaskCreate tracking task), the flagged bashes are NOT yours.** Do NOT `Stop-Process` them (live-parented hook wrappers — killing mid-hook risks corrupting a hook write) and there are no task IDs to `TaskStop`. They self-exit in seconds; the block auto-passes after attempt 2, and the reaper's `stuckHunt` collects any genuinely-orphaned ones (observed reaping 3, freeing 25 MB, while `crashWatch` logged the crashed peer's postmortem). The flagged `parent` PID is often the *crashed* chat, not you.
