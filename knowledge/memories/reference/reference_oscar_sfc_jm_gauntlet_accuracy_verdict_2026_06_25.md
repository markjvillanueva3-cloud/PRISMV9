**Source:** `state/shared/SFC-JM-PHYSICS-COMPARE.json` (gen 2026-06-24) + `SFC-JM-CORPUS-ANALYSIS.json` (1,171,812 ops / 154,414 program rows). Read live 2026-06-25.

**The honest numbers (turning CSS = Vc, no tool-diameter ambiguity):**
- byBand: in-band 153,410 / conservative 190,324 / **aggressive 123,962** / very-conservative 41,685 (509,381 compared).
- **aggressiveUnclamped: 169** -- the HIGH-CONFIDENCE true over-speeds (PRISM says slow down AND the lathe was NOT rpm-capped, so the programmed CSS is actually reached). This is 0.03%.
- **aggressiveClamped: 123,793** -- G50/rpm-capped, so the programmed CSS is only an UPPER BOUND the spindle never reaches -> NOT real over-speeds.
- byBandSoftBound.aggressive: 16,942 (default-material reclassified to milder ISO P).
- byIso: **H 507,785** / N 324 / P 1,191 / M 81 -- 99.7% default to ISO H.

**Why the "124K aggressive" headline is NOT a bug (R12 -- I almost chased it):**
1. 123,793 / 123,962 are CLAMPED (upper-bound artifacts), not real over-speeds. The script ALREADY stratifies this (`aggressiveUnclamped` vs `aggressiveClamped`); the console output reports it correctly -- only the gross `byBand.aggressive` JSON field looks alarming. The nightly cron reports the gross field (mildly misleading, not wrong).
2. The material-default-to-ISO-H is GROUNDED: `scripts/lib/sfc-jm-stock-prior.mjs` derives it from JM's actual stock purchases (93.7% tool steel), and **JM Die is a DIE shop -- it machines H13 tool-steel extrusion dies**. So H is the CORRECT default even for customer "ALCOA" (their DIE is tool steel; the aluminum is what the die later EXTRUDES). The naive customer->material inference (ALCOA->aluminum/N) would be the BUG. The corpus already feeds customer+path+comment into `inferIsoGroup` (sfc-material-infer.mjs); the H default is a feature, not a miss.

**169-over-speed spot-check (iter 5, R12 -- hypothesis disproven by reading the actual NC):** the top-30 `aggressiveUnclamped` entries are ALL `units:unknown` + `matMatched:null` (default ISO H) + identical 198.1/85/2.48. I hypothesized a G97-RPM-treated-as-CSS artifact, then READ the actual programs (`ALCOA/0007/W472A34-0007.MIN`, `BRICO/3-16 HIPRO PUNCH CASING WITH FLANGE.MIN`): both issue `G96 S650` (genuine constant-surface-speed) -- so 650 IS a real CSS and 650 SFM -> 198.1 m/min is the CORRECT inch->metric conversion (units handling is RIGHT, NOT a bug -- do not "fix" it). The programs mix G96 S650 (a high-CSS op) with G96 S150 (a finishing/threading op) + G50 S800 (rpm clamp). So the "aggressive" verdict is driven SOLELY by the default material = H (recVc 85); these are punch/die parts whose actual material is UNMATCHED. If a part is really pre-hard 4140 (ISO P, aggressive Vc ~200+) not hardened H, 198 m/min is IN-BAND, not aggressive. CONCLUSION: the remaining accuracy uncertainty is MATERIAL identification, NOT units/mode. The real lever = resolve per-program material from JM setup sheets / order data / stock callouts (cross-domain: hotel/quoting order materials + DocuStrata), NOT customer-name heuristics (die-shop trap) and NOT a units fix.

**GROUNDED MATERIAL SOURCE + JOIN SPEC (iter 7, the concrete fix for the material-default-H gap):** the flagged JM programs state NO material in-program (verified: ALCOA W472A34-0007.MIN has zero comments; BRICO comments are op labels only). The external source is `state/shared/quoting/baseline-records-corpus.json` -- 47,905 records, keys `{customer, part_id, material_iso, ...}`, of which **32,502 (68%) carry a real material_iso**. Distribution EMPIRICALLY VALIDATES the default-H prior: tool_steel_h13 24,887 + a2 3,375 + d2 3,492 + hss 7 = ~85% ISO H; steel_1018 669 + 4140 67 = ISO P; aluminum_6061/7075 = 5 ISO N; 15,403 null. So default-H is correct for the die-shop modal, and the few non-H parts (4140/1018 -> P, aluminum -> N) are where false-aggressive flags hide. **The scoped build (next iteration):** a `jm-program-material-join` that maps quoting `material_iso` -> the SFC corpus material by (customer, part_id) <-> program folder/part-number (e.g. ALCOA/**0007**/ <-> part_id `0007`). Non-trivial: customer-name normalization (474 distinct) + part-number extraction from filePath + the part_id format is messy (`1441__FROM__BIRMINGHAM FASTENER MFG`) + 32% have null material_iso (still fall back to H). Wire into `sfc-jm-program-corpus.mjs` material resolution as a HIGHER-confidence source above the comment/path inferer. Validates by re-running the gauntlet + checking byIso shifts off 99.7%-H + the aggressive count drops for the now-correctly-P/N parts. This is oscar+charlie(quoting)+hotel(orders) cross-domain but the DATA already exists -- no new mining.

**JOIN YIELD (iter 8, verified -- tempers the value):** of the 32,502 records with material_iso, **24,930 (77%) are customer=UNASSIGNED** (NOT joinable to a specific program); only **7,572 (23%) have a joinable real customer** -- top: FONTANA 2062, OPTIMAS 1446, AGRATI 1291, ITW 854, VALLEY GROUP 835 (fastener makers -> likely the 4140/1018 ISO-P parts where the false-aggressive flags hide). So the join is FEASIBLE but MODERATE-ROI: best-case it material-grounds ~7,572 records (before part_id-match losses), ~5% of the 154K-row corpus; the other ~95% stay default-H (empirically correct). Verdict: a legitimate, scoped enhancement (removes false-aggressive flags for the joinable P/N parts + lets the H parts be CONFIRMED real over-speeds), NOT a critical fix -- the gauntlet is already accurate-by-design. Build it cleanly with fresh budget; don't rush it at the tail of a long loop.

**JOIN-KEY DECISIVE FINDING (iter 9 -- the join is NOT cleanly feasible; do NOT build as scoped):** verified the actual key on FONTANA (2062 materialed records). Quoting keys material by JOB/PART NUMBER (`4309__FROM__FONTANA`, `0025`, `1025__FROM__FONTANA`). But the FONTANA PROGRAM FILES on disk are DESCRIPTION-named in a flat customer folder (`JM DIE/CNC LATHE/FONTANA/.../BACK OF HAMMERS FONTANA.MIN`) -- they do NOT carry the quote part-number. ALCOA-style numbered folders (`ALCOA/0007/W472A34-0007.MIN`) WOULD join, but description-named customers (the majority of the joinable 7,572) will NOT. So a (customer, part_id<->folder) join yields few reliable matches AND risks WRONG material attribution (worse than default-H). CONCLUSION: default-H is not just the modal prior -- it is the BEST AVAILABLE because the per-program material cannot be reliably joined from the quote data. A real material-accuracy lift would need a part-description<->material map or per-program setup-sheet material extraction -- a much larger, different effort, not this join. The gauntlet is as accurate as the source data allows; this is the honest end of the JM-program-side material investigation.

**INFERER-CORRECTNESS FINAL CHECK (iter 10, lever DEFINITIVELY closed -- corrects the 'needs a description-map/setup-sheet build' framing above):** verified `scripts/lib/sfc-material-infer.mjs` directly. It is CORRECT + COMPLETE -- not a bug, not under-extracting. The one explicit material comment found in the sample, `(MATERIAL - STEEL INCH - 1030 - 200 BHN)` (9007405.MIN), is ALREADY caught: the generic `\bSTEEL\b` rule -> ISO P (medium conf), and `\bHRC\b|\bHARDENED\b|A2/D2/S7/H13` -> H first by rule order, aluminum/stainless/cast-iron words -> N/M/K. It even carries a LEARNED PRECISION RULE (2026-06-24) that drops collision-prone bare numerics (625/718/304/2024) to avoid false moves off the P default.
