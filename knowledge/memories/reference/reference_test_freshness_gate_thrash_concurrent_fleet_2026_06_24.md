**Observed 2026-06-24 (slot:echo overnight loop).** The `stop_on_failing_tests` Stop gate blocks when `data/state/VITEST_REPORT.json` is older than the most-recently-edited `*.test.ts` file. With ONE builder this is fine. With the **26-slot fleet building concurrently overnight**, it THRASHES:

- echo ran the full suite (`npx vitest run --reporter=json --outputFile=data/state/VITEST_REPORT.json`, ~30 min, exit 0 green) to clear a block caused by `CADTrialErrorLearningEngine.test.ts` (delta's edit).
- Within ONE turn of that suite completing, the gate re-blocked on `MultiModelConsensusEngine.test.ts` (india/bravo's edit) — a DIFFERENT foreign test file, edited while echo's suite was running.

**Why it's un-winnable for a single slot:** the global report is fleet-shared, but every slot edits its own test files independently. The report is stale the instant ANY slot touches ANY `*.test.ts` after the last full run. A 30-min full-suite refresh is guaranteed to be re-staled by a concurrent peer before (or just after) it finishes. So a single slot can never satisfy the gate during active fleet building — it's a losing race.

**Echo's own work is unaffected:** echo's 5 committed G4 test files (GCodeVerification/Validation/Template/Runtime/IntelPipeline) were verified green BY the full suite that passed. The re-stale is purely foreign concurrent edits in unrelated domains (consensus engine, CAD), which cannot affect already-committed-and-green post-processor tests.

**Fix candidates (golf/sierra/zulu infra lane, NOT echo):** (1) make the freshness check PER-FILE/PER-SLOT (a slot's Stop only needs ITS edited test files fresh, not the whole fleet's); (2) a short grace window / debounce so concurrent edits don't instantly re-stale; (3) a per-slot report shard rather than one global VITEST_REPORT.json; (4) honor `STOP_ON_FAILING_TESTS_SKIP_FRESHNESS=1` when the staling edit is outside the current slot's domain. The gate's intent (don't ship on a stale-green) is correct; the GLOBAL granularity is the bug under concurrency.

**Compounding blocker tonight:** this thrash coincides with the 5h session limit being >120% over ceiling (account-switch unarmed/RED, operator-gated) — so the fleet is blocking regardless. Re-running the suite is doubly moot. Both blockers are operator/infra-gated; echo holds with all work committed + green.

**GENERALIZATION (2026-06-24, same root cause — a CLASS of bug, not one gate):** the `leave-a-copy-behind-guard` Stop hook ALSO thrashes the same way. At echo's Stop it blocked on 6 RENAMED pricing test files (`LocationAwareVendorPricingEngine`/`ThreeViewPricingEngine`/`VendorUnitPriceEngine` `*.test.ts` moved `src/engines/` → `src/__tests__/`) — charlie's domain, NOT echo's, and a CORRECT convention move (engine tests belong in `__tests__/`). The guard fired at echo's Stop purely because it scans the WHOLE shared working tree, which holds **13,633 uncommitted files** from all 26 slots building concurrently. **Root cause (shared by both gates): shared-tree Stop gates (`stop_on_failing_tests` freshness + `leave-a-copy-behind-guard`) scan the entire H:/prism working tree, so every slot's Stop is blocked by every OTHER slot's uncommitted changes — un-clearable by any single slot during active fleet building.** The fix is the same family as the freshness-gate fix: SCOPE the Stop-gate scan to the CURRENT slot's own changed files (git diff for files the slot touched this session), not the global working tree. Golf/sierra/zulu infra lane. Until then, overnight multi-slot loops saturate into mutual Stop-block once the shared tree accumulates foreign uncommitted churn.

**ROOT CAUSE of the 56-DAY-STALE report (verified 2026-06-24, slot:echo): the freshness gate's prescribed refresh command CANNOT RUN in a background/automated bash context -- `npx` is not on PATH there (EXIT 127).** The gate tells you to re-run `cd mcp-server && npx vitest run --reporter=json --outputFile=data/state/VITEST_REPORT.json`. In an interactive shell with `rtk`/portable-node PATH set up, `rtk npx vitest run <file>` works fine (that is how per-file green is verified). But the SAME `npx vitest` invocation launched as a `run_in_background` Bash task exits **127 (command not found)** and writes NOTHING -- the report stays frozen at its 2026-05-12 mtime. Echo confirmed this twice: two background full-suite "refreshes" both reported exit 0 / 127 but `mcp-server/data/state/VITEST_REPORT.json` never changed (stayed 18327 bytes, 2026-05-12T08:27). So the report is 56-days stale FLEET-WIDE not because nobody tries, but because the refresh tooling is broken in exactly the non-interactive contexts (crons, background tasks, automated loops) that would keep it fresh. **Implication:** the `stop_on_failing_tests` freshness gate is effectively PERMANENTLY-BLOCKING on this shared tree for any slot that edits a test file -- the only way to clear it is a FOREGROUND `rtk npx vitest run` of the full ~756-file suite (~30min, a giant-burn the overnight directive warns against), which then re-stales on the next peer test-edit anyway. **Fix family (golf/sierra/zulu infra lane), in priority order:** (1) make the report-refresh tooling PATH-robust -- invoke vitest via the portable-node binary with an absolute path (`H:/.claude/bin/portable-node <vitest.mjs>`) or via `rtk` so background/cron refreshes actually write the report; (2) THEN scope the gate per-slot (a slot's Stop needs only ITS own changed test files fresh). Until (1) lands, the report cannot stay fresh under any automation and the gate is documented-broken. A slot whose own edited test files are individually verified green (e.g. echo's U-PP-GCODEENERGY-TEST + U-PP-POSTANALYZER-TEST) has NO stale-green risk -- the block is purely this broken-refresh + whole-tree-scan infra, not a real failure. Do NOT set `STOP_ON_FAILING_TESTS_SKIP_FRESHNESS=1` in settings.json to dodge it -- that is a fleet-wide gate-softening (never soften a safety gate unilaterally).
