2026-06-09 (slot golf, synergy /loop). MCP :3100 was DOWN for 6+ consecutive Stop-hook `consolidate-graph mcp-down (fetch failed)` counters — a SUSTAINED outage, not a transient flap, degrading every `mcp__prism__*` tool + the consolidate-graph process fleet-wide.

**Root cause: duplicate wedged daemons → port-bind conflict.** `:3100` refused, but `Get-CimInstance Win32_Process` showed **TWO** `mcp-server\dist\index.js` daemons alive (PIDs 53400 + 63708), **both 2 hours old**, both parented by `cmd.exe` (NOT a managing supervisor). Two daemons can't both bind :3100 → neither served. The auto-reconnect ("daemon (re)start initiated pid 63992" in earlier Stop banners) kept spawning NEW daemons that died, while the two old wedged ones lingered holding/blocking the port.

**Recovery (operational, golf [[feedback_golf_owns_reaper|fleet-hygiene]] — no code change):**
1. `Stop-Process -Id 53400,63708 -Force` (reap both wedged daemons).
2. :3100 immediately returned **404 = UP** — removing the port-conflict let a single clean daemon (PID 79436) bind. `/health` → **200**, 3/3 stable, exactly one daemon now.
(No manual restart was even needed — the active auto-reconnect's fresh daemon bound the instant the port freed.)

**THE CORRECT :3100 START (found the hard way, 2026-06-09, commit `006c435ddb`):** the recurring outages persist partly because **the documented restart commands DON'T WORK.** `node mcp-server/dist/index.js --port 3100` runs the MCP server in **STDIO mode** (logs `Server running on stdio`) — it does NOT serve :3100 (`--port` does not switch transport). `ollama-docker-launcher.mjs --services=mcp` fails `no such service: mcp` (MCP is a node daemon, NOT a compose service). The **CORRECT** start is **`TRANSPORT=http node mcp-server/dist/index.js`** (per `mcp-http-bridge.mjs:27`); PowerShell: `$env:TRANSPORT='http'; node ...`. Validated: a TRANSPORT=http spawn brought :3100 back (404, /health 200, single daemon, singleton-guard healthy) where both documented commands failed. Fixed the wrong instructions in `mcp-connectivity-check.mjs` (006c435ddb). **Singleton guard SHIPPED (`35e01ca5f3` + Stop-wire `d3ed737c23`):** `scripts/singleton-service-guard.mjs` classifies {portUp,daemons,servingPid}→safe action (reap-all when wedged, reap-non-serving when dup, report-only when server unknown, start when none) + `--fix`; wired into `docker-service-health-stop` so a downed/duplicated MCP daemon surfaces every Stop (it caught a REAL outage the moment it was wired). Note the auto-reconnect/connectivity restart is REACTIVE (fires only when a chat hits MCP-down) — there is no persistent supervisor keeping :3100 up, so it dies between active uses; a durable keep-alive (a scheduled task that runs `singleton-service-guard --fix` + the TRANSPORT=http start) is the real fix (golf/papa).

**GAP this reveals (golf's lane):** the [[reference_fleet_reaper|fleet-reaper]] attributes orphans by SLOT and reaps orphan node/bash/git by dead-ancestor logic — but TWO legit-looking service daemons (both real MCP servers, both with live-ish cmd parents) are NOT flagged as orphans, so the reaper misses the duplicate-service-daemon case. Sister gap to the docker-service-health one (golf U-DOCKER-SERVICE-HEALTH-GUARD): nothing auto-detects a downed/duplicated named service. **Next unit (golf, fresh budget):** a singleton-service guard — detect >1 daemon bound to a known PRISM port (3100 MCP, others) and reap the older duplicate(s), OR detect :3100-down-with-daemons-alive and reap+restart. The MCP supervisor/watchdog's spawn-without-reliably-killing-old is the deeper root cause (papa's lane to fix the restart logic). **CORRECTION (2026-06-09 later, slot golf, U-MCP-FIXSTART):** the line above — *"there is no persistent supervisor keeping :3100 up… a durable keep-alive (scheduled task) is the real fix (golf/papa)"* — is **WRONG/stale.** A live `Get-ScheduledTask *MCP*` enumeration shows **FOUR** repeating MCP tasks already armed + `Ready`: `PRISM MCP Server` (the `mcp-server-supervisor.mjs` respawn loop, with the 3-min repeating trigger golf added 2026-05-31 — see [[reference_mcp_supervisor_persistence_fix_2026_05_31]]), `PRISM MCP Server Watchdog` (5-min /health→restart), `PRISM MCP Connectivity Monitor`, and `PRISM MCP Priority Guardian` (1-min). The proactive supervisor stack EXISTS; this session's recurring flaps were transient cold-boot recoveries it handled (server came back each time), NOT an unsupervised port. **A new keep-alive scheduled task would be a redundant 5th layer — DO NOT build it** (the operator-directed 06-04 resilience plan [[reference_mcp_resilience_plan_2026_06_04]] names server-core FIX-1/FIX-2 as the real wins, never a new task). What the existing stack genuinely LACKS is **duplicate-pileup reaping** (supervisor/watchdog respawn a down server but don't reap two daemons fighting for the port — the actual failure mode HERE). So the shipped fix was scoped to exactly that gap: upgraded `singleton-service-guard.mjs --fix` to reap-pileup-THEN-respawn in ONE command (was reap-only) + safe no-op when healthy (14/14 tests, live-validated no-op on the healthy daemon). The connectivity banner now points operators at the one-command `--fix`. **Lesson: enumerate the existing `*MCP*` scheduled tasks BEFORE concluding "no supervisor" — the R8 miss here was not listing them.**
