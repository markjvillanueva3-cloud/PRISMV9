**U-LORA-MACHINE-DATASET-WIRE (slot:india, 2026-06-18, commit 6b7cb17902).** The `MachineLoRABaseEngine` family (milling/5axis/millturn/wedm/sinkerEDM/laser/waterjet/grinding/lathe builders) had a PARTIAL-WIRE gap in `prism_edm` (`edmDispatcher.ts`): SinkerEDM/Laser/Waterjet builders each had a `*_lora_dataset_schema` action (requiredSchema reachable) but NO `*_lora_build_dataset` action -- so `buildDataset()` was UNREACHABLE via the dispatcher even though the engine existed and worked. Fixed by cloning the `wedm_lora_build_dataset` pattern (added 2026-06 in the WEDM builder ship): 3 ACTIONS entries + 3 typed case handlers (`params as { jobs?: RawJob[]; split?: DatasetSplitConfig }`, fail-loud non-empty-array guard, inline `await import`). New `LoRADatasetFamilyWiring.test.ts` (21 tests: source-pins `toBe(2)` + per-engine round-trip exercising each machine-specific validate/render). 31 tests green (10 WEDM + 21 family), tsc clean, 2-of-2 reviewers PASS.

**REACH-DESTINATION GAP (R15 step 3, verified same session -- the builder layer is wired but its output does NOT yet reach the GPU corpus):** the fleet LoRA corpus the GPU fine-tune consumes is `state/shared/lora/fleet-lora-combined.jsonl`, assembled by `assemble-fleet-lora-corpus.mjs` from sources REGISTERED in `state/shared/training/fleet-training-corpus-inventory.json` (hardcoded `SOURCES` array in `build-fleet-training-corpus-inventory.mjs`). The live inventory has 19 sources (vault/wiki/bridge/outcome/cad) and **ZERO** machine-builder output. So `buildDataset()` is dispatcher-reachable but nothing writes its Alpaca rows to a registered `.jsonl` -> the machine builders are a capability with no corpus destination ("building != delivering", [[feedback_ultimate_destination_check]]). The CLEAN closure (`U-LORA-MACHINE-CORPUS-PRODUCER`) SHIPPED 2026-06-18 (commits 4756e77c8b + 16bc1440f8): `scripts/build-machine-lora-datasets.mjs` -- a DI'd producer (`buildMachineDatasets({resolveBuilder, fs...})`) that reads real per-machine `RawJob`s from `state/shared/training/machine-jobs/<type>.jsonl` -> routes by machine type to the builder -> writes `state/shared/lora/machine-<type>-dataset.jsonl`; the 8 outputs are registered as `lora-training-jsonl` SOURCES in `build-fleet-training-corpus-inventory.mjs` (DRY -- imports the producer's MACHINES registry; live inventory now 27 sources, the 8 `machine-<type>-lora` at status `missing`). 8/8 hermetic tests (`build-machine-lora-datasets.test.mjs`) prove routing/write/0-row-skip/malformed-count/error-isolation WITHOUT dist or real engines. So the reach-destination PIPE is now structurally complete: real jobs -> builder -> per-machine jsonl -> inventory -> `assemble-fleet-lora-corpus.mjs` -> `fleet-lora-combined.jsonl`. REMAINING (honest, R12): the pipe emits 0 rows until (a) the owning galaxy slot drops REAL per-machine actuals at `machine-jobs/<type>.jsonl` (whiskey=lathe, oscar=speed-feed, mike=wedm/sinker/laser/waterjet, foxtrot=mill/5axis/grinding) -- NEVER synthesize jobs (poisons the fine-tune) -- and (b) for the live-engine path, a FRESH `(cd mcp-server && npm run build)` since the producer's default resolver imports the builders from `mcp-server/dist` (on-disk dist is stale; the resolver fails LOUD if a dist engine is missing). Lathe stays excluded (archive-scanning shape, own path). So "LoRA synergized to all galaxies": builder layer wired + dispatcher-reachable + corpus-feed pipe built+registered (DONE); only real per-machine data collection remains, which is each galaxy slot's job.

**Reusable lesson:** when you wire ONE member of an engine family to a dispatcher, AUDIT THE WHOLE FAMILY -- a `requiredSchema`-only action is a tell that `buildDataset` was never wired (the schema half is cheap to add and easy to stop at). Grep the dispatcher for `<machine>_lora_*` and confirm BOTH schema AND build actions exist per sibling. This is the R15 "apply-to-all" form applied to a sibling-engine set. The `as any` arg cast the anti-pattern hook flags is avoidable with a type-only import of `RawJob`/`DatasetSplitConfig` from `MachineLoRABaseEngine.js` (the file already had a type-only-import convention at the top).

**FULL-FAMILY SWEEP RESOLVED (2026-06-18, same session):** the 9 `*LoRADatasetBuilderEngine` are now all accounted for. 8 are simple `BaseLoRADatasetBuilder` wrappers, ALL wired with build+schema actions: milling/5axis/millturn (millDispatcher: `mill_lora_build_dataset` etc.), wedm/sinker/laser/waterjet (edmDispatcher), grinding (dataDispatcher -- NOTE it uses `grinding_lora_dataset_build`/`_dataset_schema` WORD-ORDER, not `_build_dataset`; a regex for `_build_dataset` misses it). The 9th, `LatheLoRADatasetBuilderEngine`, is a DIFFERENT shape -- a 716-line archive-scanning batch engine (`async buildDataset({basePath,splitConfig,maxPrograms,outputDir})` that scans `JM DIE/CNC LATHE` + writes files), part of a 40+-action `lathe_lora_*` pipeline in turningDispatcher. It is NOT an orphan (surfaced via `lathe_lora_dataset_stats` -> getStats, exercised by 2 test files); its `buildDataset` is an IO-heavy batch op, correctly run via script/cron rather than a synchronous MCP dispatcher action. So the family is appropriately complete -- do NOT chase a `lathe_lora_build_dataset` dispatcher action (it would scan an archive inside the request path).
