**U-XRAY-GDT-CORPUS-SCAN-ROUTE shipped (slot:xray, cad-fusion-live-ms0, commit `6a9f5253f6`, 2026-06-23).** Implements section 2 (the proof-run routing rule) of `state/shared/specs/BLUEPRINT-GDT-TRIBAL-INJECTION-PLAN-2026-06-19.md` (P2.10 tribal-knowledge injection).

**The bug:** `scripts/pdf-parse-extract.mjs::main` called `writeOutputs()` for EVERY `rec.ok===true` record. An image-based drawing PDF parses (via pdf-parse) to `rec.ok=true` with 0 headings + 0 real (>=80-char) paragraphs, so it STILL wrote a hollow `(no headings...)/(no paragraph...)` wiki .md + tribal jsonl row -> pollutes the knowledge corpus with empty noise. (Drawings carry no text layer; they belong to the OCR/VLM lane, `blueprint-ocr-training-loop`, not the text lane.)

**The fix (pure helper + gate):**
- `scripts/lib/pdf-parse-extract-helpers.mjs` -- NEW pure exports `classifyPdfExtraction(signals)` + `extractionSignals(record)` (+ internal `numOr0`). Rule: `charCount<=0 -> ocr no-text-layer`; `headingCount===0 && firstParagraphChars===0 -> ocr image-based-no-structure`; else `text`. A heading-only deck or paragraph-only sheet is still TEXT (real knowledge) -- only the both-empty case routes to OCR. Defensive: malformed/negative/NaN/null signals coerce to ocr (fail-safe: never emit garbage; never falsely emit).
- `scripts/pdf-parse-extract.mjs::main` -- gates `writeOutputs` with `classification.lane === "text"`. Text PDFs emit BYTE-IDENTICALLY (only change is the guard). Summary gains per-result `lane/routed_to_ocr/skip_reason/char_count/line_count` + run-level `emitted_count/routed_to_ocr_count` (R12 fail-loud). `--dry-run` summary made schema-consistent.

**Validated LIVE (numbers):** real `resources/1- Basic Training Day 1/2D_Drawing.pdf` -> lane=ocr, image-based-no-structure, 0 files written (pollution prevented). Real `resources/RESOURCE PDFS/G-Code Basics_ Program Format and Structure.pdf` -> lane=text, 9 headings/600-char paragraph, 2 files emitted (unchanged). 39/39 tests (14 new reference-value, mutation-tested by scrutiny). Per-file 2-arm scrutiny (reviewer + code-analyzer): both PASS, 0 P0/P1.

**ACCEPTED false-negative (R12, both scrutiny arms flagged, documented in the docstring):** an all-lowercase, short-line text PDF with no blank-line paragraph breaks and no ALL-CAPS/numbered/chapter lines harvests 0/0 and routes to OCR. NOT data loss -- the OCR lane re-processes it (re-routed, not dropped) -- and rare (tolerance tables trip the ALL-CAPS or numbered-line detector). `char_count`/`line_count` now logged on every routed_to_ocr record so a high-char OCR-routed PDF (a likely false-negative) is auditable.

**KEY NUANCE (do not regress):** lima's pypdf page-by-page extractor (`scripts/extract-jm-die-corpus-page-by-page.py`) is CANONICAL for NEW corpus drains ([[feedback_use_lima_pypdf_page_extractor]]). This fix hardens `pdf-parse-extract.mjs` because that is the extractor the LIVE watcher (`scripts/pdf-corpus-watcher-sweep.mjs:50`) actually spawns -- so it is on the live ingestion path.

**R15 APPLY-TO-ALL -- VERIFIED CLOSED (no clone needed):** lima's pypdf extractor ALREADY prevents empty-note pollution by design: `notability_score()` (line 90-117) returns a low score for empty/near-empty text (`if not text or len(text) < 50` line 96) and TOC/header/blank pages; `emit_tribal_entries(notability_floor=0.4)` (line 175-214) SKIPS every page below 0.4 ("skip pages below this score (likely TOC/cover/blank)"). So an image-based drawing PDF (near-empty extracted text) scores low -> skipped, never emitted. Both extractors now prevent the pollution: pdf-parse-extract via the new classifier, lima's via its pre-existing notability floor. The fix was needed ONLY for pdf-parse-extract.mjs, which had NO notability/empty gate.
