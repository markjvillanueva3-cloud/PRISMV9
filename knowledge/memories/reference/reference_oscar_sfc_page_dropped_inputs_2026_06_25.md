**Two SFC web-page accuracy bugs (slot:oscar, 2026-06-25).** Found while finishing the SFC frontend. The page (`mcp-server/web/src/pages/SfcCalculatorPage.tsx`) collected customer inputs but `handleCalculate` discarded them before POSTing to `/api/v1/sfc/calculate` (-> `prism_product:sfc_calculate` -> `ProductEngine.sfcCalculate`), so the engine fell back to DEFAULTS and every page force/MRR/power/tool-life/safety number was computed at the WRONG operating point. The page test layer was "proven" (renders + logic 234/234) but NONE of it asserted the customer's inputs actually reached the engine -- the classic "looks done" gap.

**1. U-SFC-PAGE-MACHINE-LIMITS (commit ~iter2).** The page lets the customer pick a machine (`MachineEntry.spindleMaxRpm`/`spindlePowerKw`, `data/machines.ts:7-8`) but `handleCalculate` never sent them, so `ProductEngine.sfcCalculate`'s rpm clamp (`:744`) + over-power safety (`:795/1061`) never fired for page customers -> the page could publish an unreachable spindle speed (the aluminum-RPM-cap confusion the SFC-vs-GWizard spec s6b flagged). Fix: new pure `components/sfc/buildSfcRequest.ts::buildSfcCalcRequest()` maps `spindleMaxRpm->machine_max_rpm`, `spindlePowerKw->machine_power_kw` (omits non-positive/absent so the engine treats unclamped; a 0 would falsely collapse Vc). 4 tests. Backend already accepted+tested these (`sfc-jm-fleet-page-closed-loop.test.ts`); only the wiring was missing.

**2. U-SFC-PAGE-DEPTH-WIDTH (this iter, TDD).** Bigger: the page posts cut geometry as `depth`/`width` (the `SfcParams` names) but `ProductEngine.sfcCalculate` read ONLY `depth_of_cut`/`width_of_cut`, and NOTHING in the prism_product chain mapped them (the `depth->axial_depth` maps live in `calcDispatcher`/prism_calc, a DIFFERENT path). So the customer's depth-of-cut + width-of-cut were SILENTLY IGNORED -- engine used `toolDiam*0.5` for both. TDD-proven: passing `depth:8` returned `depth_of_cut_mm=6` (=12*0.5), not 8. Fix: `SFCInput` declares `depth?`/`width?` aliases; all 4 SFCInput-reading sfc fns (`sfcCalculate`/`sfcCompare`/`sfcOptimize`/`sfcSafety`) read `depth_of_cut ?? depth ?? toolDiam*0.5` (canonical wins). R15/R16: applied to ALL 4 sites (not just the one the page hits) since the shared `SFCInput` type now advertises the alias. 2-arm scrutiny traced + cleared the consumer-collision risk: the only OTHER `params.depth`/`width` readers are the ACNC funcs reached via separate `acnc_*` actions; cross-galaxy consumers (blueprint/document extraction) pass nested `dimensions`, never top-level depth/width.

**LESSON: a frontend that "renders + has green logic tests" can still SILENTLY DROP every user input that the backend reads under a different field name** -- there was no end-to-end test asserting the page's machine/depth/width reach the engine. When wiring a page to an engine, verify the FIELD NAMES match across the whole chain (page SfcParams.depth -> request -> route -> dispatcher schema -> engine param), and add a test that proves a non-default input changes the engine output. The `buildSfcCalcRequest` helper makes the page->request mapping pure + testable. Spec: `state/shared/specs/SFC-VS-GWIZARD-HSMADVISOR-2026-06-19.md` s6.
