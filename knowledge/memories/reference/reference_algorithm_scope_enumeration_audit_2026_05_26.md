# 58-Algorithm Scope Enumeration — audit findings (2026-05-26, slot:tango /goal /loop iter5)

## Headline

In this session I produced a "Comprehensive Algorithm Scope" enumeration across 8 domains identifying 58 algorithms. When the operator said "continue", I built A (Speed-Feed algorithm 8.1, `JointSpeedFeedOptimizer`) cleanly — that one was a real gap. But when I moved to pick B (Modal-State Tracker, algorithm 6.1) and C (Op-Order Topological Sort, algorithm 2.5), **both were already built+wired**:

| Pick | "Recommended" | Reality |
|------|---------------|---------|
| A — Kienzle×Taylor Joint Solver (8.1) | New | ✅ Built clean (commit `01157e9d24`) |
| B — Modal-State Tracker (6.1) | New | ❌ `PPModalStateTrackerEngine.ts` (11.1KB), wired in `ppDispatcher.ts` |
| C — Op-Order Topological Sort (2.5) | New | ❌ `OperationSequencerEngine.ts` (18.1KB) is a SUPERSET (topo sort + TSP + thermal + deflection + Bellman-Ford + fixture grouping), wired in `multiOpDispatcher.ts` + `toolpathDispatcher.ts` |

**Hit rate: 1/3 of recommended trio = 33%.** The enumeration over-promised gap closure.

## Root cause

The enumeration was generated by domain-reasoning over what 8 domains "ought to need" rather than by *intersecting with the existing 91-algorithm + 593-unwired-engine inventory*. CLAUDE.md doctrine §"Duplication Guard Protocol" mandates `duplicationGuardEngine.checkBeforeCreating()` BEFORE creating anything. I ran that check on A (clean), but only ran it on B + C when I started building each — by then the "recommendation" was already in the prior turn's report. I anchored the operator on a flawed slate.

## Method correction for future enumerations

Before naming an algorithm as a "gap" to fill:

1. **Grep the algorithms/ dir** for keyword matches:
   `cd mcp-server/src/algorithms && ls | grep -iE "<keyword>"` — catches near-name dups.
2. **Grep the engines/ dir** with the same keywords — many "algorithms" live as Engines.
3. **Check dispatcher wiring** — `awk '/<EngineName>/{print FILENAME":"NR}' mcp-server/src/tools/dispatchers/*.ts` confirms whether it's already MCP-callable.
4. **Run duplicationGuardEngine.checkBeforeCreating** with the proposed keywords/description.
5. **Only after all 4 pass** mark the item as a real gap.

For the remaining 55 algorithms in the enumeration, this audit is unrun. Treat the list as PROPOSED-but-unverified. Each pick needs the 4-step check at build time.

## What the audit revealed about PRISM's coverage

The PRISM engine inventory is RICHER than the headline counts suggest:

- "**91 algorithms**" in `src/algorithms/` + **2,763 engines** (per CLAUDE.md awareness) means many domain algorithms live as engines, not algorithm files.
- Engine names often describe the JOB (`OperationSequencerEngine`) rather than the canonical math (`TopologicalSortAlgorithm`) — the enumeration mistook absent-by-math-name for absent.
- Existing engines frequently SUPERSET the proposed scope (OperationSequencer covers algorithm 2.5 PLUS 4 other algos in the enumeration: 2.4 Retract-Plane via thermal/deflection rules, 2.6 Adaptive-Step via TSP-tool-change, 2.8 Multi-Setup via fixture-grouping, etc.).

This means the 58-item enumeration likely overstates the gap by ≥40%. A re-audit with the 4-step method would yield a more accurate (likely 15-30 algorithm) actual-gap list.
