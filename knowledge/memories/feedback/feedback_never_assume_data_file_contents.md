NEVER assume the contents of a data file or a data folder. Before you rely on it, cite it, claim a topic is "covered" by it, or claim a gap exists "because it isn't there" — ENUMERATE it (Glob/ls the full tree + report the count) and READ its actual contents. A filename, a folder name, a title, or a one-line description is NOT evidence of what is inside. This is the shallow-search / "existence != content" failure applied specifically to DATA.

**Why:** Operator directive 2026-06-12 (slot:bravo, mill-knowledge expansion). The mill galaxy was assumed "rich/done" from the mere presence of files like `milling-pdf-cited-tips.ts`, `user-proven-cutting-data.ts`, `jm-die-profile.ts`, the JM program corpus — but nobody had documented what is ACTUALLY inside them, so real gaps (per-machine alarm refs, tool-holder/insert selection, thermal doctrine, tool-on-hand→toolpath ROI) went unseen while the galaxy was reported complete. Assuming data contents = shipping a coverage claim you cannot defend (R12 fail-loud).

**How to apply:** (1) Before authoring/expanding knowledge for a domain, DIG into its data files/folders — read them, never infer coverage from names. (2) Maintain a DATA-CONTENTS INVENTORY (what is actually inside each data file/folder: counts + schema + a real sample) so future chats can trust "documented" rather than re-digging. (3) A topic is "covered" only when a file's ACTUAL content covering it has been read + cited; otherwise it is an OPEN gap. (4) Pairs with [[feedback_read_full_content_not_titles]] (read the body, not the title) · [[feedback_never_claim_absence_without_deep_search]] · [[feedback_enumerate_before_read]].
