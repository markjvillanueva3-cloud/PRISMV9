Standing rule (2026-05-15, user directive): *"when you updates to claude, memories, project folder, obsidian memories. refelct ALL CHANGES since last update"*. Every change set must propagate across the four documentation surfaces in the same session — no silent drift.

**Why:** PRISM has four documentation surfaces that operators and other chats read independently. If only one is updated, the others silently rot and a peer chat or a fresh session sees stale guidance. Specifically the user observed gaps between code shipped and docs updated. Touch one surface → touch all surfaces.

**The four surfaces:**

1. **CLAUDE.md** (`H:/prism/CLAUDE.md` + `C:/Users/<user>/.claude/CLAUDE.md`)
   - Add/update a section for the new capability
   - Cross-link to wiki entries via `[[wiki-slug]]`
   - Cross-link to memories via `[[memory-name]]`
   - Keep the ≤200-line discipline — extract details into wiki, leave doctrine pointers here

2. **MEMORY.md** (`C:/Users/<user>/.claude/projects/H--PRISM/memory/MEMORY.md`)
   - Add a one-line index entry for any new memory file
   - Update existing entries if their pointer-fields drifted
   - Keep entries one line under ~200 chars per the memory-prune skill

3. **Project folder / wiki** (`H:/prism/knowledge/wiki/`, `state/shared/`)
   - New engine → wiki entry under `architecture/`
   - New hook → wiki entry under `hooks/` (or `architecture/hook-*.md`)
   - New skill → wiki entry
   - New cross-cutting capability → `architecture/<feature>.md` doc
   - Update `_orphans-rescue.md` if a new wiki entry has no inbound links yet

4. **Obsidian memories** (`C:/Users/<user>/.claude/projects/H--PRISM/memory/*.md`)
   - Operator memories (feedback/reference/project/user) — auto-mirrored to the vault
   - Add `[[other-memory]]` cross-references so the graph stays connected
   - When the topic spans multiple memories, write a hub memory referencing all of them

**How to apply (every commit / every shipped unit):**

```
For each shipped change:
  1. CLAUDE.md updated? (new capability / new doctrine / new pointer)
  2. MEMORY.md updated? (index line for any new memory)
  3. Wiki entry added/updated? (architecture/, hooks/, etc.)
  4. Cross-links from existing wiki/memory to the new entry?
  5. If any of (1-4) was skipped — why? Surface the gap, don't hide it.
```

**Boundary cases:**

- Doc-only changes still trigger the rule — if you update a wiki entry, update CLAUDE.md if the doctrine moved.
- Test-only changes: usually no doc reflection needed (the test IS the doc); skip with a note.
- Auto-generated files (BUILD_STATE, MILESTONE_PROGRESS, _stats.md): regenerate via their scripts, don't hand-edit. The regen IS the reflection.
- Hooks creation/removal: MUST be reflected in `HOOK_REGISTRY.json` (auto-regenerated by `↻ HOOK_REGISTRY.json regen queued` after every hook edit — verify the regen ran).
