The three knowledge surfaces — `knowledge/tribal/` (4,245 tip files), `knowledge/memories/` (84 Obsidian-style subdirs, the in-repo 2nd brain), and `state/shared/system-viz/system-graph.json` (the live 10-layer 627-edge codebase map) — are independently mature but operationally disconnected. This memory codifies how to USE them together so the next chat does not re-derive the playbook.

**Why:** The 2026-05-09 round-2 knowledge-memory scrutiny + `tribal-utilization-audit.mjs` confirmed three disconnects: (1) the tribal-embed-index covers only 381 of 4,245 tips (9%); (2) tip files lack `domain:` and `customer:` frontmatter so the system-viz join produces 0 tips for every non-EDM cluster; (3) `OBSIDIAN_VAULT` is unset on this machine so the `tribal-obsidian-mirror.mjs` script cannot externalise tips to a phone-readable vault. Together these mean the trio currently behaves as three islands rather than one compounding artefact.

**How to apply (per-surface usage rules):**

- **Tribal tips** (`knowledge/tribal/*.md`) — the cheap-retrieval layer. Query via `tribal-rerank.mjs --query "<text>" --domain <slug> --k 3` (logs to `tribal-citation-log.jsonl` so L4/L6 hooks know which tips actually fire). Never grep the directory directly — the index is the entry point. If the rerank returns <3 hits with low cosine, the domain is tribally thin → escalate to wiki query or Claude reasoning. The 9% index coverage means most queries currently miss; running `tribal-embed-index.mjs --update --full` is the highest-leverage one-shot fix.

- **Obsidian-style memories** (`knowledge/memories/<type>/<slug>.md`) — the durable belief layer. Three types per the global CLAUDE.md schema: `feedback/` (corrections + confirmed approaches), `project/` (current-work facts), `reference/` (pointers to external systems or audited state). The `wiki-precheck-inject` hook auto-surfaces top-3 entries on UserPromptSubmit when keywords match — that is the consumption path; do not Read the entire memories tree. When writing, put the rule first, then `**Why:**` and `**How to apply:**` lines so future chats can judge edge cases.

- **system-viz** (`state/shared/system-viz/system-graph.json`, query via `scripts/system-viz-query.mjs coverage-by-domain --json`) — the structural layer. Use it to (a) check before creating an engine (does the domain already have 100+? → /dedup first), (b) identify orphaned engines (in-graph but zero inbound edges), (c) plan blast-radius before edits (neighbors query). The graph is regenerated by claude-0413eca6 — do not touch from this lane; consume read-only.

**The compounding loop the trio is supposed to close:**

```
shop-floor outcome  →  /shop-knowledge captures tribal tip
                    →  tribal-embed-index --update reindexes
                    →  domain hint backfilled from filename + content
                    →  tribal-rerank starts citing it (citation log grows)
                    →  cite-frequency promotes the tip into wiki/code-tribal/
                    →  wiki entry attaches [[wiki-link]]s to engines
                    →  system-viz nightly regen colours those engines tribal-rich
                    →  next chat's audit sees tribal density, prefers cheap path
                    →  if Obsidian env is set, tribal-obsidian-mirror.mjs externalises
                       the same tips to phone for shop-floor lookup
```

Three breaks today: (a) the index is 9% coverage so step 3 is starved; (b) tips have no `domain:` field so step 4's domain weighting falls back to "general"; (c) OBSIDIAN_VAULT unset breaks step 9. Closing in that order yields the compounding behaviour the cyrilXBT post (referenced by `reference_obsidian_compound_audit_2026-05-07`) describes.

**Maintenance cadence (when each runs):**

- Tribal index: nightly cron + on-demand after any /shop-knowledge or /distill-tribal write. Currently has no cron — manual until a `wiki-morning`-style cron is wired.
- Obsidian memories: written by chats at decision/correction time + auto-injected by `wiki-precheck-inject` and `memory-rag-inject`. The PostToolUse `memory-mirror-to-vault` hook copies new memories to the vault if env is set.
- system-viz: regenerated by `/system-viz` skill (manual) or scheduled by claude-0413eca6's lane. Auto-injected on SessionStart via `BUILD_STATE.json` summary.

**Diagnostics:**

- `node H:/prism/.claude/scripts/tribal-utilization-audit.mjs` — single-shot report (index coverage, citation activity, customer-tag coverage, Obsidian env, per-domain density join). Output lands at `state/shared/tribal-utilization-report.json` and the recommendations array is the prioritised gap list.

**Anti-patterns to avoid:**

- Grepping `knowledge/tribal/*.md` directly. The corpus is too large; the index exists for a reason.
- Writing tribal tips without `domain:` and (where applicable) `customer:` frontmatter — they end up un-routable and fall through to the "general" bucket.
- Reading the full `knowledge/memories/` tree at SessionStart. The auto-inject hooks are keyword-gated; trust them.
- Editing `state/shared/system-viz/*` from any lane other than claude-0413eca6's — the graph regenerator owns it.
- Treating "OBSIDIAN_VAULT unset" as broken. The in-repo `knowledge/memories/` tree is the authoritative 2nd brain. The env-set vault is an OPTIONAL phone-mirror, not a requirement.
