## Summary

I've completed a comprehensive analysis of the chat keepalive automation in the PRISM codebase. Here are the key findings:

### Current Architecture

**Three overlapping patterns:**

1. **Loop-State Persistence** (`H:/prism/.claude/helpers/loop-state.mjs`): Tracks `/loop` iteration metadata in `H:/prism/state/shared/loop-state/loop-<session-id>.json` with stale detection (>4h idle → reap). Problem: No auto-resume on session-start.

2. **Session-Only Crons** (CronCreate with `durable=false`): Ephemeral jobs that disappear when the chat crashes. Golf-cron-registry shows the pattern for resurrection, but it's golf-specific.

3. **Session-Start Resumption Hooks** (`precompact-handoff.mjs`, `session-continuity-chain.mjs`, `session-start-compact.mjs`): Inject prior context and loop-state summaries via RESUME directives, but don't actively resurrect crons or validate that loops are actually running.

### Critical Gaps

- When a `/loop` at iter=47/target=100 crashes, the next session's precompact-handoff surfaces it in RESUME text only if the loop-state file is found and hasn't been reaped (>4h stale).
- Session-only crons vanish; the golf-cron-registry pattern (with 15m reconciliation via `cron-registry-reconcile.mjs`) solves this only for golf, not the general fleet.
- No hardwired keepalive pump—idle chats don't signal liveness, so hung chats can silently block peer chats from claiming slots.
- Session-end hooks finalize state but don't export active crons/loops to a durable registry for next-session consumption.

### The Solution Blueprint

The **GOLF-WATCHDOG-MS0** spec (esp. R2 revisions) documents the complete pattern: durable cron registry + Session-Start restoration hook + chat liveness heartbeat + reconciliation daemon. These 7 build targets show how to generalize beyond golf to keep all chats active across crashes.
