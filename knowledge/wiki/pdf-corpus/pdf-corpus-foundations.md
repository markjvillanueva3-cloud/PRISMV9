## The PDF object model — what a "text" PDF actually is (ISO 32000)

The first decision in any PDF-corpus pipeline is *what kind of PDF is this* — and that decision is made against the PDF format's own structure, so the extractor must understand the object model rather than treat the file as an opaque blob.

- **PDF is standardized as ISO 32000** and was originally developed by Adobe in 1993 — so it is an open, documented file format the extractor parses against a spec, not a proprietary black box. [confirmed via [Wikipedia — PDF](https://en.wikipedia.org/wiki/PDF)]
- **A PDF file has four structural parts: a header (`%PDF-1.7` magic + version), a body of indirect objects, a cross-reference (xref) table near the end giving the byte offset of each indirect object, and a trailer (the `startxref` keyword + offset to the xref table).** A PDF-corpus loader that recovers text from damaged/linearized/incrementally-updated files must walk this structure — the xref table is the index that lets the parser seek any object by byte offset rather than scanning linearly. [confirmed via [Wikipedia — PDF](https://en.wikipedia.org/wiki/PDF)]
- **PDF defines a small set of basic object types — boolean values, real numbers, integers, strings, names, arrays, dictionaries, streams, and null objects (nine types)** — organized in the COS (Carousel Object System) structure, with content streams describing the text, vector graphics, and images on each page. Every page's extractable text lives inside a content stream; the dictionary/array/name machinery is the metadata graph (fonts, resources, page tree) the extractor traverses to reach it. [confirmed via [Wikipedia — PDF](https://en.wikipedia.org/wiki/PDF)]
- **Text in a PDF is represented by text elements in page content streams**, using fonts and character encodings. This is the "lucky path": a text-bearing PDF carries the characters directly, so extraction is decoding-not-OCR. [confirmed via [Wikipedia — PDF](https://en.wikipedia.org/wiki/PDF)]

*Engineering relevance:* the pdf-corpus loader is a PDF-object-model parser first — it must reach the content stream of every page and read its text elements before it ever considers raster OCR.

## The text-vs-raster fork — the single most important branch in the corpus pipeline

- **A text document scanned to PDF without OCR "is an image, with no fonts or text properties."** This is the load-bearing distinction for the whole galaxy: a *searchable* PDF contains real text objects (decode them), while a *scanned* PDF is purely raster pixels (it must be OCR'd to recover any text at all). Misclassifying a scanned PDF as text-bearing silently yields zero extracted dimensions/text; misclassifying a text PDF as a scan wastes GPU on needless OCR. [confirmed via [Wikipedia — PDF](https://en.wikipedia.org/wiki/PDF)]

*Engineering relevance:* the corpus router must detect "has a real text layer vs image-only" per page and dispatch decode-vs-OCR accordingly — the wrong branch is a silent total-loss class of bug (the same family as the OCR page-0-only / parse-discard regressions already recorded for this fleet).

## The OCR pipeline — when a document is raster (Tesseract, open-source)

When the text-vs-raster fork lands on "raster," the corpus pipeline becomes an OCR pipeline. The canonical free reference implementation is Tesseract.

- **Tesseract is an open-source text-recognition (OCR) engine available under the Apache 2.0 license**, usable via command line or API, supporting 100+ languages — a legal, free OCR backend for a document corpus. [confirmed via [Tesseract OCR documentation](https://tesseract-ocr.github.io/tessdoc/)]
- **Tesseract was released as open source in 2005 by Hewlett-Packard and UNLV; Google began sponsoring it in 2006.** Its provenance is an industrial+academic OCR engine, not a toy. [confirmed via [Wikipedia — Tesseract (software)](https://en.wikipedia.org/wiki/Tesseract_(software))]
- **Since version 3 Tesseract has supported output text formatting, hOCR positional information, and page-layout analysis; version 4 added an LSTM-based (neural-network) OCR engine.** hOCR positional output is what lets a corpus pipeline keep *where on the page* each recognized word sits (bounding boxes) — essential for re-associating recognized text with layout regions and for any downstream geometry. [confirmed via [Wikipedia — Tesseract (software)](https://en.wikipedia.org/wiki/Tesseract_(software))]

*Engineering relevance:* the raster branch routes to an OCR engine that emits positioned (hOCR-style) tokens, not flat text — position is metadata the corpus pipeline must preserve.

## OCR preprocessing + recognition — the document-image-analysis primitives (free CV references)

The OCR stage is itself a chain of classical document-image-analysis steps. Each is grounded below; the shared image-formation/filtering theory under these steps points to blueprint-vision.

- **Typical OCR preprocessing is de-skewing (rotate so text lines are horizontal/vertical), despeckling (remove positive/negative spots, smooth edges), binarization (color/grayscale -> black-and-white), line removal, layout analysis/zoning (identify columns, paragraphs, captions as distinct blocks), and normalization (aspect-ratio/scale).** "Most commercial recognition algorithms work only on binary images," so binarization is a mandatory, not optional, front-end step. [confirmed via [Wikipedia — Optical character recognition](https://en.wikipedia.org/wiki/Optical_character_recognition)]
- **Binarization is thresholding a grayscale image into exactly two classes; the simplest standard method is Otsu's method, which assigns each pixel to foreground or background by grayscale intensity** (the document-scanning industry calls a two-tone image "bi-tonal"). A robust corpus binarizer for mixed-quality scans is an Otsu/adaptive-threshold problem. [confirmed via [Wikipedia — Binary image](https://en.wikipedia.org/wiki/Binary_image)]
- **The two basic recognition techniques are matrix matching (compare the glyph image to a stored glyph pixel-by-pixel — works best for typewritten text, fails on new fonts) and feature extraction (decompose glyphs into lines, closed loops, line direction, intersections — computationally efficient, used by most modern OCR and handwriting recognition).** Modern neural OCR generalizes the feature-extraction line. [confirmed via [Wikipedia — Optical character recognition](https://en.wikipedia.org/wiki/Optical_character_recognition)]
- **OCR post-processing improves accuracy by constraining output to a lexicon (a list of allowed words) and using near-neighbor / co-occurrence-frequency analysis to correct errors.** For an engineering-document corpus, the "lexicon" is the domain vocabulary (material codes, tolerance grammar, standard callouts) — a domain-constrained post-pass is a principled accuracy lever, not a hack. [confirmed via [Wikipedia — Optical character recognition](https://en.wikipedia.org/wiki/Optical_character_recognition)]
- **Reported OCR accuracy is treacherous: one study found commercial character-level accuracy of 81%-99%, but a 1% character error rate can become a 5%+ error rate when measured per whole word.** The corpus QA harness must report word-level (and field-level) accuracy, not just character-level — a single mis-OCR'd digit in a dimension is a whole-field failure. [confirmed via [Wikipedia — Optical character recognition](https://en.wikipedia.org/wiki/Optical_character_recognition)]
- **The recognition/feature-matching theory the OCR classifier builds on is grounded in a free textbook**: Richard Szeliski's *Computer Vision: Algorithms and Applications, 2nd ed.* is downloadable as a PDF for personal use (the author asks that you link to szeliski.org rather than repost), and is based on the computer-vision courses co-taught at the University of Washington (2001-2020) and Stanford (2003). [confirmed via [Szeliski — Computer Vision: Algorithms and Applications, 2nd ed. (free book)](https://szeliski.org/Book/)] — *(the chapter-level mapping to image-processing/feature-detection/recognition is owned by the blueprint-vision foundations entry, not re-derived here.)*

*Engineering relevance:* each OCR preprocessing step is a tunable corpus stage; the deeper image-formation/convolution/filter theory under them lives in blueprint-vision — point there, don't duplicate.

## Document layout analysis — recovering structure, not just characters (free CV reference)

A document is more than a character stream: it is columns, blocks, captions, tables, and reading order. Recovering that structure is a distinct stage from glyph recognition.

- **Document layout analysis is "the process of identifying and categorizing the regions of interest in the scanned image of a text document"** — segmenting text from non-text zones and arranging them in proper reading order. [confirmed via [Wikipedia — Document layout analysis](https://en.wikipedia.org/wiki/Document_layout_analysis)]
- **It splits into geometric (physical) layout analysis — labeling zones as text body, illustrations, math symbols, tables — and logical layout analysis — semantic roles like titles, captions, footnotes.** A corpus pipeline needs both: geometric zoning to crop the right region per OCR call, logical labeling to know which region is the title-block vs the notes vs the dimension table. [confirmed via [Wikipedia — Document layout analysis](https://en.wikipedia.org/wiki/Document_layout_analysis)]
- **Two algorithmic families: bottom-up (iteratively parse from raw pixels: pixels -> connected regions -> words -> lines -> text blocks; no structural assumptions but slower) and top-down (recursively cut the document into columns/blocks on white space + geometry; faster but assumes a layout structure); the named top-down algorithm is the Recursive X-Y Cut, which decomposes the document into rectangular sections.** Mixed-format engineering corpora (clean CAD-exported PDFs vs noisy shop scans) argue for a hybrid: top-down X-Y cut where white space is reliable, bottom-up connected-component clustering where it is not. [confirmed via [Wikipedia — Document layout analysis](https://en.wikipedia.org/wiki/Document_layout_analysis)]
- **Connected-component labeling (CCL) is the bottom-up primitive: on a binary image it labels each maximally connected pixel group (4-connectivity = N/S/E/W; 8-connectivity adds diagonals) with a unique id, classically via a two-pass raster scan + union-find equivalence resolution.** CCL is what isolates an individual glyph/symbol/blob from the binarized page so the recognizer and the layout grouper have atoms to work on. [confirmed via [Wikipedia — Connected-component labeling](https://en.wikipedia.org/wiki/Connected-component_labeling)]

*Engineering relevance:* the corpus pipeline's "split a multi-region page into OCR-able zones" stage is a layout-analysis problem; CCL on the binarized page provides the bottom-up atoms, recursive X-Y cut provides the top-down zoning.

## Corpus-as-index — the information-retrieval framing (free Stanford college textbook)

A pdf-corpus is ultimately built to be *searched/indexed*. The free Stanford IR textbook names the exact front-end stage the extractor implements and frames it as a classification problem.

- **"Digital documents that are the input to an indexing process are typically bytes in a file or on a web server"; once the encoding is determined, "we decode the byte sequence to a character sequence," and "the characters may have to be decoded out of some binary representation like Microsoft Word DOC files and/or a compressed format such as zip files."** PDF is exactly such a binary representation — so PDF text extraction is the textbook "obtain the character sequence" stage of an IR pipeline, and encoding determination is a real, named sub-problem. [confirmed via [Stanford — Introduction to Information Retrieval (Manning, Raghavan, Schutze), §"Obtaining the character sequence in a document"](https://nlp.stanford.edu/IR-book/html/htmledition/obtaining-the-character-sequence-in-a-document-1.html)]
- **Determining the encoding / decoding the format "can be regarded as a machine learning classification problem... but is often handled by heuristic methods, user selection, or by using provided document metadata."** This legitimizes the corpus router's text-vs-scan and encoding decisions as a classification problem with a heuristic fast path — and warns that document metadata (the PDF's own dictionaries) is a first-class signal, not to be ignored. [confirmed via [Stanford — Introduction to Information Retrieval, §"Obtaining the character sequence in a document"](https://nlp.stanford.edu/IR-book/html/htmledition/obtaining-the-character-sequence-in-a-document-1.html)]
- **After the character sequence is recovered, "Tokenization is the process of chopping character streams into *tokens*, while linguistic preprocessing then deals with building equivalence classes of tokens which are the set of *terms* that are indexed."** The extracted text is not the end state — it must be tokenized into terms before the corpus becomes searchable; this is the bridge from raw extraction to the indexed, query-able corpus. [confirmed via [Stanford — Introduction to Information Retrieval, Ch. 2 "The term vocabulary and postings lists"](https://nlp.stanford.edu/IR-book/html/htmledition/the-term-vocabulary-and-postings-lists-1.html)]

*Engineering relevance:* the corpus extractor is the "obtain character sequence -> tokenize into terms" front end of an IR system; framing it this way (free Stanford IR textbook) keeps the pipeline honest about encoding, metadata, and the decode-vs-OCR classification decision.

## Archival / preservation target — PDF/A as the durable corpus format (ISO 19005)

A long-lived document corpus benefits from a preservation-grade format; PDF/A is the standardized one, and its constraints double as a quality contract for ingested PDFs.

- **PDF/A is an ISO-standardized (ISO 19005) version of PDF specialized for archiving and long-term preservation, requiring documents to be 100% self-contained — all information needed to display the document the same way later is embedded in the file.** A corpus ingest gate can treat "PDF/A-conformant" as a strong signal that a file will extract reproducibly. [confirmed via [Wikipedia — PDF/A](https://en.wikipedia.org/wiki/PDF/A)]
- **PDF/A mandates that all fonts be embedded (and legally embeddable for universal rendering) and forbids archival-unsuitable features: audio/video, JavaScript and executable launches, encryption, external content references, and LZW compression.** Embedded fonts directly improve text extractability (the glyph-to-character mapping travels with the file); the prohibition on encryption / external references removes two common silent extraction-failure causes. [confirmed via [Wikipedia — PDF/A](https://en.wikipedia.org/wiki/PDF/A)]

*Engineering relevance:* PDF/A's "self-contained + embedded fonts + no encryption/external refs" rules are precisely the conditions under which a PDF extracts cleanly — so they make a good ingest-quality checklist even for non-PDF/A inputs.
