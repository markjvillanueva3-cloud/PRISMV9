# Frontend-App Advanced Techniques

The **world-leader-depth** layer for the **frontend-app** galaxy (owner: quebec): the state-of-the-art web-performance and rendering-architecture STRATEGIES an expert reaches for *after* the intro theory and the common gotchas. This is distinct from its two siblings — read both first:
- `frontend-app-foundations.md` = intro theory (the rendering pipeline, semantic HTML, one-way data flow, WCAG/ARIA, HTTP semantics, DOM event phases).
- `frontend-app-applied-practice.md` = common practitioner gotchas (memo defeats, stale closures, derived state, list keys, hydration mismatch, fetch races, focus loss, *basic* code-splitting).

This entry is the next altitude: **the advanced strategy that makes the difference at the top of the field** — measuring and attacking each Core Web Vital by its sub-parts, streaming the UI instead of blocking on it, shipping zero JS for non-interactive surfaces, virtualizing instead of paginating, and serving instantly-then-revalidating at the edge. ## 1. Core Web Vitals — attack each metric by its sub-parts, not as a single number

The novice optimizes "performance" as a blur. The expert decomposes each Core Web Vital into its constituent phases and attacks the phase that actually dominates in *field* data — because the lever that fixes LCP is not the lever that fixes INP.

### Technique 1.1 — Decompose LCP into its four sub-parts and target the dominant one
**CONFIRMED** ([web.dev — Optimize LCP](https://web.dev/articles/lcp)): Largest Contentful Paint (the largest image, text block, or video in the viewport) breaks into **time-to-first-byte + connection overhead -> resource load delay -> resource load time -> element render delay.** **When an expert uses it:** any time the hero/above-the-fold element renders late — you profile the breakdown first and only then choose the fix (a server/TTFB fix is wasted if the real cost is *load delay*). **Method (no numbers):** speed the LCP resource's *start* with `fetchpriority`/priority hints and `preload`; never `loading="lazy"` the LCP image (that intentionally delays the very element you are timing); render the LCP content server-side so it isn't gated on client JS. **Trade-off direction:** earlier/prioritized resource initiation improves LCP but spends initial bandwidth and request priority that other resources then lose — prioritize the LCP element *at the cost of* less-critical ones, never the reverse. **PRISM application:** the app's heaviest first-paint surfaces (dashboards, the system-viz/Recharts views per the quebec brain) are the LCP candidates — quebec profiles the sub-part breakdown per route; this entry only fixes the *order of attack*.

### Technique 1.2 — Treat INP as three phases (input delay / processing / presentation) and fix the slow phase
**CONFIRMED** ([web.dev — Optimize INP](https://web.dev/articles/inp)): an interaction's latency is **input delay (before any handler runs) + processing duration (the callbacks) + presentation delay (until the next frame paints).** Long tasks on the main thread inflate input delay so a click "does nothing" and the user clicks again. **When an expert uses it:** any sluggish click/keypress/tap — you measure which of the three phases dominates before touching code. **Method:** reduce input delay by not blocking the main thread during load (pairs with §2); reduce processing by doing less work in the handler; reduce presentation delay by avoiding large, complex layout/style recalcs and oversized DOM in the committed update. **Trade-off direction:** deferring or chunking work improves responsiveness but can delay the *completion* of the deferred work — you trade total-throughput for perceived-responsiveness, which is the correct trade for user-facing interactions. **PRISM application:** filter/search/sort interactions over large tables or graph views are INP-critical; quebec measures the per-interaction phase split.

### Technique 1.3 — Prevent CLS by reserving space *before* late content arrives
**CONFIRMED** ([web.dev — Optimize CLS](https://web.dev/articles/cls)): layout shift is caused by media without dimensions, third-party embeds/ads that resize themselves, dynamically injected content pushing existing content down, and fonts that render at a different size than their fallback. **When an expert uses it:** any "the page jumped while I was reading/clicking" report — and proactively on every image, embed, and async-loaded region. **Method:** set explicit `width`/`height` (or `aspect-ratio`) on media so the box is reserved before the bytes arrive; reserve space for dynamic content up front and show a loading placeholder of the *final* size; control web-font swap with `font-display` (and size-adjusted fallbacks) so text doesn't reflow on font load; animate with `transform` (composite-only) rather than top/left/width/height. **Trade-off direction:** reserving space trades a little extra initial whitespace for zero shift — the right trade, because a shift that moves a button under a user's finger is a correctness/safety problem, not a cosmetic one. **PRISM application:** any operator action button (run/optimize/ship) that could shift under the cursor is the highest-stakes CLS case; quebec audits the live components.

## 2. Keep the main thread free — yield, chunk, and offload long work

Foundations §3 establishes the frame budget; applied-practice covers basic code-splitting. The advanced move is actively *scheduling* long JS so the browser can service interactions between chunks — the difference between a frozen tab and a responsive one under heavy load.

### Technique 2.1 — Break up long tasks by yielding to the main thread
**CONFIRMED** ([web.dev — Optimize long tasks](https://web.dev/articles/optimize-long-tasks)): a long task is main-thread work that runs past the responsiveness budget; the portion beyond it is a "blocking period" that degrades INP. The fix is to **split a monolithic operation into smaller chunks and yield between them so higher-priority work (especially user input) can run.** **When an expert uses it:** large client-side transforms, big list builds, parsing, or any handler that visibly freezes the UI. **Method:** prefer `scheduler.yield()` (yields, then resumes with priority so your continuation isn't starved) with a `setTimeout`/`postTask` fallback for cross-browser support; batch with a time threshold so you only yield when a chunk overruns. **Anti-pattern flagged by the source:** avoid `isInputPending()` — it can falsely report no pending input and ignores non-input responsiveness like animation. **Trade-off direction:** yielding adds scheduling overhead and lengthens *wall-clock* completion of the long task, in exchange for an interactive page throughout — correct for anything the user is waiting on visually. **PRISM application:** any client-side data crunching the web app does before backend round-trips (chart prep, large result shaping) should yield; the heavy compute itself belongs on a `prism_*` dispatcher, not the browser thread (CLAUDE.md R5).

### Technique 2.2 — Move non-UI work off the main thread entirely (web workers)
**CONFIRMED** ([web.dev — Optimize long tasks](https://web.dev/articles/optimize-long-tasks)): for non-UI work, **run it in a web worker so the main thread is never blocked.** **When an expert uses it:** CPU-heavy pure computation that produces a result the UI consumes but doesn't need DOM access to produce. **Method:** post the work to a worker and message the result back; the main thread stays free to paint and handle input. **Trade-off direction:** you gain a non-blocked UI at the cost of architectural complexity and serialization/messaging overhead across the worker boundary — worth it only when the work is genuinely heavy and DOM-independent. **PRISM application:** most heavy compute in PRISM is backend (physics/CAM dispatchers), so workers are a *last-resort* client lever — but the decision rule (DOM-independent + heavy -> offload) is the same.

## 3. Stream the UI instead of blocking on it — Suspense + Server Components

The top-of-field rendering-architecture shift: don't make the user wait for the slowest data before showing *anything*, and don't ship JavaScript for parts of the page that never become interactive.

### Technique 3.1 — Stagger content reveal with nested Suspense boundaries (streaming SSR)
**CONFIRMED** ([React.dev — Suspense](https://react.dev/reference/react/Suspense)): a `<Suspense fallback={...}>` boundary shows a fallback while its children load; **nesting boundaries reveals content progressively** — outer content paints first, inner sections stream in as their data resolves, integrated with React's streaming server rendering and selective hydration. **When an expert uses it:** a page where one slow region (a heavy panel, a slow query) would otherwise hold the whole page hostage behind a single spinner. **Method:** wrap the slow subtree in its *own* nested boundary so the fast content reveals immediately and the slow content "pops in" when ready; a single shared boundary is the opposite choice (atomic reveal — everything waits for the slowest child). **Trade-off direction:** nested boundaries improve *perceived* load (content sooner) at the cost of a staggered, multi-stage reveal that needs deliberate UX design; atomic reveal is more coherent but slower-to-first-content. **PRISM application:** a dashboard combining a fast summary with a slow analytics panel should boundary the slow panel separately so the operator sees the summary instantly.

### Technique 3.2 — Keep stale content interactive during navigation with transitions + deferred values
**CONFIRMED** ([React.dev — Suspense](https://react.dev/reference/react/Suspense)): wrapping a state update in `startTransition`/`useTransition` **keeps already-revealed content on screen** instead of snapping back to a fallback; `useDeferredValue` **shows the previous result** (optionally dimmed) while the new one loads. **When an expert uses it:** route changes and search/filter UIs where flashing a spinner over content the user is already reading is jarring. **Method:** mark navigation/filter updates as transitions; defer the value that drives an expensive results list so the old list stays visible until the new one is ready. **Trade-off direction:** smoother, flicker-free updates in exchange for briefly showing *stale* content — acceptable for search/filter, but signal staleness (e.g. reduced opacity) so the user isn't misled. **PRISM application:** filtering a large parts/quotes/jobs view should defer the results so the prior view stays usable mid-keystroke.

### Technique 3.3 — Render non-interactive surfaces as Server Components to ship zero client JS for them
**CONFIRMED** ([React.dev — Server Components](https://react.dev/reference/rsc/server-components)): Server Components render **ahead of time on the server** (at build time or per-request) in an environment separate from the client bundle; they can fetch data directly and **keep large dependencies out of the client JavaScript** — the browser receives rendered output, not the component code or its libraries. Interactivity lives in Client Components marked `"use client"`. **When an expert uses it:** read-only/display-heavy surfaces (content, tables, detail panels) and anywhere a big formatting/parsing library would otherwise bloat the bundle. **Method:** make the default a Server Component (direct data access, no client cost), and push the `"use client"` boundary down to the smallest interactive leaves (buttons, inputs, toggles). **Trade-off direction:** you minimize client JS and remove client-side data waterfalls, at the cost that Server Components themselves cannot hold state or handle events — interactivity must be composed in at the boundaries. **PRISM application:** the app already consumes `prism_*` dispatchers over the HTTP bridge (quebec brain) — server-rendering the read surfaces and keeping only the action controls as Client Components is the bundle-discipline form of CLAUDE.md R5 (don't ship logic the client doesn't need).

## 4. Render less, fetch smarter — virtualization, route-level lazy load, edge

### Technique 4.1 — Virtualize (window) long lists instead of rendering every row
**CONFIRMED** ([web.dev — Virtualize large lists with react-window](https://web.dev/articles/virtualize-long-lists-react-window)): windowing **renders only the items currently in (or near) the viewport** and recycles DOM nodes as the user scrolls, so the rendered-element count is bounded by the window size, not the list length — cutting DOM nodes, style/layout work, and memory. **When an expert uses it:** any list/table/grid that can grow to thousands of rows (or an "infinite scroll" that otherwise accretes nodes forever). **Method:** mount a fixed window of rows plus a small overscan buffer; render placeholders for off-screen content. **Trade-off direction:** large performance + memory wins in exchange for added complexity — a library dependency, careful handling of variable row heights, scroll-position math, and the fact that off-screen content isn't in the DOM (affects in-page find, anchor links, and naive screen-reader traversal). **PRISM application:** large result sets (catalog rows, job/quote lists, tool tables) should virtualize rather than paginate-by-hand; quebec sets the threshold list-size at which it kicks in.

### Technique 4.2 — Route-level lazy load as an architectural default, not a one-off
**CONFIRMED** ([React.dev — Suspense](https://react.dev/reference/react/Suspense)): `lazy()` is a Suspense-enabled source — a lazily-imported component triggers its boundary's fallback while its code chunk downloads, so **the code for a route/feature loads only when that route/feature is reached.** **When an expert uses it:** as the *default* split granularity for an app — per route, and for heavy/rarely-used in-page features (editors, charts, modals). (Applied-practice §9 introduces *why* to code-split; the advanced move is making it the architectural default tied to Suspense boundaries, not a hand-picked optimization.) **Method:** wrap lazily-loaded routes/features in a Suspense boundary with a meaningful fallback so the split is invisible to the user. **Trade-off direction:** smaller initial bundle and faster first interaction, at the cost of a load delay on first navigation to the split chunk (mitigate by prefetching the likely-next chunk on idle/hover). **PRISM application:** the app's ~18 routes (quebec brain) are the natural split lines; heavy CAD/viz/editor surfaces are prime per-feature lazy targets.

### Technique 4.3 — Serve instantly then refresh in the background (stale-while-revalidate)
**CONFIRMED** ([web.dev — stale-while-revalidate](https://web.dev/articles/stale-while-revalidate)): the pattern serves a cached (possibly stale) response **immediately** while triggering a background revalidation for the *next* request — three windows: fresh (serve cached), stale-but-revalidatable (serve cached + refresh in background), expired (block on network). It lives at the HTTP `Cache-Control` layer and has a client/service-worker analog. **When an expert uses it:** data that tolerates brief staleness and benefits from instant display — dashboards, lists, reference data that changes occasionally. **Method:** set `stale-while-revalidate` on cacheable responses (and/or use the equivalent client data-layer pattern) so the user sees content with no spinner while freshness catches up out-of-band. **Trade-off direction:** prioritizes speed/immediacy over absolute freshness — explicitly the wrong choice for must-be-current data (a live safety state, a financial total mid-edit), so scope it to tolerant reads only. **PRISM application:** read-mostly surfaces over the HTTP bridge can be served stale-while-revalidate; anything safety- or money-critical (an S(x) gate result, a live quote total) must stay fresh — quebec decides per endpoint, and the HTTP idempotency/cacheability contract from foundations §6 governs which methods are even cacheable.

### Technique 4.4 — Edge / per-request server rendering to cut time-to-first-byte
**CONFIRMED** ([React.dev — Server Components](https://react.dev/reference/rsc/server-components)): Server Components can render **per-request on a web server** (as opposed to build-time), producing dynamic HTML close to where it's served. **When an expert uses it:** dynamic, per-user content that still wants fast first paint and small client JS — the combination that pure static build-time rendering or pure client rendering each can't give alone. **Method:** render dynamic surfaces server-side per request (an edge/server runtime), stream the result (§3.1), and keep interactivity in Client Components. **Trade-off direction:** faster TTFB/first paint and direct server-side data access, at the cost of server/edge runtime infrastructure and per-request compute — versus build-time static (cheapest, but can't be per-user) or client-only (no server cost, but slowest first paint + biggest bundle). **PRISM application:** the app is per-operator/per-shop dynamic, so per-request server rendering is the natural fit; *where* it runs (origin vs edge) and the runtime are **[quebec-gate]** against the live Next.js deployment.
