# tribal-to-wiki promotion

H1 of [[audit-system-synergy-2026-05-09]]. Auto-promotes high-confidence
tribal-knowledge tips from `knowledge/tribal/*.md` (~3919 entries) →
`knowledge/wiki/code-tribal/tribal-<id>.md`. The compounding-gains exemplar
of the audit: every tribal-ingest now feeds the wiki without manual curation.

## Why this exists

Pre-2026-05-20 state:

- `knowledge/tribal/` — 3919 source-of-truth tribal tips (`bobcad-cam-tips-*.md`,
  `auto-ingested-tips-*.md`, etc.) generated by various ingest pipelines.
- `knowledge/wiki/code-tribal/` — 42 hand-authored backend-dev patterns
  (`bash-cwd-and-git-c-pattern.md`, `concurrency-and-locking-patterns.md`, …).
- **No bridge** between the two. Manufacturing tribal knowledge never reached
  the wiki — the existing `tribal-by-domain-inject` hook reads the tribal
  corpus directly via vector embeddings, but the wiki was blind to it.

H1 builds the bridge as a one-way promotion: above-threshold tribal tips
become wiki entries (idempotent — never overwrites an existing entry).

## Contract

`scripts/promote-tribal-to-wiki.mjs` — pure-core + injected-IO, single-file.

```
node scripts/promote-tribal-to-wiki.mjs [--dry-run | --apply]
                                        [--threshold <N>]
                                        [--limit <N>]
                                        [--json]
```

| Flag | Default | Effect |
|---|---|---|
| `--dry-run` | default | Show candidates without writing |
| `--apply` | — | Write candidates atomically (`.tmp.{pid}+rename`) |
| `--threshold <N>` | `90` | Minimum `confidence:` for promotion |
| `--limit <N>` | unset | Cap writes per run (use small batches for human review) |
| `--json` | — | Emit machine-readable JSON |

Knobs: `PRISM_TRIBAL_PROMOTE_THRESHOLD`, `PRISM_TRIBAL_PROMOTE_LIMIT`.

## What gets promoted

A tribal entry promotes iff:

1. Lives at the top level of `knowledge/tribal/` (subdirs like
   `auto-ingested-quarantine/` are skipped — they're explicitly under review).
2. Has parseable YAML frontmatter with a numeric `confidence:` ≥ threshold.
3. Has no existing target file at `knowledge/wiki/code-tribal/tribal-<id>.md`.

## Output frontmatter

```yaml
---
name: tribal-<id>
category: code-tribal
subdomain: <original-category>       # e.g. cam_strategy / speeds_feeds
domain: tribal-knowledge             # distinguishes from hand-authored 42 dev entries
tags: [...]
confidence: <0..100>
source: "<original-source-URL-or-vendor>"
promoted_from: knowledge/tribal/<source-file>.md
promoted_at: <iso>
---
```

`domain: tribal-knowledge` deliberately differs from the pre-existing
`domain: backend-dev` so the two corpora coexist in the same directory
without semantic collision. The wiki-recall pipeline can filter by domain
to retrieve one or the other.

## First-batch ship state (2026-05-20)

Live measurement on the work PC:
- Dry-run scanned all 3919 entries in ~805 s under heavy fleet load.
- 628 entries pass the default `confidence ≥ 90` threshold.
- First `--apply --limit 5` promoted: `tribal-bc-001..004` + `tribal-bc-010`
  (5 BobCAD adaptive-roughing / chip-thinning tips).
- The remaining ~620 await operator review + batched apply.

## Safety

- **Idempotent** — `existsSync` skip ensures re-running never overwrites.
- **Atomic writes** — `.tmp.{pid}` + `rename` pattern; readers never see partial files.
- **Dry-run default** — operator must pass `--apply` to write.
- **No deletion** — promotion adds, never removes. The tribal source file stays.
- **No domain coercion** — wiki entries' `subdomain` field preserves the original
  tribal `category` (`cam_strategy`, `speeds_feeds`, …) so a reader can tell
  manufacturing-tribal from backend-dev-tribal in the same dir.
