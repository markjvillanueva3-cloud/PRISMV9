## A. Parametric generation AS CODE — drive the model from a declarative, version-controlled program

The top-of-field shift: stop *clicking* a one-off model and start *authoring a program* that emits the model from typed parameters — so the design is reproducible, diff-able, and regenerable.

### 1. Treat the CAD program as a declarative, version-controlled definition of the desired end-state

**Technique:** define *what the finished model should be* — its parameters, features, and constraints — as code under version control, rather than a sequence of hand-clicks no one can replay. **CONFIRMED** by the infrastructure-as-code discipline, which generalizes exactly: the **declarative approach "focuses on what the eventual target configuration should be"** rather than the steps; definitions kept **"in a version control system rather than manual processes"** give **reproducibility** ("any authorized party can rebuild ... identically by referencing a specific version"), **error reduction** ("removes the risk associated with human error, like manual misconfiguration"), and **auditability** ("a complete history of ... changes"). [src: [Wikipedia "Infrastructure as code"](https://en.wikipedia.org/wiki/Infrastructure_as_code)] **When an expert uses it:** any model that will be revised, re-quoted, or produced in a family — and any model an *automation* layer (not a human) must regenerate on demand. **Trade-off DIRECTION:** authoring-as-code costs more up-front effort and discipline than free-hand modeling, and pays back as the model is regenerated/revised more often — the more reuse, the higher the return; a true one-off favors direct modeling. **PRISM cad-fusion-live applies it:** the galaxy's generation engines should emit a *declarative, parameter-driven model definition* (kept in PRISM's version-controlled state) that can be re-run to reproduce the body byte-for-comparable, not a captured click-stream.

### 2. Make every generation step idempotent so a re-run or retry converges, never duplicates

**Technique:** design each generation/update step so that **applying it again produces the same end-state**, not a second copy of the feature. **CONFIRMED:** in computer science idempotence means **"multiple calls to the subroutine have the same effect on the system state as a single call,"** which lets an operation be **"repeated or retried as often as necessary without causing unintended effects"** — removing the need to track "has this already run?" and making crash-restart safe (**"if a process crashes mid-execution, you can restart it from the beginning without duplicating previous work"**). [src: [Wikipedia "Idempotence"](https://en.wikipedia.org/wiki/Idempotence)] **When an expert uses it:** any unattended/headless generation that may be retried after a transient failure, and any "regenerate this model from its definition" path. **Trade-off DIRECTION:** idempotent code is more work to write (it must check-then-act / find-or-create instead of blindly create) and buys retry-safety + restart-safety — strongly favored as automation moves from supervised to unattended. **PRISM cad-fusion-live applies it:** pairs with the durability/atomicity discipline in the applied-practice sibling (#5/#6 there) — a reaped or restarted PRISM generation job must be able to re-apply its definition and converge to the intended model, not litter the document with duplicate features.

### 3. Generative / design-automation: specify goals and constraints, let the machine produce the variants

**Technique:** at the frontier, the human stops authoring *one* geometry and instead specifies **objectives + constraints + parameters**, and the system **algorithmically produces many candidate designs** to choose from. **CONFIRMED:** generative design uses **"software to generate outputs that fulfill a set of constraints iteratively adjusted by a designer"**; the designer is a **"constraint-setter and evaluator"** who **"establish[es] the design objectives and parameters, while the computer generates candidate solutions,"** exploring **"a wider solution space"** and yielding **"multiple design alternatives from which the designer selects."** [src: [Wikipedia "Generative design"](https://en.wikipedia.org/wiki/Generative_design)] **When an expert uses it:** complex problems with a large/uncertain solution set where hand-iteration cannot cover the space. **Trade-off DIRECTION:** broadening the explored variant space raises compute cost and the burden of evaluating/down-selecting outputs — so an expert *bounds* the search (tighten objectives/constraints) rather than enumerating blindly; more exploration buys a better optimum at higher cost. **PRISM cad-fusion-live applies it:** the galaxy's parametric-generation surface is the substrate for goal-driven variant generation — emit a *family* of parameterized candidates against stated constraints, then rank/down-select, rather than committing to a single hand-shaped body. (Manufacturability scoring of the candidates is delegated to the `cad`/DFM surfaces — this galaxy owns the *parametric generation* of the variants.)

## B. Headless / scriptable session driving — run the kernel without the GUI

The live session does not require a human at a screen. The advanced operator drives the modeling engine programmatically, batch, and (where supported) without a UI at all.

### 4. Use the CAD application's API to perform the same operations a user performs interactively — programmatically

**Technique:** drive the model through the application's published API so a script does, repeatably and at scale, exactly what a human would do by hand. **CONFIRMED:** the Fusion API lets programs **"perform the same types of operations you can perform when using Fusion interactively,"** supporting both added functionality and **automation of repetitive operations**, organized around a **structured (hierarchical) object model** with **code samples** for **"common and useful workflows."** [src: [Autodesk "Fusion API — Welcome"](https://help.autodesk.com/view/fusion360/ENU/?guid=GUID-A92A4B10-3781-4925-94C6-47DA85A4F65A)] The general principle is the scripting-language story: scripts **"interact with the same ... menus, buttons"** and **automate user actions ... rather than requiring human repetition**, and embedded scripting gives **"more control and more functionality than can be available through a user interface."** [src: [Wikipedia "Scripting language"](https://en.wikipedia.org/wiki/Scripting_language)] **When an expert uses it:** any repetitive, family-table, or pipeline-fed modeling task — and anywhere the model must be produced/updated faster or more consistently than a human can click. **Trade-off DIRECTION:** API-driving trades interactive immediacy + visual feedback for repeatability + scale; the more a task repeats, the more the API wins; a single exploratory model favors the GUI. **PRISM cad-fusion-live applies it:** the galaxy is the *programmatic driver* of the live CAD session — model the object hierarchy (application -> document -> design -> feature) as the surface the engines call, and prefer published-API operations over UI-simulation where the API exists (more robust to UI changes).

### 5. Drive the kernel headless by using the CAD engine as an importable library / batch process

**Technique:** for unattended generation, run the modeling engine **without its GUI** — embed it as a library or run it in batch — so generation happens on a server/agent, not at a workstation. **CONFIRMED:** **"FreeCAD itself can also be used as a library by other programs,"** and its **"feature-based parametric modeler with a modular software architecture"** is extended **"using the Python programming language."** [src: [Wikipedia "FreeCAD"](https://en.wikipedia.org/wiki/FreeCAD)] This is the application of scripting's long batch-automation tradition — automating **"the starting and controlling of system programs"** without manual intervention. [src: [Wikipedia "Scripting language"](https://en.wikipedia.org/wiki/Scripting_language)] **When an expert uses it:** server-side/CI generation, large parameter sweeps, and any pipeline where no human is present to operate a UI. **Trade-off DIRECTION:** headless trades away interactive visualization/recovery prompts for throughput and automatability; it demands the recovery + atomicity discipline of Section E precisely *because* no human is watching to catch a half-built state. **PRISM cad-fusion-live applies it:** headless/library driving is the natural fit for PRISM's agent fleet and Blackwell host — generation can run as a batch job; but because it is unattended, it MUST carry the checkpoint/atomic/idempotent disciplines (Sections A2, E) so a reaped process resumes rather than restarts from zero. (Whether a *specific* CAD product exposes a true no-UI mode, and the exact entry point, is product-specific and **owner-gated**.)

## C. Datum-first robust-reference automation — references that survive a rebuild

The single highest-leverage durability technique in live parametric automation: anchor everything to **stable theoretical references** so an upstream edit cannot silently re-bind a downstream feature to the wrong geometry.

### 6. Anchor features to datums (planes / axes / points), not to derived faces/edges, so references survive a topology renumber

**Technique:** attach sketches, features, and mates to a **datum reference frame** — origin planes, named axes, named points — rather than to faces/edges that an upstream edit can renumber. **CONFIRMED:** a datum is **"a reference point, surface, or axis ... against which measurements are made"**; engineers select **"primary, secondary, and tertiary datums that progressively constrain degrees of freedom"** (three planes can control all six DOF), and a datum **"create[s] a structured coordinate system rather than relying on arbitrary surfaces"** — **"by establishing fixed theoretical references, datums enable consistent ... repeatability."** [src: [Wikipedia "Datum reference"](https://en.wikipedia.org/wiki/Datum_reference)] This is the strategic answer to the **topological-naming problem** documented in the applied-practice sibling (gotcha #2): a derived face named "Face6" can re-bind to a different face after an edit, but an origin plane / named datum does not get renumbered. **When an expert uses it:** every reference in a model that will ever be edited — i.e. essentially every reference in a *live* session. **Trade-off DIRECTION:** datum-first costs a little more setup (you create/maintain explicit reference geometry instead of grabbing the nearest face) and buys rebuild-survivability; the more an edit history the model will accrue, the more it pays. **PRISM cad-fusion-live applies it:** the galaxy's generation engines should *prefer datum attachments by construction* — emit features that reference named datums/origin geometry, treating a reference-to-derived-face as a flagged fragility, so generated models are robust against later parametric edits. (The deeper *kernel mechanism* of persistent/topological naming stays owner-gated per the applied-practice sibling.)

### 7. Front-load the reference frame: establish the datum/DOF skeleton before building dependent geometry

**Technique:** build the **reference skeleton first** — the primary/secondary/tertiary datum frame that pins the part's degrees of freedom — then hang features off it, so the dependency graph fans out from stable roots, not from incidental geometry. **CONFIRMED:** datums are chosen as **primary/secondary/tertiary** to **"progressively constrain degrees of freedom"** into a complete reference frame. [src: [Wikipedia "Datum reference"](https://en.wikipedia.org/wiki/Datum_reference)] This composes with the foundations sibling's DOF accounting (a free 3D part has 6 DOF; constraints/datums remove them) and with the applied-practice "base geometry first, cosmetic features last" ordering rule — the *strategy* generalization is: the most-referenced nodes should be the most stable nodes. **When an expert uses it:** at the *start* of any model that will be automated or revised; retrofitting a datum skeleton into a finished tree is far costlier. **Trade-off DIRECTION:** an explicit skeleton is more disciplined/slower to set up and minimizes the *breakage radius* of every later edit (edits touch leaves, not roots); favored strongly for any model with a long edit life. **PRISM cad-fusion-live applies it:** generation should sequence datum/reference creation before dependent features so the emitted timeline DAG (foundations Section 2) has stable roots — minimizing the regeneration blast-radius managed in Section D.

## D. Regeneration-cascade management — control the recompute, react to its events

A live parametric model is a graph that recomputes. The expert *manages* that cascade — bounding it, sequencing it, and reacting to its change events programmatically — rather than letting every edit trigger a blind full rebuild.

### 8. Control WHEN the cascade fires: defer/batch recompute around a scripted multi-edit instead of recomputing per call

**Technique:** when a script makes many edits, **suspend recompute, apply the batch, then recompute once** — instead of paying a full graph re-evaluation after every single API call. **CONFIRMED (principle):** the re-evaluable timeline is a DAG where **"modifying an early feature may cause later features to fail"** and a change cascades over the whole tree (foundations Section 2 / applied-practice A1) [src: [Wikipedia "Solid modeling"](https://en.wikipedia.org/wiki/Solid_modeling)]; the observer-pattern literature names the exact efficiency concern and its remedy: **"the subject's state may change so frequently that notifying observers on every change is inefficient,"** so systems use **throttling** to **"remain responsive without being overwhelmed by high-frequency updates."** [src: [Wikipedia "Observer pattern"](https://en.wikipedia.org/wiki/Observer_pattern)] **When an expert uses it:** any scripted sequence of more than a couple of edits on a non-trivial tree, where per-edit recompute would multiply the cost. **Trade-off DIRECTION:** deferring recompute trades intermediate visual/feedback fidelity (the model is briefly inconsistent until the batch recompute) for a large drop in total recompute cost; the bigger the tree and the more edits batched, the larger the win — but the batch MUST be wrapped atomically (applied-practice #6) so a mid-batch failure rolls back rather than leaving the deferred state half-applied. **PRISM cad-fusion-live applies it:** the galaxy's automation should group a multi-feature operation, suppress per-step recompute, and trigger one explicit recompute at the boundary — the same boundary as the atomic + single-undo unit from the applied-practice sibling. (The *specific* suspend/recompute API call is product-specific and **owner-gated**.)

### 9. React to model-change events with an observer/event-driven hook rather than polling the tree

**Technique:** subscribe to the document's **change/recompute events** and let the model *notify* the automation layer, instead of repeatedly re-reading the feature tree to detect change. **CONFIRMED:** the observer pattern maintains **"a list of its dependents, called observers ... and automatically notifies them of any state changes,"** excels in **"event-driven programming, particularly in-process systems like GUI toolkits or MVC frameworks"** handling **"GUI model changes,"** and **decouples** producers from consumers (**"separating state producers from state consumers without tight coupling,"** observers **"added and removed independently at run time"**). [src: [Wikipedia "Observer pattern"](https://en.wikipedia.org/wiki/Observer_pattern)] **When an expert uses it:** keeping a derived artifact (a drawing, a CAM setup, a validation result) in sync with a live model, and triggering downstream associativity (foundations Section 6) on edit — without busy-polling. **Trade-off DIRECTION:** event-driven is more responsive and far cheaper than polling, at the cost of more careful lifecycle handling (subscribe/unsubscribe, avoid re-entrancy into a recompute you triggered); pairs with throttling (#8) when change frequency is high. **PRISM cad-fusion-live applies it:** the galaxy's live-associativity surface should be event-driven — a model-change event is the signal that the digital-thread ripple (toolpath/inspection) may be needed (foundations Section 6) — decoupling the change-producer (the live model) from the consumers (PRISM's downstream engines).

## E. Live-session state recovery — snapshots, checkpoints, replayable definitions

The applied-practice sibling establishes the *need* for durability/atomicity (gotchas #5-#7). This section is the *advanced recovery architecture* built on that need: how a top-tier system actually survives a crash mid-session.

### 10. Take periodic point-in-time snapshots so recovery loses a window, not the whole session

**Technique:** capture the in-flight document state as a **periodic snapshot** — a point-in-time recovery point — so a crash rolls back to the *last snapshot*, not to an empty document. **CONFIRMED:** a snapshot is **"the state of a system at a particular point in time,"** a **"frozen recovery point that allows systems to revert to known-good configurations"**; periodic snapshots mean **"users can restore from the most recent snapshot rather than losing all work performed since the last complete backup,"** and **copy-on-write** keeps them cheap by **copying only changed blocks** so snapshot creation cost stays roughly constant regardless of model size. [src: [Wikipedia "Snapshot (computer storage)"](https://en.wikipedia.org/wiki/Snapshot_(computer_storage))] **When an expert uses it:** any long-running session — and *especially* an unattended headless one on a host where the process can be OOM- or reaper-killed. **Trade-off DIRECTION:** more frequent snapshots shrink the recoverable-loss window at the cost of more storage/IO overhead — the expert tunes the cadence to the work's value, NOT to a number this wiki sets (the cadence is owner-gated). **PRISM cad-fusion-live applies it:** this is the galaxy's live/long-running differentiator — a session engine should checkpoint the in-flight document periodically (mirroring PRISM's atomic-write + schema-version discipline) so a reaped CAD-automation job resumes from the last snapshot, not from zero. (The snapshot *cadence/interval* and recovery-file format are product/engine-specific and **owner-gated**.)

### 11. Make recovery replayable: a durable, version-controlled model definition IS the ultimate recovery point

**Technique:** because the model is authored as code (Section A1) under version control, the strongest recovery is to **re-run the definition** — the program reproduces the model deterministically, so the "recovery point" is the committed definition itself, not just a binary snapshot. **CONFIRMED:** version-controlled declarative definitions give **reproducibility** — **"any authorized party can rebuild ... identically by referencing a specific version"** [src: [Wikipedia "Infrastructure as code"](https://en.wikipedia.org/wiki/Infrastructure_as_code)] — and **idempotent application** means re-running the definition **converges to the same end-state** rather than duplicating work [src: [Wikipedia "Idempotence"](https://en.wikipedia.org/wiki/Idempotence)]. **When an expert uses it:** as the backstop beneath snapshots — when a snapshot is unavailable or stale, re-run the definition; when both exist, the definition is the source of truth and the snapshot is the fast path. **Trade-off DIRECTION:** a replayable definition is the most robust recovery (a text definition cannot bit-rot like a binary and is diff-able), at the cost of the up-front authoring-as-code discipline (Section A); favored for any model whose generation is automated. **PRISM cad-fusion-live applies it:** the galaxy should treat the *committed parametric definition* as the canonical model-of-record and any binary snapshot as a regenerable cache — so recovery is "re-run the definition idempotently," composing Sections A1, A2, and E10 into one recovery architecture.
