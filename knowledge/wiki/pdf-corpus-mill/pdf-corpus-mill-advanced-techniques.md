# PDF-Corpus-Mill Advanced Techniques

The **world-leader-depth** layer for the `pdf-corpus-mill` galaxy: the state-of-the-art strategies an expert in mill-document extraction reaches for AFTER the intro theory and AFTER the common gotchas are handled. Read [`pdf-corpus-mill-foundations.md`](./pdf-corpus-mill-foundations.md) (why a mill corpus is a table-extraction + template-OCR + domain-lexicon problem) and [`pdf-corpus-mill-applied-practice.md`](./pdf-corpus-mill-applied-practice.md) (what goes wrong and how to keep it loud) FIRST — this entry does NOT repeat them. It carries only the advanced strategy that makes the difference at the top of the field.

Two organizing principles run through every section below, both distinct from the sibling entries:

1. **Stage the pipeline so each stage is independently verifiable and gated.** A top extractor never runs OCR on a whole page and hopes; it runs *layout analysis -> region routing -> structure recognition -> confidence-gated content extraction -> entity reconciliation*, with a measurable quality signal between each. This is the strategy the gotchas presuppose but never state.
2. **Treat the highest-blast-radius fields (units, diameter-vs-radius, tool/material codes) as STRUCTURED-LANGUAGE parse targets with their own grammars and reconciliation passes — never as free text.** The advanced move is to model the grammar, not to raise the average OCR accuracy.

R12-SAFETY note up front: this entry promotes only the SHAPE of a relationship and the DIRECTION of a trade-off. It states no SFM/RPM/IPR/chip-load/feed/DOC/coolant number and no kc1.1/Taylor C-n constant — those are owner-gated for golf and live only in `mcp-server/src/physics/constants.ts`. Any speeds/feeds VALUE that the corpus EXTRACTS from a manual is data, not a constant this galaxy authors.

## Theme A — Layout analysis FIRST: the staged-pipeline strategy

The single highest-leverage architectural decision: run document-layout analysis as a separate, prior stage and let it ROUTE each region to the right extractor, instead of pushing whole pages through one OCR/text pass.

- **Technique A1 — Layout analysis as a distinct pre-OCR stage that segments physical zones.** WHEN an expert uses it: on any heterogeneous mill page (a manual page mixing prose, an alarm table, and an inset drawing). The strategy: "Document layout analysis is typically performed before a document image is sent to an OCR engine," and geometric layout analysis is the "detection and labeling of the different zones (or blocks) as text body, illustrations, math symbols, and tables." TRADE-OFF DIRECTION: adding the layout stage costs an extra pass and a model/heuristic to maintain, but it prevents the dominant corpus-corruption mode (a table linearized as prose) by routing each zone to the matching extractor. [confirmed via [Wikipedia — Document layout analysis](https://en.wikipedia.org/wiki/Document_layout_analysis)]. *Galaxy hit:* the mill corpus loader should classify-then-segment a page into {prose, table, drawing} zones BEFORE choosing a Tesseract PSM or a table extractor — this is the architecture the foundations' "classify-then-template" and the applied-practice "PSM per page type" both assume.

- **Technique A2 — Choose top-down vs bottom-up segmentation by document regularity.** WHEN: top-down ("iteratively cut up a document into columns and blocks based on white space and geometric information") for the *regular, repeated* vendor layouts (a fixed catalog spread, a templated Haas manual page); bottom-up ("first parse a document into connected regions of black and white, then ... grouped into words, then into text lines, and finally into text blocks") for *irregular or scanned* pages where the global structure can't be assumed. TRADE-OFF DIRECTION: top-down is "faster, but ... typically require[s] a number of assumptions ... about the layout"; bottom-up "require[s] no assumptions" but is "time consuming." So an expert picks top-down where a known template lets them assume structure, bottom-up where they can't. [confirmed via [Wikipedia — Document layout analysis](https://en.wikipedia.org/wiki/Document_layout_analysis)]. *Galaxy hit:* a vendor catalog with a stable spread -> top-down (fast, assume the columns); a degraded photocopied JM Die manual scan -> bottom-up (no layout assumption survives the noise).

- **Technique A3 — Recover LOGICAL reading-order separately from the geometric blocks.** WHEN: any multi-column manual page, where physical block detection alone interleaves columns. The strategy: geometric layout analysis finds the blocks, but logical layout analysis is a *separate* problem — "text zones play different logical roles inside the document (titles, captions, footnotes, etc.) and this kind of semantic labeling" — which includes resolving the order/role of the blocks, not just their boxes. TRADE-OFF DIRECTION: a second logical pass costs more but is what turns detected-blocks into a coherent read-order; skipping it is exactly the two-column-interleave failure the applied-practice entry flags. [confirmed via [Wikipedia — Document layout analysis](https://en.wikipedia.org/wiki/Document_layout_analysis)]. *Galaxy hit:* a two-column Haas programming-manual page needs the logical/reading-order pass on top of block detection so the corpus stores the column flow, not line-interleaved nonsense.

## Theme B — Structure recognition vs detection, and the multimodal frontier

The advanced table strategy is to split *detecting that a table exists / where it is* from *recognizing its internal cell structure*, and to consider models that fuse text + spatial position rather than reasoning over text alone.

- **Technique B1 — Constrain extraction to a known table ZONE before recognizing structure (table detection, decoupled).** WHEN: any *templated* mill document where the table always sits in roughly the same place (a catalog's spec block, an alarm-list column). The strategy: Camelot lets you pass `table_areas` ("strings of the form x1,y1,x2,y2 where (x1, y1) -> top-left and (x2, y2) -> bottom-right in PDF coordinate space") for exact zones, or `table_regions` so "camelot will only analyze the specified regions to look for tables" when the position varies slightly. TRADE-OFF DIRECTION: pinning the zone costs a per-template coordinate map to maintain, but it removes whole-page false-positive tables and focuses recognition where the value is — strictly better than full-page auto-detection on a known layout. [confirmed via [Camelot — Advanced usage](https://camelot-py.readthedocs.io/en/latest/user/advanced.html)]. *Galaxy hit:* the mill catalog/alarm templates carry the table in a stable zone — supply the zone (detection done by the template) and let the extractor spend its effort on cell-structure recognition.

- **Technique B2 — Gate and RANK extractions on a programmatic structure-quality score, not eyeballing.** WHEN: at corpus scale, where no human reviews every table. The strategy: Camelot's `Table.parsing_report` exposes `accuracy` (0-100, "how correctly the table structure was detected") and `whitespace` (0-100, proportion of empty cells), and extractions can be filtered/ranked programmatically (`tables.filter(min_accuracy=...).filter(max_whitespace=...)`). TRADE-OFF DIRECTION: computing and enforcing a quality score adds a gate (and rejects/queues some tables for re-extraction) but is the only way a structure-recognition error fails LOUD instead of entering the corpus as plausible-looking garbage. [confirmed via [Camelot — Advanced usage](https://camelot-py.readthedocs.io/en/latest/user/advanced.html)]. *Galaxy hit:* every extracted speeds/feeds table passes a structure-quality gate before ingest; below the (owner-gated) floor it is rejected and re-run, never silently stored. The numeric floor itself is owner-gated.

- **Technique B3 — Reach for a layout-aware MULTIMODAL model when text-only extraction plateaus.** WHEN: on documents where position carries meaning that flat text loses (a spec value's meaning depends on which column/row it sits in). The strategy: Document AI "combines text data, which has a time dimension, with other types of data, such as the position of an address in a business letter, which is spatial," and "with the advent of dimension-type agnostic transformer architecture, these two different types of dimension can be more easily combined." The field has also moved "beyond extraction toward generative tasks" with large language models. TRADE-OFF DIRECTION: a multimodal/transformer model is heavier (compute, a trained model to host) than rule/template extraction, so an expert escalates to it only where the text-plus-layout coupling is what's failing — not as a first resort over a clean templated table. [confirmed via [Wikipedia — Document AI](https://en.wikipedia.org/wiki/Document_AI)]. *Galaxy hit:* when a mill catalog's column semantics can't be recovered by geometry alone, a layout-aware model that jointly reads text + (x,y) position is the principled escalation — and it runs on the Blackwell box the fleet targets, so the compute trade-off is favorable here.

## Theme C — Confidence-gated, multi-engine ensemble OCR

The expert move beyond "tune Tesseract" is to make OCR emit a per-field CONFIDENCE and to run MULTIPLE diverse engines and reconcile them — so a low-confidence or disagreed field is caught, not averaged away.

- **Technique C1 — Extract word-level confidence + bounding boxes, not just plain text.** WHEN: always, on any field that must be exactly right (a tool SKU, an alarm number, a dimension). The strategy: Tesseract's `hocr` output carries per-word confidence and coordinates (`<span class='ocrx_word' ... title='bbox 65 41 111 61; x_wconf 96'>`), and the `tsv` output has columns "left, top, width, height, conf, text" at the word level. TRADE-OFF DIRECTION: requesting hocr/tsv instead of plain text costs nothing at runtime but yields a per-field confidence the pipeline can THRESHOLD on — turning silent mis-reads into flagged low-confidence fields. [confirmed via [Tesseract — Command-Line Usage](https://tesseract-ocr.github.io/tessdoc/Command-Line-Usage.html)]. *Galaxy hit:* the mill OCR stage emits per-word `x_wconf`; any code/dimension below the (owner-gated) confidence floor is routed to review/re-OCR rather than ingested as fact.

- **Technique C2 — Select the OCR ENGINE MODE deliberately and keep a diverse fallback.** WHEN: an expert pins `--oem 1` (the modern LSTM/neural-net engine) as the default but keeps the legacy engine (`--oem 0`) available, because the two engines fail on *different* inputs. The strategy: Tesseract exposes `--oem` with the LSTM neural-net engine and the legacy engine as distinct modes. TRADE-OFF DIRECTION: maintaining two engines costs setup and the legacy traineddata, but a second engine that errs differently is the raw material for the consensus step below. [confirmed via [Tesseract — Command-Line Usage](https://tesseract-ocr.github.io/tessdoc/Command-Line-Usage.html)]. *Galaxy hit:* the mill corpus keeps a diverse engine roster (Tesseract LSTM + at least one differently-architected reader) so disagreement is meaningful.

- **Technique C3 — ENSEMBLE multiple diverse OCR/VLM readers and take a corroborated consensus.** WHEN: on the highest-value, highest-blast-radius fields where a single reader's hallucination is unacceptable. The strategy: "ensemble methods use multiple learning algorithms to obtain better predictive performance than could be obtained from any of the constituent learning algorithms alone," and crucially "ensembles tend to yield better results when there is a significant diversity among the models" (i.e. they must make uncorrelated errors). TRADE-OFF DIRECTION: "evaluating the prediction of an ensemble typically requires more computation than evaluating the prediction of a single model" — N readers cost N-fold inference — but on a box with the spare GPU to run several families concurrently, the accuracy/robustness gain on load-bearing fields is worth it; a field where >=2 diverse readers agree is corroborated, a 1-of-N field is a hallucination candidate. [confirmed via [Wikipedia — Ensemble learning](https://en.wikipedia.org/wiki/Ensemble_learning)]. *Galaxy hit:* this is exactly PRISM's already-shipped multi-VLM ensemble-fuse pattern (>=2-agree = corroborated, 1-of-N = hallucination-candidate; see the 2026-06-04 vision-ensemble-fuse work) generalized to the mill corpus — and the diversity requirement is why the roster must span different model families, not N copies of one.

## Theme D — Domain adaptation as an active, data-efficient loop

The foundations entry establishes that a generic NLP/NER model is brittle on milling vocabulary and that domain adaptation is mandatory. The advanced strategy is HOW to adapt cheaply: an active-learning loop that spends scarce human labels on exactly the examples the model is least sure about.

- **Technique D1 — Active learning / uncertainty sampling to adapt the extractor with minimal labels.** WHEN: building or refining the milling NER/field-typing model, where labeling is expensive and most pages are easy. The strategy: in active learning "a learning algorithm can interactively query a human user ... to label new data points," and "since the learner chooses the examples, the number of examples to learn a concept can often be much lower than the number required in normal supervised learning"; the primary query strategy (uncertainty sampling) targets "points for which the current model is least certain as to what the correct output should be." TRADE-OFF DIRECTION: you must build the query loop and accept that "there is a risk that the algorithm is overwhelmed by uninformative examples," but in return you reach a usable domain model with far fewer expensive expert labels than passive bulk labeling. [confirmed via [Wikipedia — Active learning (machine learning)](https://en.wikipedia.org/wiki/Active_learning_(machine_learning))]. *Galaxy hit:* the natural source of "least-certain" examples is the low-confidence (C1) and disagreed-ensemble (C3) fields — route those to the operator for labeling, and the labels both fix the corpus AND become the next domain-adaptation training batch. This closes the loop the foundations entry says is mandatory, at the lowest labeling cost.

## Theme E — Load-bearing fields as STRUCTURED-LANGUAGE parse + reconciliation targets

The decisive expert habit: the fields that cause 25.4x or 2x errors are not free text — they obey a known grammar (units context, GD&T feature control frames) and they must be reconciled against an authority (the milling code/material lexicon) with a tolerant-but-principled matcher.

- **Technique E1 — Units-resolution FIRST, with the title-block unit as a REQUIRED record field (an architectural rule, not a post-check).** WHEN: before any dimension on a sheet is stored. The strategy is to elevate the units decision from "infer per number" to "resolve the sheet's unit FIRST and propagate it, and refuse to store a dimension whose unit is unresolved." This is the same separation document layout analysis already endorses (resolve the title-block zone before the dimension zones). TRADE-OFF DIRECTION: making the unit a required, enforced field (a dimension with no resolved unit is a hard error, not a defaulted value) costs a stricter schema and rejects some records, but it eliminates the latent unit-mismatch error class entirely — and the SHAPE of that error is catastrophic (a unit slip is a 25.4x scale error, the canonical silent-loss failure). The numeric conversion factor is a definition, not a cutting constant, and lives in the units guard / constants, not here. [grounded in PRISM's UNITS-FIRST rail + the title-block-unit and Mars-Climate-Orbiter sources already cited in pdf-corpus-mill-applied-practice.md — not re-fetched here to avoid duplication]. *Galaxy hit:* the mill corpus schema makes `unit` a required field of every dimensional record, populated from the title-block resolution stage; a dimension extracted before the unit is resolved is `unit-unknown`, never `unit-default`. This is the architectural form of the applied-practice gotcha, promoted to a non-negotiable schema rule.

- **Technique E2 — Parse a GD&T callout with its GRAMMAR (the feature control frame), not as a text string.** WHEN: any mill page carrying a dimensioned/toleranced drawing region. The strategy: GD&T is "a system for defining and communicating engineering tolerances via a symbolic language," and a geometric tolerance is carried by a feature control frame — "rectangular boxes on a drawing that indicate the type of geometric control, tolerance value, modifier(s) and/or datum(s)" — i.e. an ORDERED structure: geometric-characteristic symbol, then tolerance value, then optional modifier, then datum reference(s). TRADE-OFF DIRECTION: building a feature-control-frame parser (a small grammar over a fixed symbol set) is more work than dumping the box as text, but it recovers each component into its correct slot and lets you VALIDATE the callout (a frame missing its tolerance value, or a diameter-vs-radius prefix that doesn't fit the geometry, is flagged) — turning a high-blast-radius mis-read into a caught structural error. [confirmed via [Wikipedia — Geometric dimensioning and tolerancing](https://en.wikipedia.org/wiki/Geometric_dimensioning_and_tolerancing)]. *Galaxy hit:* when the layout stage (A1) routes a region to "drawing with tolerances," parse the feature control frame as the ordered structure it is; this is the advanced complement to the applied-practice diameter/radius gotcha — model the grammar, don't just guess the prefix. (The metrology/GD&T extraction depth itself is owned by the blueprint-vision galaxy; this galaxy detects + routes + structurally validates.)

- **Technique E3 — Reconcile extracted codes/materials against the lexicon with PROBABILISTIC record linkage, not exact-match-or-fail.** WHEN: matching an OCR'd tool SKU / material grade / machine code to the authoritative milling lexicon, where the OCR may have slipped a character. The strategy: deterministic ("rules-based") linkage "generates links based on the number of individual identifiers that match" and is exact-or-fail; probabilistic ("fuzzy matching") linkage instead computes "weights for each identifier based on its estimated ability to correctly identify a match," and "blocking ... has the effect of increasing the positive predictive value (precision) at the expense of sensitivity (recall)." TRADE-OFF DIRECTION: probabilistic linkage tolerates OCR slips (recovering matches deterministic matching would drop) but introduces false-positive risk, so an expert tunes the weight thresholds and reserves a borderline band for human review ("human review often becomes necessary for borderline cases between acceptance and rejection thresholds"). [confirmed via [Wikipedia — Record linkage](https://en.wikipedia.org/wiki/Record_linkage)]. *Galaxy hit:* an OCR'd `EM-O5OO-4FL` reconciles to the canonical `EM-0500-4FL` via weighted/fuzzy linkage against the milling lexicon — and a low-confidence borderline match is exactly an active-learning (D1) query, not a silent auto-link. This is the principled, scale-safe upgrade of the foundations' tolerant-retrieval idea: not just "robust query lookup" but "weighted entity reconciliation with a review band." The numeric weight thresholds / edit-distance / acceptance band are owner-gated.

## How the eleven techniques compose (the staged pipeline, end to end)

An expert mill-document extractor is the COMPOSITION, in order: **classify page type -> layout analysis [A1] segments zones -> pick top-down/bottom-up by regularity [A2] -> recover reading order [A3] -> route each zone -> for tables: constrain to zone [B1], recognize structure, gate on quality score [B2], escalate to multimodal only on plateau [B3] -> for OCR: emit confidence [C1], deliberate engine mode + diverse fallback [C2], ensemble-consensus the load-bearing fields [C3] -> resolve units FIRST as a required field [E1], parse GD&T frames by grammar [E2], reconcile codes via probabilistic linkage [E3] -> the low-confidence / disagreed / borderline fields feed the active-learning loop [D1] that cheaply improves the domain model for next time.** Each arrow is a gate where a failure is made LOUD; none is "OCR the page and hope."
