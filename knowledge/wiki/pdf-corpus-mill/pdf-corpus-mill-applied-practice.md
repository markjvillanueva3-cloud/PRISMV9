# PDF-Corpus-Mill Applied Practice

The **practitioner-knowledge** layer for the `pdf-corpus-mill` galaxy: the hard-won engineering gotchas, failure modes, and technique decisions that pure theory does not teach. Read [`pdf-corpus-mill-foundations.md`](./pdf-corpus-mill-foundations.md) FIRST — it grounds *why* a mill corpus is a table-extraction + template-OCR + domain-lexicon problem. This entry is the complement: **what actually goes wrong when you extract a Haas/Mazak manual or a milling tool catalog, and how an expert keeps it from corrupting the corpus.** Every claim is checked against a free/legal source fetched this session; anything a source did not confirm is parked under Owner-gate.

A unifying theme across all five sections: in a mill corpus a *silent* extraction error is worse than a loud failure, because a misaligned speeds/feeds row or a mis-read diameter looks like valid data downstream. The expert's job is to make those failures loud or impossible, not to chase a higher average accuracy.

## 1. Table column/row alignment — the dominant failure mode of a tool catalog

A milling tool catalog's value is a grid (diameter | flutes | helix | coating | SFM | IPT | DOC). Recovering that grid is where most corpus corruption happens.

- **Gotcha: a PDF tool catalog has no `<td>` markup, so a flat text dump scrambles the grid into token soup.** WHY: pypdf documents that "the text within a PDF document is absolutely positioned, meaning that every single character could be positioned on the page" and that this "makes it very hard to guarantee correct whitespaces"; it even poses the unsolvable-in-general question "how many spaces should be extracted if there is 3 cm of horizontal whitespace?" [confirmed via [pypdf — Extract text](https://pypdf.readthedocs.io/en/stable/user/extract-text.html)]. EXPERT AVOIDANCE: never use plain text extraction on a catalog page — run a geometry-aware table extractor, or pypdf's `extraction_mode="layout"` (a "fixed width format that closely adheres to the rendered layout"), so column positions are preserved instead of reflowed. *Galaxy hit:* the mill corpus catalog path must keep x-positions; a flat dump merges the SFM and IPT columns into one unparseable string.

- **Gotcha: ruling-line ("Lattice") detection fails on faint/scanned tables and silently returns nothing or a broken grid.** WHY: Camelot's Lattice flavor "relies on ruled lines"; lines "in the background instead of foreground," "gaps at corners from older scanned documents," and "faint vector graphics the rasterizer misses" all defeat it. [confirmed via [Camelot — Advanced usage](https://camelot-py.readthedocs.io/en/latest/user/advanced.html)]. EXPERT AVOIDANCE: for a borderless or scanned catalog use the whitespace-based `Stream` flavor; for faint-but-present lines enable `process_background=True` and tune `line_scale` (larger detects shorter lines). *Galaxy hit:* old JM Die / vendor catalog scans have no clean ruling lines — Lattice-only is the wrong default for the mill corpus.

- **Gotcha: whitespace ("Stream") parsing mis-assigns text to the wrong column when rows are tall or columns sit close.** WHY: Camelot's Stream flavor "uses whitespace and text positioning" and "struggles with tables lacking clear column structure," "text positioned far apart vertically," and "inconsistent row heights." [confirmed via [Camelot — Advanced usage](https://camelot-py.readthedocs.io/en/latest/user/advanced.html)]. EXPERT AVOIDANCE: pin the column separators explicitly with the `columns` parameter (comma-separated x-coordinates) and set `split_text=True` to "split any strings that lie in different cells but have been assigned to a single" cell; tune `row_tol` / `edge_tol` for proximity. *Galaxy hit:* a milling spec table with a wide SFM range next to a narrow flute count is exactly the close-column / tall-row case where unpinned Stream merges cells.

- **Gotcha: a spanning/merged header cell (one "Coated" label over four coating columns) drifts the data rows out of alignment.** WHY: Camelot exposes `shift_text` (default `['l','t']` shifts spanning text left-then-top) and `copy_text` (`['v']`/`['h']` to copy a spanning label into the empty cells it covers) precisely because merged cells leave holes that misalign downstream rows. [confirmed via [Camelot — Advanced usage](https://camelot-py.readthedocs.io/en/latest/user/advanced.html)]. EXPERT AVOIDANCE: decide the gravity (`shift_text`) or fill (`copy_text`) policy per catalog layout rather than accepting the default. *Galaxy hit:* multi-coating end-mill tables routinely span a header over several columns — uncontrolled, every tool below it shifts one cell.

- **Gotcha: a low-quality extracted table looks fine but is mostly noise.** WHY: Camelot ships a `parsing_report` with `accuracy` and `whitespace` metrics (0-100) and a `TableList.filter()` on `min_accuracy`/`max_whitespace` because some extractions are quantitatively garbage. [confirmed via [Camelot — Advanced usage](https://camelot-py.readthedocs.io/en/latest/user/advanced.html)]. EXPERT AVOIDANCE: gate every extracted catalog table on its accuracy/whitespace score before it enters the corpus; reject and re-extract rather than ingest. *Galaxy hit:* the mill corpus loader needs a per-table quality gate so a scrambled speeds/feeds table never silently becomes "shop knowledge." (The numeric floor itself is owner-gated.)

## 2. UNITS in a machining document — inch vs mm in the SAME manual

The single most dangerous mill-document gotcha: a dimensionless number that the corpus treats as units-agnostic, when the source mixed inch and millimeter.

- **Gotcha: a numeric value with no attached unit is a latent 25.4x error.** WHY: an inch is defined as **exactly 25.4 mm** ("the inch has been based on the metric system and defined as exactly 25.4 mm"). [confirmed via [Wikipedia — Inch](https://en.wikipedia.org/wiki/Inch)]. So a tool diameter "0.5" read as mm instead of inch (or vice versa) is off by 25.4x. EXPERT AVOIDANCE: never store an extracted dimension without its resolved unit; carry the unit as a required field of the record. *Galaxy hit:* this is the exact failure PRISM's UNITS-FIRST rail names (a part built metric when it was inch -> tool + holder 25.4x oversized) — the corpus must not be the place a unitless number enters the system.

- **Gotcha: mixing two unit systems through a software interface causes total, silent loss — the canonical engineering case.** WHY: the Mars Climate Orbiter was lost because "one piece of ground software ... produced results in a United States customary unit ... while a second system ... expected those results to be in SI units," with software using pound-force-seconds "as if they were newton-seconds, never converting between the two unit systems." [confirmed via [Wikipedia — Mars Climate Orbiter](https://en.wikipedia.org/wiki/Mars_Climate_Orbiter)]. EXPERT AVOIDANCE: make the unit an explicit, enforced part of the data interface (the corpus schema), never an assumed default. *Galaxy hit:* a milling manual may quote inch in one table and mm in an appendix; the corpus interface must demand the unit at the cell, not infer it once for the document.

- **Gotcha: the units are usually declared in the title block, NOT next to each number — so per-number context is missing.** WHY: the title block specifies "measurement units of the drawing (for example, inches, millimeters)" and "default tolerances for dimension callouts where no tolerance is specified." [confirmed via [Wikipedia — Engineering drawing](https://en.wikipedia.org/wiki/Engineering_drawing)]. EXPERT AVOIDANCE: extract the title-block unit FIRST and propagate it to every dimension on that sheet; treat a dimension found before the title block is resolved as unit-unknown, not unit-default. *Galaxy hit:* a mill setup sheet / fixture print embedded in a manual carries its unit only in the title block — read it before the dimension rows.

## 3. OCR of a dimensioned drawing — diameter/radius and confusable glyphs

When a mill PDF carries a drawing, the symbols and characters most likely to be mis-read are exactly the load-bearing ones.

- **Gotcha: the diameter symbol is a circle-with-a-slash that OCR readily confuses with O, 0, or Q — and radius is just a leading "R".** WHY: "diametral dimensions use a circle with forward-leaning diagonal line through it, called the diameter symbol," while "radial dimensions use an 'R' followed by the value for the radius." [confirmed via [Wikipedia — Engineering drawing](https://en.wikipedia.org/wiki/Engineering_drawing)]. A diameter callout misread as a radius (or vice versa) is a **2x** geometric error. EXPERT AVOIDANCE: treat the diameter glyph and the leading-R as a dimension-prefix recognition sub-problem (template/zone OCR), not generic text; flag any dimension whose prefix is ambiguous for review rather than guessing diameter-vs-radius. *Galaxy hit:* a mill feature called out as diameter but ingested as radius doubles the modeled bore — a silent, high-blast-radius corpus error.

- **Gotcha: zero/O, one/l/I and touching characters are the classic OCR confusions, and they live inside tool codes and dimensions.** WHY: OCR struggles where "whitespace between letters can sometimes be greater than that between words, and vertical lines can intersect more than one character" (touching/proportional-font segmentation), and historically cannot even separate similar glyphs (the long-s/f case). [confirmed via [Wikipedia — Optical character recognition](https://en.wikipedia.org/wiki/Optical_character_recognition)]. EXPERT AVOIDANCE: constrain the OCR with a domain lexicon — "OCR accuracy can be increased if the output is constrained by a lexicon" and a "smaller dictionary can increase recognition rates greatly"; co-occurrence ("near-neighbor") correction fixes errors "by noting that certain words are often seen together." [confirmed via [Wikipedia — OCR](https://en.wikipedia.org/wiki/Optical_character_recognition)]. *Galaxy hit:* a tool SKU `EM-0500-4FL` mis-OCR'd as `EM-O5OO-4FL` fails an exact lookup — the milling lexicon (known SKUs, material grades, G/M-code set) is the principled fix, and the corpus retrieval layer must also be typo-tolerant (foundations §tolerant retrieval).

- **Gotcha: 99% character accuracy can still be 5%+ word-error — and a tool code is only useful if EVERY character is right.** WHY: "a 1% character error rate (99% accuracy) may result in an error rate of 5% or worse if the measurement is based on whether each whole word was recognized with no incorrect letters." [confirmed via [Wikipedia — OCR](https://en.wikipedia.org/wiki/Optical_character_recognition)]. EXPERT AVOIDANCE: measure and gate the mill corpus on *word/field*-level accuracy of the entities that matter (SKU, code, dimension), not on a flattering character-level average. *Galaxy hit:* "99% accurate OCR" on a catalog still mangles ~1-in-20 multi-character tool codes — the corpus must validate codes against the lexicon, not trust the headline number.

## 4. Scan quality — the upstream lever that decides everything downstream

Most extraction failures are really scan-quality failures one stage earlier; the expert fixes them at the image, not in post.

- **Gotcha: below ~300 DPI, OCR degrades and no amount of post-processing recovers it.** WHY: Tesseract "performs optimally at at least 300 dpi," and low-resolution sources benefit from rescaling. [confirmed via [Tesseract — Improve Quality](https://tesseract-ocr.github.io/tessdoc/ImproveQuality.html)]. EXPERT AVOIDANCE: check/upscale source DPI before OCR; reject sub-threshold scans into a re-scan queue rather than ingesting garbage. *Galaxy hit:* old JM Die manual scans are the low-DPI case — measure DPI first. (The exact min-DPI ship gate stays owner-gated.)

- **Gotcha: the default page-segmentation mode treats a table as one block of prose and shreds it.** WHY: Tesseract's default PSM 3 ("fully automatic ... no OSD") "has a problem" with tables; sparse/table layouts need PSM 11 or custom segmentation, single columns PSM 4, uniform blocks PSM 5/6. [confirmed via [Tesseract — Improve Quality](https://tesseract-ocr.github.io/tessdoc/ImproveQuality.html)]. EXPERT AVOIDANCE: pick the PSM per page TYPE (the foundations' classify-then-template step) — sparse PSM for a catalog grid, column PSM for a two-column manual page. *Galaxy hit:* running default PSM over a Mazak alarm table linearizes it into unusable text.

- **Gotcha: scan borders and uneven background lighting corrupt OCR — too little border AND too much border both fail.** WHY: Tesseract docs warn that missing borders cause "problems" (add ~10px padding), oversized borders cause "empty page" errors, "dark scanning borders" get "misrecognized as characters," and Otsu binarization "can be suboptimal, particularly if the page background is of uneven darkness." [confirmed via [Tesseract — Improve Quality](https://tesseract-ocr.github.io/tessdoc/ImproveQuality.html)]. EXPERT AVOIDANCE: crop dark borders, normalize padding, and use an adaptive threshold (Adaptive Otsu / Sauvola) on unevenly-lit manual scans rather than global Otsu. *Galaxy hit:* photocopied vendor manuals have dark gutters and uneven toner — a global threshold turns the gutter into phantom characters in the alarm column.

- **Gotcha: leaving the dictionary on (or off) blindly hurts code-bearing pages.** WHY: Tesseract lets you disable `load_system_dawg`/`load_freq_dawg` for "non-dictionary text (receipts, codes)" and whitelist characters via `tessedit_char_whitelist`. [confirmed via [Tesseract — Improve Quality](https://tesseract-ocr.github.io/tessdoc/ImproveQuality.html)]. EXPERT AVOIDANCE: turn the English dictionary OFF for SKU/code columns (they are not English words) but constrain them to a milling lexicon/whitelist instead; keep it ON for prose manual text. *Galaxy hit:* the system dictionary "corrects" `4FL` toward an English word — wrong for a flute-count code; per-zone dictionary control is the fix.

## 5. Multi-page + resume — the corpus-scale gotchas a single-page demo never shows

The mill corpus is thousands of pages across many documents; the failures that only appear at scale are about reading order and durability.

- **Gotcha: extracted text/page order does NOT necessarily equal visual reading order, and layout coordinates can be wrong on complex pages.** WHY: PDF text is "absolutely positioned" drawing instructions, not logical flow; pypdf's `extraction_mode="layout"` warns that "in complicated PDF documents the coordinates given to the visitor functions may be wrong." [confirmed via [pypdf — Extract text](https://pypdf.readthedocs.io/en/stable/user/extract-text.html)]. EXPERT AVOIDANCE: never assume read order from extraction order on a multi-column manual page; reconstruct order from geometry (and verify, since coordinates themselves can be wrong on complex pages). *Galaxy hit:* a two-column Haas programming-manual page extracted naively interleaves the two columns line-by-line into nonsense.

- **Gotcha: a multi-page document that extracts only page 0, or that re-OCRs everything on a crash, silently loses most of the corpus.** WHY (general, not a single fetched source — flagged as engineering judgment): the per-page positioned-text/whitespace ambiguity above applies independently to *each* page, so a multi-page manual must be iterated page-by-page; processing only the first page drops the rest. EXPERT AVOIDANCE: process every page (cap + log if capped), and stream-append each page's records to a durable store with a processed-page cursor so a kill mid-corpus resumes instead of restarting. *Galaxy hit:* PRISM already burned this exact failure in the OCR closed-loop — page-0-only on 96% multi-page drawings + a non-resumable end-of-run write that lost all progress on a reaper kill (see `## Recent regressions` 2026-06-08, commit 265e8a6e41). This galaxy must inherit the per-page + stream-append + resume-cursor pattern. *(The per-page record schema, page cap, and any throughput number are owner-gated.)*
