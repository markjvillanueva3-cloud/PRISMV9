# Knowledge-Conversion Advanced Techniques

The **world-leader-depth** layer for the knowledge-conversion galaxy: the state-of-the-art STRATEGIES an expert reaches for once past the intro theory ([[knowledge-conversion-foundations]]) and the common practitioner gotchas ([[knowledge-conversion-applied-practice]]). Read both first — neither is repeated here. Foundations defines *what* the IE/KR/ETL pipeline is; applied-practice catalogs *what goes wrong* running one; this entry is *the advanced method that makes the difference at the top of the field* — how a modern extraction system is actually architected and supervised when hand-labeled data is scarce, the schema must be honored, and a wrong fact poisons everything downstream.

Each technique below: the method + WHEN an expert uses it + the trade-off DIRECTION + the confirmed source inline + one line on how THIS galaxy (MIT-OCW transcripts, the engine monolith, tribal tips, the PDF corpus -> wiki/memory/tribal/graph nodes) applies it. Per R12 + SAFETY, only the qualitative *strategy/method/trade-off direction* is promoted — every numeric threshold, model hyperparameter, and any manufacturing constant is owner-gated for golf (see Owner-gate).

## 1. Modern neural extraction backbone — transformers, transfer learning, and finetuned token classification

### Technique 1.1 — Self-attention transformer as the extraction substrate
**Method:** Replace recurrent/CRF feature pipelines with a multi-head self-attention transformer that contextualizes every token against the whole window in parallel. **CONFIRMED** ([Wikipedia, Transformer (deep learning architecture)](https://en.wikipedia.org/wiki/Transformer_(deep_learning_architecture))): a transformer is "a family of artificial neural network architectures based on the multi-head attention mechanism," where each token is "contextualized within the scope of the context window with other (unmasked) tokens via a parallel multi-head attention mechanism," and they have "the advantage of having no recurrent units, therefore requiring less training time than earlier recurrent neural architectures."
**WHEN an expert uses it:** as the default encoder for any non-trivial NER/relation extractor today — when entities depend on long-range context (a part name disambiguated by a clause ten tokens away) that a bag-of-features or short-window model cannot see.
**Trade-off DIRECTION:** richer contextual disambiguation and faster training than recurrent models, paid for in model size and inference cost — heavier compute and a harder-to-inspect model than a rule system. Bias toward the transformer when context matters more than transparency.
**Galaxy applies it:** the encoder under any conversion lane that learns (rather than rule-matches) entities — a tool/material/controller mention whose type depends on surrounding manufacturing context is exactly the long-range case self-attention resolves.

### Technique 1.2 — Pretrain-then-finetune transfer learning (BERT for token classification)
**Method:** Take an encoder pretrained self-supervised on a huge generic corpus, then finetune it on a small task-specific labeled set for the downstream task (NER = token classification). **CONFIRMED** ([Wikipedia, Transformer](https://en.wikipedia.org/wiki/Transformer_(deep_learning_architecture))): "Transformers typically are first pretrained by self-supervised learning on a large generic dataset, followed by supervised fine-tuning on a small task-specific dataset." **CONFIRMED** ([Wikipedia, BERT (language model)](https://en.wikipedia.org/wiki/BERT_(language_model))): BERT is "a deeply bidirectional, unsupervised language representation, pre-trained using only a plain text corpus" via masked language modeling, and "After pre-training, BERT can be fine-tuned with fewer resources on smaller datasets to optimize its performance on specific tasks" — for token classification "the task head is removed and replaced with task-specific modules, then retrained."
**WHEN an expert uses it:** whenever in-domain labeled data is scarce (the normal case) — the pretrained model supplies general language competence so you only need a modest labeled set to specialize, instead of training from scratch.
**Trade-off DIRECTION:** dramatically lowers the labeled-data requirement and lifts accuracy, at the cost of inheriting the pretraining corpus's biases and blind spots (the source of the domain-brittleness gotcha in applied-practice §1.1). Bias toward finetuning a pretrained encoder over training a fresh model — but always measure on in-domain held-out data.
**Galaxy applies it:** the practical answer to "we cannot hand-label thousands of JM-Die sentences" — finetune a pretrained encoder on a small labeled slice of manufacturing text rather than building a manufacturing NER from zero.

## 2. Supervising the extractor without hand-labels — distant/weak supervision, data programming, active learning

### Technique 2.1 — Weak / distant supervision (label at scale from noisy heuristics and a knowledge base)
**Method:** Instead of hand-labeling, generate a large noisy training set from cheap signals — heuristics, domain rules, or an existing knowledge base (distant supervision: if two entities are related in the KB, treat sentences containing both as positive examples). **CONFIRMED** ([Wikipedia, Weak supervision](https://en.wikipedia.org/wiki/Weak_supervision)): weak supervision addresses "limited or imprecise labeled data" by incorporating "noisy labels, heuristics, domain expert rules, or partially labeled datasets," with techniques including "data programming, label modeling, and semi-supervised learning" — motivated because "acquisition of unlabeled data is relatively inexpensive" whereas "the cost associated with the labeling process thus may render large, fully labeled training sets infeasible."
**WHEN an expert uses it:** when labeled data is the bottleneck but you have an existing KB or a set of reliable heuristics — trade a small amount of clean data for a large amount of cheaply, imperfectly labeled data.
**Trade-off DIRECTION:** orders-of-magnitude more training data with near-zero labeling cost, paid in label NOISE — every heuristic mislabels some examples, and a model trained on noisy labels inherits that noise. Bias toward weak supervision when you can model and down-weight the noise (label modeling), away from it when a wrong label silently corrupts a precision-critical KB.
**Galaxy applies it:** PRISM already HAS a knowledge base (the wiki/memory/graph nodes + the typed cross-substrate edges) — that is the distant-supervision signal for labeling new source text automatically, so a conversion lane can be trained on the corpus it is converting instead of waiting on hand-labels.

### Technique 2.2 — Data programming / labeling functions as the supervision interface
**Method:** Encode each weak signal as a labeling function (a small program that votes a label or abstains); a label model then combines the noisy, conflicting votes into probabilistic training labels. **CONFIRMED** ([Wikipedia, Weak supervision](https://en.wikipedia.org/wiki/Weak_supervision)): the named techniques include "data programming, label modeling, and semi-supervised learning," explicitly framing programmable noisy sources plus a model that reconciles them as the weak-supervision toolkit.
**WHEN an expert uses it:** when domain knowledge is easier to express as rules than as per-example labels — a senior machinist can state "a token after `Ø` in a drawing is a diameter" as a labeling function far faster than hand-tagging 10,000 tokens.
**Trade-off DIRECTION:** turns expert knowledge into supervision cheaply and lets you add/revise signals without re-labeling, at the cost of needing a label model to handle disagreement and abstention — naive majority vote over correlated functions over-counts. Bias toward labeling functions for codifiable domain rules.
**Galaxy applies it:** shop-floor and domain heuristics (controller-code patterns, material-name lexicons, dimension-prefix rules) become labeling functions over the corpus — the programmable bridge between tribal knowledge and a trainable extractor.

### Technique 2.3 — Active learning (spend the human label budget where the model is least sure)
**Method:** Let the model pick which unlabeled examples a human should label next, querying the most uncertain/informative points rather than a random sample. **CONFIRMED** ([Wikipedia, Active learning (machine learning)](https://en.wikipedia.org/wiki/Active_learning_(machine_learning))): an active learner "can interactively query a human user ... to label new data points," and because "the learner chooses the examples, the number of examples to learn a concept can often be much lower than the number required in normal supervised learning"; the core uncertainty-sampling strategy is to "label those points for which the current model is least certain as to what the correct output should be."
**WHEN an expert uses it:** when human labeling time is the scarce resource (it always is) and the corpus is large — concentrate the operator's review on the few examples that actually move accuracy.
**Trade-off DIRECTION:** far higher accuracy per labeling hour than random labeling, at the cost of an iterative loop (label -> retrain -> re-query) and a sampling bias risk if uncertainty is mis-estimated. Bias toward active learning whenever a human must be in the loop anyway.
**Galaxy applies it:** when golf reviews converted nodes, the lane should surface the *lowest-confidence* extractions for human confirmation first (pairs with the foundations exact-span F1 yardstick), not a random or first-N sample — maximum quality lift per minute of owner attention.

## 3. Schema-guided extraction — make the target ontology drive the extraction, and force conformance

### Technique 3.1 — Ontology-based information extraction (OBIE: the schema steers what you look for)
**Method:** Drive extraction with the target ontology/schema — identify exactly the concepts, instances, and relations the ontology defines, so output is structured-by-construction rather than structured after the fact. **CONFIRMED** ([Wikipedia, Knowledge extraction](https://en.wikipedia.org/wiki/Knowledge_extraction)): in ontology-based information extraction "the OBIE system uses methods of traditional information extraction to identify concepts, instances and relations of the used ontologies in the text, which will be structured to an ontology after the process"; knowledge extraction's distinguishing criterion is that it requires "reusing formal knowledge through existing identifiers and ontologies, or generating schemas from source data" — going "beyond the creation of structured information."
**WHEN an expert uses it:** when the output must integrate with an existing schema/KB (PRISM's case) — let the known node-kinds and edge-types define the extraction targets instead of extracting freely and reconciling later.
**Trade-off DIRECTION:** output is interoperable and immediately mergeable, at the cost of being blind to anything the ontology does not model (a new concept type falls through). Bias toward ontology-driven extraction for integration, but pair it with drift detection (applied-practice §5.1) so new concepts are surfaced, not dropped.
**Galaxy applies it:** the cross-substrate typed-edge whitelist + node-kind schema (the galaxy's ontology, per foundations §5) should DRIVE extraction — a lane extracts `owned-by-slot`/`documented-by`/`embeds`/`consensus-of` candidates because those are the schema, not arbitrary free-text relations.

### Technique 3.2 — Constrained decoding / schema-constrained structured outputs (guarantee the shape)
**Method:** When an LLM does the extraction, constrain token generation at inference time to a supplied JSON schema/grammar so the output is *guaranteed* to parse and carry every required field. **CONFIRMED** ([OpenAI, Structured Outputs guide](https://developers.openai.com/api/docs/guides/structured-outputs)): Structured Outputs "ensure the model will always generate responses that adhere to your supplied JSON Schema," giving "reliable type-safety" with "no need to validate or retry incorrectly formatted responses"; unlike plain JSON mode it "enforces actual schema adherence" by constraining generation "to only produce outputs matching the defined schema structure, making validation unnecessary on the application side," and it makes refusals "programmatically detectable."
**WHEN an expert uses it:** any time an LLM emits structured extraction that downstream code must parse — constrained decoding eliminates the malformed-JSON / missing-field class of failure at the source rather than with brittle post-hoc repair.
**Trade-off DIRECTION:** removes parse failures and missing-key errors entirely and simplifies prompting, at the cost of locking output to the declared schema (a value the schema cannot express is forced into the nearest legal shape — so the schema must model the unknown/abstain case). Bias toward constrained decoding over free-text-plus-regex for any machine-consumed extraction.
**Galaxy applies it:** an LLM-driven conversion lane emitting nodes/edges should decode against the node-card / edge schema directly — this is the structural complement to the applied-practice §3 lesson (the leading-dot / truncation JSON-repair regressions in PRISM's own OCR pipeline are exactly the class constrained decoding prevents upstream).

### Technique 3.3 — Ontology learning with human-in-the-loop (grow the schema, validated)
**Method:** When the schema itself must expand, semi-automatically derive candidate terms/concepts/relations from text, but gate every machine-proposed addition through expert validation. **CONFIRMED** ([Wikipedia, Ontology learning](https://en.wikipedia.org/wiki/Ontology_learning)): ontology learning is "the automatic or semi-automatic creation of ontologies" extracting "terms and concepts or noun phrases from plain text using linguistic processors such as part-of-speech tagging and phrase chunking"; but quality demands a gate — "The result of both approaches need to be evaluated by an ontologist to ensure accuracy," and "a supervision step, e.g., user evaluation, is added" because automated methods "often produce noisy results."
**WHEN an expert uses it:** when the domain outgrows the frozen vocabulary (applied-practice §5.1 drift) — propose schema extensions from the corpus automatically, but never auto-commit them.
**Trade-off DIRECTION:** keeps the ontology current at a fraction of the manual cost, but only if the validation gate holds — un-gated auto-extension injects noise straight into the schema everything depends on. Bias toward machine-propose + human-approve, never machine-auto-commit, for schema changes.
**Galaxy applies it:** new node-kinds/edge-types proposed from the corpus go to golf/sierra for approval (the schema owners), never silently into the live whitelist — the doctrinal complement to "the ontology is owner-maintained or it drifts."

## 4. Resolving identity — entity linking, coreference, and joint extraction so facts attach to the right node

### Technique 4.1 — Entity linking / disambiguation (attach each mention to ONE canonical node, handle NIL)
**Method:** Beyond recognizing an entity span, link it to a unique identifier in the knowledge base via candidate generation then disambiguation — and decide NIL when no entry exists. **CONFIRMED** ([Wikipedia, Entity linking](https://en.wikipedia.org/wiki/Entity_linking)): entity linking is "the task of assigning a unique identity to entities ... mentioned in text," with subtasks "named-entity recognition," "candidate generation," and "disambiguation"; it must handle the out-of-KB case because "named entities might not have a corresponding entity in the target knowledge base," weighing that "linking to an incorrect but related entity may be more useful to the user than having no result at all."
**WHEN an expert uses it:** whenever an extracted mention must connect to an *existing* node rather than mint a new one — this is the record-linkage decision at extraction time, and the explicit defense against the over-merge gotcha (applied-practice §5.3).
**Trade-off DIRECTION:** correct linking keeps the KB coherent (one node per real entity), but the precision/recall dial cuts both ways — link too eagerly and you fuse distinct entities (over-merge), refuse too readily (NIL) and you fragment one entity into duplicates. Bias toward conservative linking with an explicit NIL/quarantine path so an uncertain mention is reviewed, not force-merged.
**Galaxy applies it:** when a lane extracts "VMC-03" or an engine name, it must LINK to the existing node (not create a near-duplicate) — and route a genuinely new entity to a NIL/quarantine queue for golf, the structured answer to applied-practice §3.2's unknown-code case.

### Technique 4.2 — Coreference resolution (so aliases, pronouns, and abbreviations attach to the same entity)
**Method:** Connect every referring expression — pronouns, aliases, abbreviations — to its referent before extracting facts, so mentions of one entity are not scattered across many. **CONFIRMED** ([Wikipedia, Coreference](https://en.wikipedia.org/wiki/Coreference)): coreference is when "two or more expressions refer to the same person or thing; they have the same referent," and resolving it is essential because "pronouns and other referring expressions must be connected to the right individuals" to "derive the correct interpretation of a text" and build an accurate knowledge base; strategies include "mention-pair," "mention-ranking," and "entity-based algorithms that leverage information from entire coreference chains."
**WHEN an expert uses it:** in multi-sentence sources where one entity is named once then referred to obliquely — without coreference, a relation stated about "it" or an abbreviation is lost or mis-attached.
**Trade-off DIRECTION:** correct coreference recovers facts that would otherwise be missed and prevents one entity splitting into many partial nodes, at the cost of a hard, context-and-world-knowledge-dependent step that, done wrong, mis-merges references. Bias toward resolving coreference before relation extraction in long sources; skip it only for single-mention fragments.
**Galaxy applies it:** an MIT-OCW transcript or a multi-line tribal tip that names a machine once then says "it"/"the same setup"/an abbreviation needs coreference so all its facts attach to ONE node — without it the converted knowledge fragments across pronoun references.

### Technique 4.3 — Joint / end-to-end entity-and-relation extraction (beat the cascade)
**Method:** Extract entity mentions and their relations in one jointly-trained model rather than a strict NER-then-RE cascade, so the two tasks inform each other. **CONFIRMED** ([Wikipedia, Relationship extraction](https://en.wikipedia.org/wiki/Relationship_extraction)): "More recently, end-to-end systems which jointly learn to extract entity mentions and their semantic relations have been proposed with strong potential to obtain high performance."
**WHEN an expert uses it:** when cascade error-propagation is the dominant failure (applied-practice §2.3 — a missed entity is invisible to every later stage) and you have enough joint training signal; the relation evidence can help recover an entity the NER stage alone would miss.
**Trade-off DIRECTION:** removes the hard cascade bottleneck (the relation recall is no longer strictly capped by NER recall) and can raise overall accuracy, at the cost of a more complex model that is harder to train and to debug stage-by-stage. Bias toward joint models when cascade propagation dominates your errors; keep a staged pipeline when you need per-stage observability.
**Galaxy applies it:** the direct counter to applied-practice §2.3's cascade trap — a lane that emits zero edges because the entity stage went blind benefits from joint extraction, where relation evidence can rescue the entity; but keep the staged view for debugging which stage failed.

## 5. Fail-loud reconciliation at load — N-of-M accounting, quarantine, and LLM-extraction guardrails

### Technique 5.1 — Load N of M, drop K loudly (counted reconciliation, never a silent merge)
**Method:** Treat the load phase as an accounting boundary — every source record either lands, is quarantined with a reason, or is rejected with a reason, and the run reports the full N-loaded / K-dropped / M-total ledger. **CONFIRMED** ([Wikipedia, Knowledge extraction](https://en.wikipedia.org/wiki/Knowledge_extraction)): knowledge extraction's defining requirement is that results map to "existing knowledge" via "existing identifiers and ontologies" — i.e. each extracted fact is reconciled against the KB, not blindly appended. **CONFIRMED** ([Wikipedia, Entity linking](https://en.wikipedia.org/wiki/Entity_linking)): the explicit NIL decision (no KB match -> return NIL rather than force a wrong link) is the per-record "this one could not be reconciled, flag it" mechanism that makes the drop visible.
**WHEN an expert uses it:** on every conversion run over a real corpus — the moment a batch of thousands of sources is converted, "it worked" is meaningless without the N/M/K numbers.
**Trade-off DIRECTION:** loud counted reconciliation makes data loss impossible to hide and recoverable (quarantine + audit trail), at the cost of building the reject channel and surfacing numbers that look worse than a silent run that "completed." Bias hard toward the loud ledger — a quiet run that drops 394 of 7,794 is the R12 lie in extraction form.
**Galaxy applies it:** a conversion run MUST report loaded-N / dropped-K / total-M with reasons (the entity-linking NIL path + the OBIE-quarantine path feed the drop reasons) — this is R12 fail-loud in extraction terms, and the lived antidote to PRISM's tribal-brain fail-OPEN clobbers (CLAUDE.md "Recent regressions") where a silent empty-return destroyed the corpus.

### Technique 5.2 — Treat LLM extraction as a high-recall draft to be verified, never as ground truth
**Method:** Use an LLM for the hard, fuzzy extraction (it generalizes to genres a trained model has not seen) but verify every emitted fact against the source/KB, because fluent output is not correct output. **CONFIRMED** ([Wikipedia, Large language model](https://en.wikipedia.org/wiki/Large_language_model)): hallucination is the fundamental failure mode — models "generate syntactically fluent text that appears factually sound, but is internally inconsistent with training data or factually incorrect," and "confidently assert claims of fact which do not seem to be justified by their training data." It also notes "few-shot prompting allows LLMs to be adapted to any task without requiring fine-tuning" and that LLMs have been "evaluated as substitutes for human annotators."
**WHEN an expert uses it:** when no trained extractor covers a source genre and few-shot prompting can reach it fast — the LLM is the flexible high-recall first pass, not the trusted final word.
**Trade-off DIRECTION:** an LLM extractor adapts to any genre with near-zero setup (few-shot) and high recall, at the cost of confidently hallucinated facts that a fluent surface hides. Bias toward LLM-extract-then-verify: pair it with constrained decoding (§3.2) for shape and source-grounded verification for content; never let an unverified LLM fact enter a precision-critical KB.
**Galaxy applies it:** an LLM conversion lane is a fast adapter for a new source type, but every node/edge it emits must be verified against the source span and the existing graph before merge — the same R12 discipline as the OCR-ensemble "1-of-N = hallucination-candidate, >=2-agree = corroborated" rule already lived in this codebase.
