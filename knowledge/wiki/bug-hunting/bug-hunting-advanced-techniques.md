# Bug-Hunting Advanced Techniques

The **world-leader-depth** layer for the bug-hunting galaxy: the advanced testing *strategies* an expert reaches for when example-based unit tests, coverage numbers, and manual review have all gone green and the bug is still hiding. Read [[bug-hunting-foundations]] (theory: oracle problem, coverage criteria, fail-fast, rep invariants, static-analysis undecidability) and [[bug-hunting-applied-practice]] (gotchas: green-no-oracle, flaky-test causes, mock drift, silent catch, off-by-one) FIRST — this entry does not repeat them. The thread here: **stop hand-writing example cases and start generating, measuring, cross-checking, and minimizing.** Each technique below is a WebFetch-confirmed verbatim quote from a free/legal source; the **galaxy application** line maps it to a real PRISM bug-hunting surface.

The expert's mental model: an example-based test asserts one `(input, output)` pair. Every technique below scales that to *many* inputs, or *measures whether the assertions are any good*, or *finds a second source of truth so no hand-written oracle is needed at all*. They attack the oracle problem from four directions.

---

## 1. Generate the inputs — property-based testing and coverage-guided fuzzing

Hand-picked example inputs only test the cases the author thought of. The advanced move is to generate inputs by the thousand and check a *property* (not an exact value), or to let code-coverage feedback evolve inputs toward the unexplored corners.

- **Property-based testing — assert a universal property over many generated inputs, not one expected value.** **CONFIRMED** ([Software testing, Wikipedia](https://en.wikipedia.org/wiki/Software_testing)): property testing is *"a testing technique where, instead of asserting that specific inputs produce specific expected outputs, the practitioner randomly generates many inputs, runs the program on all of them, and asserts the truth of some 'property' that should be true for every pair of input and output"* (*"sometimes known as 'generative testing' or 'QuickCheck testing'"*).
  - **When an expert uses it:** when the *relationship* between input and output is known but the exact value for any given input is not — round-trip (`decode(encode(x)) == x`), idempotence, ordering, conservation. **Trade-off DIRECTION:** higher input diversity and bug-finding power for the cost of a harder-to-write property (you must state an invariant, not a value) and non-deterministic failures that need a captured seed to reproduce. Pair it with shrinking so a failing case is reported minimal, not raw.
  - **Galaxy application:** the galaxy's "real reference-value / algebraic-invariant" test contract IS a property in disguise — the runout-double-count algebraic-invariant test ("the orchestrator factor must equal the engine SINGLE factor, never its square") is a hand-written property that holds for *every* derate magnitude, which is exactly why it catches the co-varying-derate class that fixed-value tests missed.

- **Coverage-guided (gray-box) fuzzing — let basic-block coverage steer input mutation toward new code.** **CONFIRMED** ([Fuzzing, Wikipedia](https://en.wikipedia.org/wiki/Fuzzing)): *"A gray-box fuzzer leverages instrumentation rather than program analysis to glean information about the program. For instance, AFL and libFuzzer utilize lightweight instrumentation to trace basic block transitions exercised by an input"* — the feedback that makes *"gray-box fuzzers extremely efficient vulnerability detection tools."*
  - **When an expert uses it:** when a parser/decoder/state-machine takes structured untrusted input and the failure modes are unknown — fuzzing finds the inputs no human enumerated. **Trade-off DIRECTION:** the coverage feedback dramatically raises the rate of reaching deep code paths versus blind random input, at the cost of needing instrumentation and a meaningful crash/assertion oracle (a fuzzer that can only see "did it crash" is blind to silent wrong answers — see section 4).
  - **Galaxy application:** any galaxy intake surface that parses untrusted structured text (the OCR JSON-repair path, NC-program parsing, STEP unit detection, the tribal-index loader) is a fuzz target. The V8 512-MiB string-cap regression was precisely a boundary a coverage-guided fuzzer with a size-growth corpus would have driven into long before it shipped.

- **Mutation-based vs generation/grammar-based fuzzing — pick the generator to match how structured the input is.** **CONFIRMED** ([Fuzzing, Wikipedia](https://en.wikipedia.org/wiki/Fuzzing)): *"A mutation-based fuzzer leverages an existing corpus of seed inputs ... It generates inputs by modifying the provided seeds"* whereas *"A generation-based fuzzer generates inputs from scratch ... a smart generation-based fuzzer takes the input model that was provided by the user to generate new inputs."* And: *"A smart (model-based, grammar-based, or protocol-based) fuzzer leverages the input model to generate a greater proportion of valid inputs"* while a dumb fuzzer *"does not require the input model and can thus be employed to fuzz a wider variety of programs."*
  - **When an expert uses it:** mutation-based when you have a real seed corpus and want fast coverage with low setup; grammar-based when the input must be valid enough to pass an early syntax gate (G-code, STEP, JSON) or the dumb fuzzer wastes all its budget being rejected at the door. **Trade-off DIRECTION:** grammar/generation buys deeper penetration past validation for the cost of authoring the input model; mutation buys near-zero setup for shallower reach into format-strict code.
  - **Galaxy application:** the galaxy's strict-format consumers (NC dialects, STEP AP242, controller posts) are grammar-fuzz targets — a dumb byte-flipper is rejected at the first parse check, so a grammar-aware generator that emits *almost-valid* programs is the one that reaches the deep semantic bugs.

## 2. Measure whether the tests are any good — mutation testing as oracle-quality auditing

Coverage tells you a line *ran*. Mutation testing tells you whether your assertions would have *noticed* if that line were wrong. This is the advanced answer to "the suite is green but a bug shipped from a covered file" — it grades the oracle, not the code.

- **Mutation testing scores the test suite by how many injected faults it kills.** **CONFIRMED** ([Mutation testing, Wikipedia](https://en.wikipedia.org/wiki/Mutation_testing)): *"The value of a test suite is measured by the percentage of mutants that it kills,"* and crucially the workflow is corrective — *"The test suite can then be improved by adding new tests designed to kill additional mutants."* Mutants are made with *"well-defined mutation operators that either mimic typical programming errors (such as using the wrong operator or variable name)."*
  - **When an expert uses it:** after coverage is already high and you need to know whether the green is real — a surviving mutant on a covered line is *proof* the assertions are too weak (the applied-practice entry's surviving-mutant gotcha, here turned into a deliberate campaign). **Trade-off DIRECTION:** mutation score is a far stronger quality signal than coverage, bought at high compute cost — *"For mutation testing to function at scale, a large number of mutants are usually introduced, leading to the compilation and execution of an extremely large number of copies of the program ... This problem of the expense ... had reduced its practical use."* Run it targeted (changed files / critical engines), not fleet-wide every commit.
  - **Galaxy application:** the right place to apply mutation testing is on a freshly-fixed regression's test — flip the fix's operator and confirm the new test goes red. If a galaxy regression test survives mutation of the exact line it was written to protect, the test encodes coverage but not intent (R9), and the bug can silently return.

- **Beware the equivalent-mutant trap — a surviving mutant is not always a test gap.** **CONFIRMED** ([Mutation testing, Wikipedia](https://en.wikipedia.org/wiki/Mutation_testing)): *"Equivalent mutants detection is one of the biggest obstacles to practical usage of mutation testing"* — *"there are cases where it is not possible to find a test case that could kill this mutant. The resulting program is behaviorally equivalent to the original one."*
  - **When an expert uses it:** every time you triage a survivor — before adding a test, confirm the mutant actually changes observable behavior; an equivalent mutant (e.g. `<=` vs `<` on a value that can never hit the boundary) is unkillable by construction and chasing it wastes effort. **Trade-off DIRECTION:** treating the raw mutation score as a hard gate manufactures busywork (and tempts weakening the score floor); read it as a ranked worklist of *suspicious* survivors a human triages.
  - **Galaxy application:** this is why the galaxy gates the *mutation-testing strategy* but NOT a numeric mutation-score floor (see Owner-gate) — an honest survivor triage is human judgment, exactly the R5 "model/expert only for judgment calls" line. A blanket "kill 100% of mutants" rule would force tests against equivalent mutants that cannot fail.

## 3. Find a second source of truth — differential and metamorphic testing (no hand-written oracle)

These two solve the oracle problem from foundations directly: when you cannot say what the correct output *is*, you can still say two outputs must *agree* (differential) or must satisfy a *relationship* (metamorphic). Both turn "I don't know the answer" into a checkable test.

- **Differential testing — two implementations of the same spec are each other's oracle.** **CONFIRMED** ([Differential testing, Wikipedia](https://en.wikipedia.org/wiki/Differential_testing)): it detects bugs *"by providing the same input to a series of similar applications (or to different implementations of the same application), and observing differences in their execution"* — it *"finds semantic bugs by using different implementations of the same functionality as cross-referencing oracles ... any discrepancy between the program behaviors on the same input is marked as a potential bug."* It is *"well-suited to find semantic or logic bugs that do not exhibit explicit erroneous behaviors like crashes or assertion failures."*
  - **When an expert uses it:** when an independent reference implementation exists — a refactor vs the old code, two vendors computing the same physics, a fast path vs a slow reference path. **Trade-off DIRECTION:** zero oracle-authoring cost (the other implementation is the oracle) for the cost of needing a genuinely independent second implementation AND a triage step — a discrepancy flags *a* bug, not *which side* is wrong.
  - **Galaxy application:** this is the galaxy's most under-used lever. PRISM already has natural differential pairs: the SFC engine's output vs the 41K-tool HSMAdvisor/G-Wizard *vendor-parity* corpus (a discrepancy is a candidate bug in either PRISM or the assumed reference), the `build:fast` esbuild path vs the full `tsc` path, the CIMCO sim bridge's parity check, and any "engine vs the workaround a consumer used to apply." Differential testing finds the silent-wrong-answer class (section 2 of applied-practice) that crash-only oracles miss.

- **Metamorphic testing — a violated relation between executions reveals a fault with no expected value.** **CONFIRMED** ([Metamorphic testing, Wikipedia](https://en.wikipedia.org/wiki/Metamorphic_testing)): MT is *"a property-based software testing technique, which can be an effective approach for addressing the test oracle problem."* Metamorphic relations (MRs) are *"necessary properties of the intended functionality of the software, and must involve multiple executions of the software"* — the classic example *"a metamorphic relation for sine functions is 'sin(π − x) = sin x'"*, and *"Any inconsistency (after taking rounding errors into consideration) indicates a failure of the program, caused by a fault in the implementation."* The subset example: filtered search results must be a subset of unfiltered.
  - **When an expert uses it:** when the function is too complex to have a closed-form expected output but obeys known transformations — scale-invariance, monotonicity, subset, permutation-invariance, units-conversion round-trip. **Trade-off DIRECTION:** sidesteps the oracle problem entirely for the cost of identifying valid MRs (a domain-knowledge task) and tolerating numeric/rounding slack in the comparison.
  - **Galaxy application:** physics-adjacent surfaces are rich in MRs the galaxy can assert *without* touching an owner-gated constant: converting a part inch->mm->inch must round-trip (the units-guard `scaleAnomaly` is a metamorphic check); doubling stock depth must not *decrease* predicted cut time (monotonicity); the same toolpath through two unit systems must produce geometrically congruent output. Each MR states the SHAPE of the relationship, never the number — the exact pattern this galaxy is allowed to promote.

## 4. Minimize and make-observable — delta debugging and sanitizer oracles

Once a generator or fuzzer *finds* a failing input, two advanced steps make it actionable: shrink it to the minimal reproducer, and add an oracle that turns silent corruption into a loud crash so the fuzzer can even see it.

- **Delta debugging — automatically minimize a failing input (or change-set) to its 1-minimal core.** **CONFIRMED** ([Delta debugging, Wikipedia](https://en.wikipedia.org/wiki/Delta_debugging)): the algorithm *"isolates failure causes automatically by systematically narrowing down failure-inducing circumstances until a minimal set remains."* It applies *"to isolate failure-inducing program input (e.g. an HTML page that makes a Web browser fail), failure-inducing user interaction ... or failure-inducing changes to the program code,"* trimming *"until a 1-minimal program is found."*
  - **When an expert uses it:** the moment a fuzzer or a user hands you a giant failing input, or a regression appeared somewhere in a large diff — let ddmin shrink the 10,000-line input to the 3 lines that matter, or bisect the change-set to the one edit that flipped pass->fail. **Trade-off DIRECTION:** turns a multi-hour manual reduction into automation, for the cost of needing a fast, deterministic pass/fail test to run repeatedly (a flaky oracle breaks the search).
  - **Galaxy application:** this is the *mechanized* form of the foundations "reproduce -> simplify -> root-cause" discipline. A failing NC program, a malformed STEP file, or a print PDF that breaks OCR should be delta-minimized to the smallest reproducing fragment before a fix is attempted; on the change side, a `git bisect` over the fleet's commit stream is delta debugging applied to "which commit introduced this regression" — the galaxy's exact daily question.

- **Sanitizers as fuzzing oracles — convert silent corruption into a visible crash.** **CONFIRMED** ([Fuzzing, Wikipedia](https://en.wikipedia.org/wiki/Fuzzing)): *"To make a fuzzer more sensitive to failures other than crashes, sanitizers can be used to inject assertions that crash the program when a failure is detected."*
  - **When an expert uses it:** always, when fuzzing — a fuzzer's only signal is "did the program crash," so a bug that silently returns a wrong answer is invisible unless an injected assertion makes it crash. **Trade-off DIRECTION:** sanitizers/assertions massively widen the class of detectable faults (the silent-wrong-answer + corruption classes) for a runtime-overhead cost that is acceptable in a fuzzing/test build and is why such checks are disabled in production (the assertion semantics from foundations section 4).
  - **Galaxy application:** this generalizes beyond C/C++ — the galaxy's own runtime guards ARE injected oracles: the tribal-index clobber-guard (refuse a >50% shrink over a populated corpus), the units-guard throw on unknown/mismatched units, and a `checkRep()` on a state store all turn an otherwise-silent corruption into a loud, fuzzer-visible failure. The doctrine "add the assertion so the next fuzz/test run can SEE the bug" is the sanitizer principle in JavaScript.

## 5. Measure the bug-finder itself — labeled-corpus tool evaluation (the meta-loop)

The most advanced move in the field is to test the *bug-hunters*, not just the code: run your detectors against a corpus of programs whose bugs are already known, and measure recall/precision. A scanner you have never benchmarked against known bugs has an unknown false-negative rate.

- **NIST SARD — a labeled corpus of programs with documented weaknesses for measuring tool effectiveness.** **CONFIRMED** ([NIST SAMATE SARD](https://samate.nist.gov/SARD/)): the Software Assurance Reference Dataset is *"a growing collection of test programs with documented weaknesses"* — *"more than 450,000 test cases"* across C/C++/Java/PHP/C# *"covering more than 150 Common Weakness Enumeration classes (CWE),"* a *"repository of test cases and test suites helping tool developers improve their solutions and end users find suitable tools."*
  - **When an expert uses it:** when adopting or building a static/dynamic bug detector — measure its catch rate against a corpus with ground-truth labels before trusting it, then re-measure after every change to the detector so a "fix" that quietly lowers recall is caught. **Trade-off DIRECTION:** a labeled-corpus benchmark replaces "the scanner feels thorough" with a measured recall/precision number, for the cost of curating (or borrowing) a labeled corpus — but the corpus need not be SARD; your own shipped-regression history IS a free labeled corpus.
  - **Galaxy application:** this is the galaxy's compounding meta-asset. Every entry in CLAUDE.md `## Recent regressions` is a known bug with a known fix and a known commit — i.e. a SARD-shaped labeled case. A regression-replay harness that re-runs each historical bug against the *current* guards measures whether the galaxy's grep/AST scans + Stop hooks would catch each known failure today. A guard that no longer catches a regression it was built for is a silent recall drop — the exact failure-of-the-bug-finder this technique is designed to surface.

## Owner-gate (NOT promoted)

- **No mutation-score floor** (e.g. "require >=N% mutants killed"). Section 2 confirms mutation score is a quality *signal* and the equivalent-mutant problem makes 100% unreachable by construction; any pass/fail mutation threshold is an owner decision, not a sourced fact.
- **No coverage-percentage gate** — unchanged from the sibling entries; coverage is necessary-not-sufficient and a 100% target is explicitly cautioned against. No numeric coverage doctrine is introduced here.
- **No fuzzing budget / corpus-size / time numbers** (e.g. "fuzz for N hours", "seed corpus of N inputs", "N basic blocks before plateau"). These are tuning knobs owned by golf and measured locally, not establishable from external sources.
- **No PRISM-local benchmark numbers** — the galaxy's own detector recall/precision against its regression corpus, fuzz crash rates, or differential-discrepancy counts are measured-locally facts owned by golf.
- **PHYSICS / CUTTING CONSTANTS — owner-gated to golf, live ONLY in `mcp-server/src/physics/constants.ts`.** This entry deliberately states cutting/physics relationships by SHAPE only and NEVER by number. Specifically NOT promoted: any SFM/RPM/IPR/chip-load/feed/depth-of-cut value, any kc1.1 specific-cutting-force or Taylor C/n tool-life constant, any coolant-pressure psi, any engagement-angle->temperature numeric coefficient. Where a metamorphic relation touches physics (section 3: "doubling stock depth must not decrease predicted cut time"; "higher engagement angle raises cutting temperature, so reduce feed"), only the monotonic DIRECTION is asserted — the magnitude is golf's, in constants.ts.
- **SAFETY_THRESHOLDS:** n/a as new claims — bug-hunting is a meta/quality galaxy carrying no physics safety thresholds of its own. The PRISM regression examples cited (tribal-index clobber/>50%-shrink guard, V8 string cap, runout double-count, units-guard, HSMAdvisor/G-Wizard parity corpus, CIMCO bridge parity) are real shipped fixes referenced as illustrations of a technique, not new numeric claims — verify each against its commit before relying on the detail.
