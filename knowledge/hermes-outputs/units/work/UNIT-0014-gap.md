## Real gaps

1. **No thermal safety-gate action** — chatter has `CHATTER_STABILITY_GATE_ACTIONS` wired end-to-end in `safetyDispatcher.ts:902-920` with the classic "compute → evaluate gate → verdict" pattern; thermal has nothing equivalent even though `ThermalGrowthCompensationEngine` already returns an `is_safe` boolean and a 50µm threshold (:149) — the physics output exists but is never routed through `prism_safety`. Acceptance criterion "Wired to prism_calc and safety" is only half-true (thermal is prism_calc-only).
2. **No per-machine-type thermal model** — `ChatterStabilityLobeEngine` binds to the JM Die fleet via `machineRegistry.getFRF(machine_id)` (:90-97, `MachineRegistry.ts:1527`), giving registry/registry_default/manual/estimated confidence tiers. `ThermalGrowthCompensationEngine` and `ThermalExpansionEngine.machineToolThermalError` take generic bearing-type/axis-length defaults (`ThermalExpansionEngine.ts:93-95`: `Xlen=500, Ylen=400, Zlen=300` hardcoded fallbacks) with **no `machine_id` parameter and no `MachineRegistry` import** (grep-confirmed: zero matches for `machine_id|MachineRegistry` in both `ThermalModelingEngine.ts` and `ThermalGrowthCompensationEngine.ts`). The unit's own criterion says "thermal model **per machine type**" — this does not exist for JM Die's 5 VMCs (`VMC-01` Hurco VM30i .. `VMC-05` Roku-Roku HC658-II, `jm-die-profile.ts:248-252`).
3. **No `<4%` error validation against JM Die data — anywhere.** `mcp-server/src/__tests__/thermal-growth-compensation-engine.test.ts:1-51` (read in full) contains only 6 tests, all sign/monotonicity invariants ("spindle growth > 0", "higher RPM increases growth" etc.) — zero JM Die reference values, zero `<4%` or any percentage-error assertion, zero measured-vs-predicted comparison. Grep for `JM Die|jm-die|JM DIE` inside that test file: 0 matches. Broader grep across `mcp-server/src` for JM-Die + chatter/thermal/valid co-occurrence returned 19 files, none of which is a thermal/chatter accuracy validation report (they are academy courseware, business/knowledge engines, and unrelated data files). **This criterion is unmet, full stop.**
4. **Inlined CTE table** (`ThermalGrowthCompensationEngine.ts:64-81`) duplicates canonical `CTE_LINEAR_BY_ISO` (`constants.ts:87`) — should be refactored to import, not a blocking gap for the unit but a real rails violation worth fixing alongside any extension.

## Verdict
**extend**

## Recommended action
Do NOT build new `ThermalManagementEngine`/`VibrationDampingEngine` engines from scratch — the deliverables the unit names already exist, more comprehensively, as `ThermalGrowthCompensationEngine`+`ThermalExpansionEngine` (thermal, 20+ dispatcher actions) and `ChatterStabilityLobeEngine`+`prism_vibration_physics` (vibration/chatter, safety-gated, 20 actions). The genuine remaining work is three extensions, in logical order:
1. **Bind thermal to `MachineRegistry`** — add optional `machine_id` to `ThermalGrowthCompensationEngine.calculate()`/`ThermalExpansionEngine.machineToolThermalError()`, mirroring `ChatterStabilityLobeEngine`'s `getFRF(machine_id)` pattern (:90-97), so the 5 JM Die VMCs each get their own bearing/axis/spindle geometry instead of generic defaults.
2. **Add a `thermal_growth_gate` safety action** to `safetyDispatcher.ts`, mirroring `CHATTER_STABILITY_GATE_ACTIONS` (:902-920), routing `ThermalGrowthCompensationEngine`'s existing `is_safe`/`total_z_error_um` output through `prism_safety` with an explicit threshold param (currently hardcoded 50µm at engine.ts:149 — externalize with citation).
3. **Build the JM Die validation harness** (the one genuine net-new-code artifact) — pull real production thermal-drift measurements (or, if none are instrumented, state that gap explicitly per R12 rather than fabricate a `<4%` figure) and real chatter/RPM outcomes for the 5 VMCs, and assert `<4%` error as a real reference-value test, not a monotonicity stub.
4. Fix the inlined-CTE rail violation (item 4 above) opportunistically while touching the file.
