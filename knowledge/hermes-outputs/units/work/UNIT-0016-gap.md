## Real gaps

1. **No cross-spindle thermal-coupling model exists.** `ThermalGrowthCompensationEngine` is single-spindle-chain only; `CrossToolCouplingEngine` is dynamic/force-only (no thermal). For a twin-/multi-spindle machine, heat from one spindle's bearings/motor measurably affects the thermal growth of an adjacent spindle (main→sub proximity on a Multus-class machine) — no engine models that cross-term. This is the ONE genuine net-new-code gap.
2. **Wiring target mismatch.** UNIT-0016 acceptance criterion demands wiring "to prism_calc and cam dispatchers." The two real engines that cover force/timing sync are wired to `prism_multi` (`MultiSpindleAutomaticEngine`) and `prism_session` (`CrossToolCouplingEngine`) — neither is `prism_calc` nor a `cam_*` dispatcher. This is a wire-only gap, not a code gap.
3. **The "≥3 multi-spindle machines at JM Die" acceptance criterion is unsatisfiable against real shop data as literally written.** JM Die's fleet (verified above) has exactly ONE multi-spindle-capable machine (Okuma Multus B250II, LTH-07). Drum-type 6/8-spindle automatics (the machine class `MultiSpindleAutomaticEngine` actually models) do not exist at JM Die at all. Either the criterion needs re-scoping to "≥1 real machine + synthetic validation for the other 2" or the unit's "real production data validation" clause cannot be met honestly for 3 machines.
4. **Dead duplicate wiring** at `turningDispatcher.ts:3861-3865` (`multi_spindle_automatic_plan` calling nonexistent `.plan/.run/.analyze`) should be removed or fixed to call the real methods — hygiene, not a criterion blocker.

## Verdict
**extend**

## Recommended action
Do NOT build a new "MultiSpindleSyncEngine" from scratch — three real, tested, physics-grounded engines already cover timing sync (`MultiSpindleAutomaticEngine` station/index timing, `SubSpindleHandoffVerifierEngine` phase-sync + grip-force balance) and force+timing coupling (`CrossToolCouplingEngine`). The comprehensive-route extension is:
(a) add a `computeThermalCoupling()` method to `CrossToolCouplingEngine` (or a small companion module) that couples per-spindle bearing heat generation (reuse `ThermalGrowthCompensationEngine`'s CTE/friction/tau constants — do not re-derive) across N active spindles/tools sharing a common structural loop, closing gap #1;
(b) add `cross_tool_coupling_*` and `spindle_*` action aliases on `prism_calc` (or a `cam_multi_spindle_*` sub-action set) that delegate to the existing engines, closing gap #2 without duplicating logic;
(c) remove or fix the dead `multi_spindle_automatic_plan` case in `turningDispatcher.ts:3861-3865`;
(d) validate against the ONE real JM Die multi-spindle machine (Multus B250II, LTH-07) via `OkumaB250LatheMasterPostEngine.generateSubSpindleTransfer` (the engine `PPOkumaSubSpindleSyncEngine.ts:21-22` itself names as the verified path), and flag the "≥3 machines" criterion to the unit owner as unsatisfiable with real JM data rather than silently faking 2 more.

## ROI
**3/10** — the timing/force-balance physics the unit asks for is ~80% already built, tested, and wired (just to the wrong dispatchers); the one true net-new piece (cross-spindle thermal coupling) is real but has thin practical payoff because JM Die owns exactly one qualifying machine. Effort here is mostly wiring-alias + a bounded thermal extension, not a new engine — high risk of duplicate-build if treated as green-field.
