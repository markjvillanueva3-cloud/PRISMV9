## Real gaps

1. **No engine or test cites REAL JM Die probe/CMM data.** Grepped `MetrologyUncertaintyEngine.ts` for "JM Die"/"Docustrata" — **no matches**. Read `ProbeRoutineEngine.ts`, `ProbeRecordEngine.ts`, `ProbeDriftEngine.ts` headers — all are generic schema/formula engines (literature-referenced: GUM, ISO 15530-3, AIAG MSA) with **synthetic/parameterized** test fixtures, not JM Die shop-floor measurement records. Confirmed JM Die's actual `.nc` programs DO contain live probe cycles (`grep -l "PROBE\|G65\|G31" "JM DIE/CNC LATHE/CSM/PRISM_UPGRADED/Okuma_LB-3000EX-BigBore/*.nc"` → 4 matching files) — so the shop-floor practice exists, but no PRISM engine ingests or validates against it. **This is acceptance criterion #1 ("real JM Die probe data") and criterion #4 ("Validation on production metrology data") — both open.**
2. **No `MetrologyEngine` / `PredictiveQualityModel` by those exact names** — the unit's "Deliverables" line names assets that don't exist verbatim, but their function is already split across `MetrologyUncertaintyEngine` + `MetrologyBudgetEngine` + `CMMPathPlanningEngine` (metrology) and `QualityPredictionEngine` + `ScrapRiskPricingEngine` + `SPCFeedbackLoopEngine` (predictive quality/scrap). Building new engines under the literal names would be R8/dedup-guard-violating duplication.
3. **Two near-duplicate `cmm_plan`-shaped surfaces** (`qualityDispatcher.ts:128-141` heuristic vs `CMMPathPlanningEngine` physics-grade planner on `prism_calc`) are not cross-referenced — an operator calling `prism_quality:cmm_plan` gets a coarse time estimate, unaware `prism_calc:cmm_sampling_strategy`/`cmm_datum_alignment`/`cmm_feature_uncertainty` exist for the rigorous version. Minor discoverability gap, not a build gap.

## Recommended action
Do **not** build new `MetrologyEngine`/`PredictiveQualityModel` engines — in-machine probing (7 engines/5 dispatchers), post-process CMM metrology (`CMMImportEngine`/`CMMHistoryEngine`/`MetrologyUncertaintyEngine`/`MetrologyBudgetEngine`/`CMMPathPlanningEngine`), the closed CMM→cutting-parameter feedback loop (`SPCFeedbackLoopEngine`), and predictive scrap/quality (`QualityPredictionEngine`/`ScrapRiskPricingEngine`/`ScrapRootCauseEngine`) are all real, dispatcher-wired, and test-covered. The ONE genuine net-new-code gap is a **JM-Die-real-data validation harness**: pull actual dimensional/inspection records from `JM DIE/SETUPS/` and `Docustrata/JMD Orders Closed` (search `manifest.json` + `.index/` per quality galaxy §8 — never re-OCR), feed them through `CMMImportEngine` → `MetrologyUncertaintyEngine.cmmUncertainty()` → `QualityPredictionEngine`/`ScrapRiskPricingEngine`, and produce a reconciliation report (predicted vs. actual Cpk/Ra/scrap-rate) that closes acceptance criteria #1 and #4. This is a **validation + wiring** task (feed real data through the existing pipeline, publish delta/uncertainty), not a new-physics build — per this soul's refuse-list (`skipping-vendor-parity-validation`, `publishing-a-speed-feed-without-uncertainty`) any published reconciliation must carry its own confidence interval, not a bare number. Route the reconciliation report artifact to `SPCFeedbackLoopEngine` so validated JM Die deltas actually adjust future predictions (closes the loop for real, not just on paper). Secondary: cross-link `qualityDispatcher.ts:cmm_plan` to `CMMPathPlanningEngine` in a doc-comment so the two depths are discoverable, not competing.
