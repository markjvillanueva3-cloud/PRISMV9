KEY FINDINGS
================================================================================

CRITICAL (Fix before next phase):
─────────────────────────────────────────────────────────────────────────────

C1: DUPLICATION ACROSS ROADMAPS
   Pattern: 10 knowledge sources cited in 3+ roadmaps
   Examples:
   - MachiningPlaybookEngine: appears in LATHE, MT, MILL, GRIND, LASER, WATERJET, TKP = 7x
   - FormulaRegistry + constants: 5-6 appearances each
   - CollisionEngine + SafetyVetoEngine: 7 appearances each

   Impact: HIGH
   - If MachiningPlaybookEngine rules change → must manually update 7 roadmaps
   - Each TKP promotion requires multi-roadmap sync burden
   - Risk of inconsistency: LATHE cites version X, MILL cites version Y of same engine

   Score: 6.2/10 (moderate risk, but trending critical if TKP promotions accelerate)


C2: SELF-UPDATE MECHANISM MISSING (CRITICAL)
   Pattern: TKP roadmap (Wave TK-0..TK-7) produces new tribal knowledge
           but ZERO roadmaps subscribe to TKP promotions

   Facts:
   - TKP Wave TK-1: "Creates canonical tribal knowledge spine"
   - TKP Wave TK-2: "Routes knowledge to speed/feed, tool selection, program pipelines"
   - Machine roadmaps: Have NO HOOK to detect these promotions

   Example failure chain:
   1. TKP promotes: "Haas lathe M100 spindle dwell = 2.5s (not 1s)" [confidence: cross-shop]
   2. KnowledgePromotionEngine marks it live
   3. TurningPrintToProgramEngine (LATHE consumer) auto-uses it correctly
   4. BUT: LATHE-MS5 session still lists generic MASTER KNOWLEDGE SOURCES
   5. Next LATHE-MS5 author reads roadmap, sees no mention of new tip
   6. Implements spindle dwell manually (wrong) instead of letting engine provide it

   Impact: CRITICAL
   - Tribal knowledge reaches engines but not roadmaps
   - Sessions inherit static/frozen knowledge snapshots, not living knowledge
   - SVI stalls because knowledge island gaps don't auto-heal

   Score: 8.5/10 (this is THE missing mechanism holding back SVI)


C3: SOURCE HIERARCHY INVERTED
   Pattern: ALL 7 roadmaps list FORMULAS before CONSTANTS

   Examples (wrong order):
   - LATHE lines 86-88: "FORMULAS: ... CONSTANTS: src/physics/constants.ts"
   - MILL lines 62-64: "Kienzle (milling: Fc = ...) ... CONSTANTS: canonical"
   - WATERJET lines 23-29: "Zeng-Kim model (depth_of_cut = ...) ... CONSTANTS: Garnet mesh sizes"

   Correct order should be:
   1. CONSTANTS (src/physics/constants.ts — always first)
   2. FORMULAS (reference canonical constants, no inline values)
   3. ENGINES
   4. TRIBAL_TIPS
   5. REFERENCE

   Impact: MAJOR
   - Documentation normalizes wrong precedent (formulas are primary, constants secondary lookup)
   - Risk of formula drift: sessions copy-paste inline values instead of importing canonical source
   - Future maintenance: new authors see FORMULAS first and might replicate pattern

   Score: 7.1/10


C4: MACHININGPLAYBOOKENGINE CITED AS MONOLITH
   Pattern: All 7 roadmaps reference "MachiningPlaybookEngine — 296 rules"
            but provide NO per-machine-type breakdown of which rules apply

   Examples:
   - LATHE: "MachiningPlaybookEngine 296 rules (turning anti-patterns)"
   - MILL: "MachiningPlaybookEngine — pocket rules, anti-patterns"
   - GRIND: "MachiningPlaybookEngine — wheel guard must clear workpiece"

   Problem: Author reading LATHE-MS0 inherits ALL 296 rules implicitly
            Sessions don't know which 50 are for turning, which 120 are milling, etc.

   Impact: MAJOR
   - Cognitive overload: sessions must mentally filter inapplicable rules
   - Risk of cross-contamination: milling pocket rules applied to lathe turret planning
   - Maintenance: if rule #75 (milling-specific) changes, LATHE author doesn't know they're not affected

   Score: 6.8/10 (compound effect with C3 — hierarchy inversion makes this worse)

MAJOR FINDINGS

M1: TRIBAL TIPS SCATTERED VIA WILDCARDS
   Pattern: Roadmaps reference "src/data/*-cam-tips.ts" instead of explicit list

   Implication: There are ~18 CAM systems with tribal tip files, but roadmaps
                don't list them explicitly or track when new ones are added

   Risk: If new CAM system added (e.g., Fusion360), roadmaps won't auto-discover it
         Sessions must manually scan src/data/ directory to find new tips

   Score: 5.4/10


M2: EXTERNAL REFERENCE SOURCES NOT VERSIONED
   Pattern: "Haas Lathe Workbook (22 programs)" cited, but no validation date
            "Sandvik Turning catalog" cited, but no link to live version
            "WJTA recommended practices" cited, but no cached copy

   Risk: If external source updates (e.g., Haas Workbook → 28 programs), roadmaps
         don't reflect change; sessions use outdated parameters

   Score: 5.1/10


M3: PER-SESSION KNOWLEDGE LACKS EXPLICIT EXCLUSIONS
   Pattern: Sessions declare per-milestone sources (GOOD)
            but don't declare which GLOBAL sources DON'T apply (BAD)

   Example: LATHE-MS0 Collision Avoidance includes collision + accessibility engines
            but implicitly inherits FormulaRegistry, ThermalWearCouplingEngine, etc.
            No statement: "EXCLUDED SOURCES: FormulaRegistry (speed/feed not needed for collision)"

   Risk: Future editor might assume all inherited sources are active and required

   Score: 4.2/10


M4: PLAYBOOK RULES NOT INDEXED BY MACHINE TYPE
   Pattern: MachiningPlaybookEngine has 296 rules, but no breakdown like:
            LATHE rules: 1-50 (turning anti-patterns)
            MILL rules: 51-120 (pocket/hole-making)
            GRIND rules: 121-180 (wheel/dresser collision)

   Risk: Sessions inherit bloat; lose precision on what's applicable

   Score: 5.5/10
