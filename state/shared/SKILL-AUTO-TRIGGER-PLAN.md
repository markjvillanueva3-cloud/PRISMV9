## P0 — Brief + acceptance criteria

### The ask
- Each of 13 new dev-velocity skills auto-invokes (or auto-suggests with one-click invoke) when its triggers match, without the operator having to type `/skill-name`.
- Obsidian/wiki layer provides the trigger metadata (keywords, file patterns, tool events).
- CLAUDE.md has a single source-of-truth section listing every trigger.
- Where appropriate, skills get bundled into existing PreToolUse / PostToolUse / UserPromptSubmit hook bundles instead of new top-level entries (preserves the HS-day-0 manifest-count reduction).

### Acceptance gates
1. Every new skill has a wiki entry (`knowledge/wiki/architecture/skills/project/<name>.md`) with `triggers` frontmatter declaring its activation rules.
2. One orchestrator hook (`skill-auto-trigger.mjs`) reads the wiki triggers index and emits a suggestion via `additionalContext` when matches occur.
3. CLAUDE.md has an auto-generated `## SKILL AUTO-TRIGGER REGISTRY` section, regenerated by the same script that builds the wiki triggers index.
4. Per-file scrutiny gate passed on every new file before next file generated.
5. Live integration test: for each of 13 skills, demonstrate a real prompt (or tool event) that triggers it.
6. No regression on the existing 30+ UserPromptSubmit injection hooks.

## P3 — Auto-trigger architecture

Single orchestrator hook (`skill-auto-trigger.mjs`) handles all three event types:

```
┌─────────────────────────────────────────────────────────────────┐
│  knowledge/wiki/architecture/_skill-triggers.jsonl              │
│  (auto-regenerated by regen-wiki-from-viz.mjs)                  │
│                                                                 │
│  Each line: { skill, event, matcher, score, action }            │
│    skill: "/wire-unwired"                                       │
│    event: "UserPromptSubmit" | "PreToolUse" | "PostToolUse"     │
│    matcher: { type: "keyword"|"regex"|"file-pattern"|"tool",    │
│               value: "..." }                                    │
│    score: 0..1 confidence                                       │
│    action: "suggest" | "inject-context" | "block" | "auto-run"  │
└─────────────────────────────────────────────────────────────────┘
                            │
                            ▼
┌─────────────────────────────────────────────────────────────────┐
│  skill-auto-trigger.mjs (NEW hook)                              │
│                                                                 │
│  Reads _skill-triggers.jsonl on first fire (cached by mtime).   │
│  On UserPromptSubmit/PreToolUse/PostToolUse:                    │
│    1. Match current input against triggers for that event       │
│    2. Score + dedupe (don't double-fire if /wire-unwired and    │
│       /wiring-batch both match — pick higher-score)             │
│    3. Emit suggestion via additionalContext (suggest action)    │
│       OR block (block action — reserved for safety skills)      │
│       OR queue auto-run (auto-run action — reserved for         │
│       deterministic skills like /index-lock-coordinator)        │
└─────────────────────────────────────────────────────────────────┘
                            │
                            ▼
                    Operator decides
```

Three action modes:
1. **`suggest`** (default for new skills): inject `💡 Consider /skill-name — <one-line why>` into context
2. **`inject-context`**: like wiki-precheck-inject — surface the skill's wiki entry as context
3. **`block`** (reserved, opt-in via wiki frontmatter): hard-deny the tool call until skill runs (e.g. `/encoding-guard` on .ps1 edits)
4. **`auto-run`** (reserved, deterministic only): hook itself invokes the skill (e.g. `/index-lock-coordinator` clears stale lock + retries silently)

## P7 — Risks + mitigations

1. **Trigger storm** — 13 skills × 3 events × ~50 keywords each = ~2000 trigger lines. Could slow UserPromptSubmit. **Mitigation:** precompile trigger index at regen time; do exact-keyword lookup with bloom filter before regex; cap to top-3 matches per event.
2. **Duplicate suggestions** — `/wire-unwired` + `/wiring-batch` (its inner helper) could both fire. **Mitigation:** `extends:` frontmatter — if A extends B, A's match suppresses B's.
3. **CLAUDE.md auto-regen race** — multiple chats writing to CLAUDE.md. **Mitigation:** post-commit hook only (single-firer), splice between markers (idempotent), file-lock during write.
4. **Cron skills running on multiple machines** — `/skill-recall-tune` weekly cron could run on MarkV AND DESKTOP-N7MI1VB simultaneously. **Mitigation:** machine-scope env-var; only the "primary" machine (configurable) runs cron skills.
5. **Wiki regen lag** — if a new skill ships but wiki regen hasn't run, the trigger registry is stale. **Mitigation:** new skill's commit triggers a wiki regen via post-commit hook; if regen is queued, skill triggers fall back to a "pending wiki regen" notice.
6. **Operator overwhelm** — 13 new suggestion sources mean every prompt could surface 5+ skills. **Mitigation:** score-based dedup; only show top-1 unless `--all-skills` env flag; sane confidence floor.

## P11 — /loop integration (iterative invocation discipline)

**Doctrine:** "this will be a good way to eliminate bugs and errors" — skills that can detect a problem AND verify a fix should also support being re-invoked until stable.

Each looped skill defines a `loop_contract:` frontmatter block:

```yaml
loop_contract:
  max_iterations: 5            # safety cap to prevent runaway loops
  initial_delay: 0             # seconds before first invocation
  inter_iteration_delay: 0     # seconds between (0 = immediate; use for IO-heavy)
  break_when: "all-pass"       # all-pass | no-change | converged | max-reached
  state_signal: "scrutiny_ledger" # which state file changes signal progress
  rollback_on_runaway: true    # if max-iterations hit without progress, revert
```

| Skill | Loop mode use | break_when | max_iterations | rollback risk |
|-------|---------------|------------|----------------|---------------|
| `/scrutiny-batch` | re-scrutinize after fixes until all files PASS | all-pass | 3 | none (advisory) |
| `/wire-unwired` | wire next-highest-priority unwired engine, loop until N done | converged (N wired) | 10 | per-engine; each wiring commits separately |
| `/scrutiny-replay` | replay after auto-fix-stop-fix cycle | no-change (ledger stable) | 5 | none (advisory) |
| `/envelope-drift-fix` | fix one envelope, recheck drift, fix next | no-change (drift = 0) | 4 | per-envelope; revert by git revert |
| `/encoding-guard` | restore BOM, re-check, fix more files | converged (no .ps1 BOM-less) | 5 | per-file; restore is byte-additive |
| `/big-blob-hunt` | scan, identify top, propose fix, re-scan | converged (no blobs > threshold) | 5 | analysis only; no mutations |
| `/index-lock-coordinator` | clear lock, retry git op, repeat on contention | all-pass (lock released + commit OK) | 5 | already retry-tolerant |
| `/peer-file-isolation` | poll peer claims, re-check on staleness | no-change (claims stable) | 3 | read-only |
| `/staged-sanity` | re-stage after un-staging out-of-lane files | all-pass (only in-lane staged) | 3 | per-file unstage |
| `/dispatcher-coverage` | not loop-suitable (informational) | n/a | n/a | n/a |
| `/route-context` | not loop-suitable (hook modification) | n/a | n/a | n/a |
| `/quick-archive` | not loop-suitable (one-shot mv) | n/a | n/a | n/a |
| `/skill-recall-tune` | weekly cron (not /loop) | n/a | n/a | n/a |

**Invocation pattern:** `/loop <interval> /scrutiny-batch` for paced, OR `/loop /scrutiny-batch` (dynamic-pace mode, model decides cadence). The skill itself returns a JSON status with `done: bool` so the loop runtime knows when to stop.
