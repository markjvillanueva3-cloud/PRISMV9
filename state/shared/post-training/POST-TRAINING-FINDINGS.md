## ✅ What the closed loop proved works
- **End-to-end wiring:** `--generate` POSTs `prism_cam {action, params:{operations, config, machine}}` to `:3100`,

## 🔴 FINDING 1 — `master_post_unified_agi_generate` (hurco-v11-agi) emits an EMPTY program
- **Repro:** `node scripts/post-training-harness.mjs --post hurco-v11-agi --generate`
- **Symptom:** dispatcher returns `success:true` + `data:{ gcode:"", line_count:0, segments_processed:0 }` for all 3 jobs.
- **Deviation message:** `empty program: line_count=0, segments_processed=0 (post returned success:true with no NC)`.
- **Read:** the AGI/unified path accepts the loose operation shape but produces ZERO output — it never
  processes the operations into segments. `segments_processed:0` is the smoking gun (input never reached the toolpath builder).
- **Owner:** PEER (AGI/unified master-post). **Severity:** P1 — `success:true` with no NC is a silent-failure class (R12 violation in the engine).

## 🔴 FINDING 2 — `master_post_hurco_v11` (hurco-v11-standalone) crashes in PhysicsSidecarBuilder on a schema-valid payload
- **Repro:** `node scripts/post-training-harness.mjs --post hurco-v11-standalone --generate`  (after corpus schema-enrichment, below)
- **Symptom:** `post rejected: PhysicsSidecarBuilder.canonicalize: unsupported type undefined`.
- **Root cause (read-only trace):** `PhysicsSidecarBuilderEngine._stringify` (L86-106) handles null/bool/string/number/array/object
  but throws on `undefined`. The standalone post builds a `sealable` payload that contains an `undefined` value
  (an optional field — e.g. `config.safe_z_mm` / `tool_description` / `radial_depth_mm` — assigned explicitly rather than omitted)
  and passes it to `canonicalize`. A schema-valid payload must not crash the provenance sidecar.
- **Two clean fixes (owner's choice):** (a) the sealable builder OMITS undefined keys before canonicalize, OR
  (b) `_stringify` treats `undefined` like an absent key. (b) changes content-hash semantics (undefined vs null vs absent) —
  prefer (a) in the post engine. **Do NOT** map undefined→null in canonicalize without auditing every seal consumer.
- **Owner:** PEER (HurcoV11 standalone master-post + possibly shared PhysicsSidecarBuilderEngine). **Severity:** P1 — blocks ALL standalone generation unless every optional field is supplied.

## 🟡 FINDING 3 — corpus job schema was incomplete (FIXED this unit, on the harness side)
- The `master_post_hurco_v11` zod schema (`camActionSchemas.ts` L113-139) requires per-op: `operation_type, tool_number,
  tool_diameter_mm, tool_flutes, material_iso (P/M/K/N/S/H), spindle_rpm, feed_mm_min, axial_depth_mm, coordinates[{x,y,z,type}]`.

- **Fixed:** jobs enriched to the full schema + a `config{units:metric, work_offset:54, program_number}` per job;
  `generateNc` now forwards `params.config`. This advanced standalone from schema-reject → FINDING 2 (deeper, engine-side).

## 🔴 FINDING 4 — EventBus 500-subscription leak saturates the server in ~a dozen calls — THE critical blocker to "fully testing the fleet"
- **Root cause (located):** `mcp-server/src/engines/EventBus.ts:657` — `subscribe()` throws `Max subscriptions reached: 500` when `this.subscriptions.size >= EVENT_CONSTANTS.MAX_SUBSCRIPTIONS (500)`. There is NO eviction and NO per-request teardown — something subscribes to the EventBus singleton on each `/mcp` request (almost certainly the fresh-McpServer-per-request wiring from the `1297b0a8f5` "Already connected to a transport" fix) and never unsubscribes. After ~12 generate calls the pool is full and EVERY subsequent action returns JSON-RPC `-32000`.
- **Symptom:** restart clears it (pool empties), then it re-saturates within a few posts. Hit 4× this session — blocks training across more than ~1-2 posts per restart.
- **Impact:** directly defeats the operator goal "finally start fully testing all fleet machines" — sustained 15-machine × 3-job training (45 calls) is impossible without it.
- **Why I did NOT patch EventBus.ts from the echo slot:** any cap-raise/eviction risks SILENTLY DROPPING a real listener (a never-fired durable subscription looks identical to a leaked per-request one without the subscriber trace) — worse than the current blocker, which has a clean workaround. The correct fix is in the per-request subscription lifecycle (unsubscribe on request-end, or reuse one durable subscription), which is MCP-core / golf's lane (`1297b0a8f5`). **Routed to MCP-infra owner via chat bus.**
- **Harness mitigation (shipped):** `generateNc` now classifies this distinctly — `SERVER SATURATED — EventBus 500-cap leak (FINDING 4); restart :3100` — instead of a generic `HTTP 500`, so the training loop names the real blocker and the operator knows to restart.
- **Workaround:** restart via `node mcp-server/.claude/helpers/mcp-server-daemon.mjs restart`; run ≤1 post per restart until the leak is fixed. The detached daemon survives the chat session.
- **Owner:** PEER (MCP core per-request subscription lifecycle + `EventBus.ts`). **Severity:** P0 for the training program. Related: `reference_mcp_server_3100_crash_fix_2026_05_22`, regression `1297b0a8f5`.
- **Validated despite saturation:** `jobsFor()` correctly routed the lathe turning-jobs to `master_post_okuma_b250`, and the lathe-op payload reached the dispatcher — the 500 is the pool cap, not a b250/corpus defect.
