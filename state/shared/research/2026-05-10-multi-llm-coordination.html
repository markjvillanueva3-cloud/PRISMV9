#Multi-LLM Coordination Research Card

#TL;DR (read first, decide later)

  1. Default to single-model. Anthropic's own data: agents use 4x tokens vs chat, multi-agent uses 15x. Only escalate when the task is parallelisable, breadth-first, and high-value.
  2. Five canonical workflow patterns (Anthropic): prompt-chaining, routing, parallelisation, orchestrator-workers, evaluator-optimizer. Everything else is a composition of these.
  3. Routing beats ensembling for cost. FrugalGPT-style cascade (qwen → kimi → claude) hits 98% cost reduction at GPT-4 parity when the cascade is calibrated.
  4. Mixture-of-Agents (MoA) wins on accuracy. Together AI's 3-layer MoA hit 65.1% AlpacaEval LC, beating GPT-4o (57.5%) using only OSS models. Cost: ~2x GPT-4 Turbo.
  5. Voting beats debate. ICLR 2025 controlled study: simple majority voting accounts for most observed gains in multi-agent debate. Debate adds latency without proportional accuracy.
  6. PRISM is already partway there. AISystemRouterEngine (8 backends, 9 task classes) is a routing pattern. scrutiny-3way.mjs is a 3-of-3 voting consensus. octopus-provider-probe is a fan-out health check. The gap: K2.6 cloud arm + cascade calibration + MoA layering.

Rule of thumb (Anthropic): start with the simplest topology and add one rung only when the prior tier demonstrably falls short. Most production systems succeed with a single LLM call plus retrieval — adding orchestration is a response to measured failure, not a default.

Cost ladder (orders of magnitude):

  • Single LLM call: 1x (baseline)
  • Routing (classifier + specialist): 1.0-1.2x (classifier overhead)
  • Pipeline (3 stages): 3x (linear)
  • Ensemble (3 parallel): 3-4x (parallel + aggregator)
  • Orchestrator-worker (lead + 5 subagents): 10-15x (Anthropic measured)
  • MoA (3 layers x 6 models): 18-20x (Together AI measured ~2x GPT-4 Turbo cost)

#§3 Consensus Mechanisms

MechanismHow it worksFailure mode
Majority votingk-of-n agree → acceptTreats semantically-equivalent answers as different (surface-form blindness); ignores high-confidence minority
Weighted votingEach model's vote scaled by historical accuracyBootstrap problem — need historical data; weights drift
Critique-revise (actor-critic)Generator produces; critic flags issues; generator revisesGenerator can ignore critic; loop without termination criterion
Multi-agent debate (MAD)All agents see all responses, revise N roundsMajority pressure suppresses minority correction (<5% for weak agents); cost scales linearly with rounds; ICLR 2025: MAD ≈ majority vote in most tasks
Judge-and-juryN proposers + 1 separate judge LLMJudge bias (favors verbose answers, preferred phrasing); single-judge brittleness
Self-consistencySame model run k times with temperature; voteDoesn't fix systematic errors; only reduces variance
Constitutional AI / self-critiqueModel critiques itself against a written constitutionSelf-favoritism bias; depends on constitution quality

PRISM's scrutiny-3way is a strict 3-of-3 jury (Codex + Gemini + Opus must all PASS). This is conservative — a 2-of-3 majority would close more sessions but admits more bad commits. The 3-of-3 strictness was adopted 2026-05-05 to fix the "single-reviewer drift" failure mode where Opus alone rubber-stamped its own work. Tradeoff: 3-of-3 has a known stall mode after 3 block attempts (auto-pass with warning) — which is itself an escape-hatch for the case where the gate is genuinely too strict.

Best practice (per ICLR 2025 controlled study): require explicit agree/disagree statements with logical justification. Weight revision by argument validity rated by an external judge. Don't trust raw majority unless you've calibrated for the surface-form-blindness failure mode (e.g. radial consensus score, semantic clustering before vote).

#§4 Two-Pass Safety Pattern (generator → critic)

The pattern: cheap LLM generates; expensive LLM verdicts PASS|REVISE|FAIL on the output. If REVISE, return to generator with critique. If FAIL, escalate to human or stronger model.

Cost-efficiency math (typical):

  • Generator (qwen2.5-coder:7b local): ~free, ~50ms TTFT, 10ms/tok
  • Critic (claude-sonnet): ~$3/Mtok input + $15/Mtok output, ~800ms TTFT
  • Average task: 500 input tok generator → 200 output tok → critic reads (500 prompt + 200 generation = 700 tok) → 50 tok PASS verdict
  • Cost per task: ~$0.003 (critic only); generator is free
  • Compare single-shot Opus: 500 input + 200 output @ $15/$75 = $0.022 per task
  • Savings: ~7x at parity, assuming critic accept rate >85%

Where it fails:

  1. Critic agreement bias — critic is from same family/training as generator → systematically misses certain bug classes. Mitigation: cross-vendor (qwen → claude, or codex → gemini).
  2. Critic underspecification — vague PASS/FAIL rubric → critic hedges. Mitigation: structured verdict schema ({verdict: PASS|REVISE|FAIL, reasons: [...], confidence: 0-1}).
  3. Loop instability — generator and critic ping-pong without converging. Mitigation: max-rounds cap (3) + escalate to single stronger model on cap.
  4. Cost runaway on REVISE — REVISE rate >40% means generator is too cheap; cascade to mid-tier (qwen → kimi).
  5. Speculative-decoding analog gone wrong — if critic acceptance rate <50%, you've added cost without removing the expensive generation. Track acceptance rate per task class; auto-disable cascade where acceptance <60%.

Speculative decoding is the inference-layer analog of this pattern: a small "draft model" predicts N tokens, the large model verifies in one pass, accepted tokens cost ~1 instead of N. 2-3x speedup at provable identical output. Same principle (cheap propose, expensive verify) at a different scale.

PRISM application: The hyperMILL safety chain (/hypermill-safety-audit) is already an instance — fast geometric checks gate expensive physics simulation. Generalising: build a prism_ai:two_pass_validate action that wraps any engine with {generator: ollama-qwen, critic: claude-sonnet, schema: PassReviseFailSchema}.

#§5 Cost Optimization — qwen → kimi → claude Cascade

The cascade ladder (per FrugalGPT 2023, refined 2024-2026):

Tier 0: prism_calc / prism_safety       → deterministic engine call (free)
Tier 1: ollama-qwen2.5-coder:7b         → ~free, ~50ms first-token, ~200 tok/sec
        ↓ confidence < threshold or task-class miss
Tier 2: kimi-k2.6 (cloud)               → $0.95/M in + $4/M out, 256k ctx, 80% SWE-Bench
        ↓ confidence < threshold or safety-critical
Tier 3: claude-sonnet                   → $3/M in + $15/M out, 1M ctx, broad
        ↓ ambiguous / requires deep reasoning
Tier 4: claude-opus                     → $15/M in + $75/M out, 1M ctx, deepest

Hit-rate measurement (FrugalGPT methodology):

  1. Log every (input, model, output, downstream-success) tuple to routing-decisions.jsonl (PRISM already does this in AISystemRouterEngine.appendLedger).
  2. Compute per-tier accept rate = % of tasks where tier-N output passed downstream validation without escalation.
  3. Calibrate confidence threshold per task class so that escalation only fires when accept-rate-conditional-on-current-confidence drops below target accuracy floor.
  4. Target distribution (production-realistic): 60-70% Tier 0-1 (free/cheap), 20-25% Tier 2 (kimi), 5-10% Tier 3 (sonnet), 1-2% Tier 4 (opus).

Reference numbers from public reports:

  • FrugalGPT achieves 98% cost reduction at GPT-4 parity on QA benchmarks.
  • LeanLM (production guide): 50-90% inference cost eliminated via routing + caching + distillation.
  • PRISM's current ollama-offload-stats: 38% offload rate (15 offloaded / 24 total events; the wider sample of "fired" hooks shows higher engagement). Below the 30% healthy floor would trigger investigation; 38% means cascade is calibrated but not aggressive yet. Target after K2 cloud arm wired: 80%+ at Tier 0-2.

Pitfall: measuring "savings" via tokens-not-spent is a vanity metric. Measure (a) downstream task success rate vs always-Opus baseline and (b) cost per successful task end-to-end. A cascade that saves 80% on average but doubles failure rate is a regression.

#§7 Octopus / Ensemble Patterns — When Ensemble Beats Single Best

The MoA finding (Together AI, ICLR 2025 spotlight): 3 layers of 6 OSS models hit 65.1% AlpacaEval LC, beating GPT-4o (57.5%) at ~2x GPT-4-Turbo cost. The "collaborativeness" insight: LLMs produce better outputs when they can see other models' outputs, even when the other models are weaker individually.

Layer recipe (MoA standard):

  • Layer 1 (proposers): 4-6 diverse models generate independent responses to the input. Diversity > raw quality here.
  • Layer 2 (refiners): same model set, each receives Layer-1 outputs as context, produces refined response.
  • Layer 3 (aggregator): single strong model (often the most capable) synthesises Layer-2 outputs into final answer.

For PRISM's stack, a 3-layer Octopus would be:

  • Layer 1 proposers: qwen2.5-coder:7b + qwen2.5-coder:14b + codellama + Codex + Gemini (5 diverse OSS/cloud)
  • Layer 2 refiners: same 5, with Layer-1 outputs as auxiliary context
  • Layer 3 aggregator: claude-opus (highest synthesis ability + tool use)

When ensemble beats single-best:

  • High-stakes single answer (e.g. final spec, contract clause, irreversible commit)
  • Diverse expertise needed (e.g. cross-domain synthesis: physics + business + UX)
  • Adversarial validation matters (catch jailbreak, factual error, hallucination)
  • Latency budget allows 3-5s instead of <1s

When ensemble multiplies cost without value:

  • Routine tasks (80% of dev work): single Sonnet wins
  • Highly subjective tasks (poetry, brand voice): no convergence
  • Tasks where any of N models can do it: cascade wins instead
  • Tasks bounded by tool I/O (e.g. read 50 files): bottleneck is I/O, not LLM
  • Real-time agents (e.g. autocomplete): latency budget gone

PRISM's octopus-provider-probe.mjs is the readiness check for ensemble mode — verifies Codex + Gemini + Ollama all reachable, then surfaces banner. Currently prism_ai:consensus is the consumer action (per banner text). The octopus pattern aligns with MoA layer-1; PRISM has the fan-out plumbing but does not yet do layer-2 refinement (the auxiliary-context pass that gives MoA its accuracy edge).

Production resilience pattern (from Cloudflare AI Code Review, Maxim, Portkey 2025):

  1. Retries with jitter for transient errors only (429, 5xx, network)
  2. No retries for 400-class (auth, malformed, context overflow)
  3. Circuit breaker per provider (open after 5 failures in 60s, half-open probe every 30s)
  4. Fallback chain ranked by cost/quality (cheap first if cost-sensitive; reverse if quality-sensitive)
  5. Idempotency keys on every call (so retries don't double-charge or double-write)
  6. Full request/response logging for replay debugging
  7. Per-provider quotas (don't let one provider blow the budget)

Common patterns across production:

  1. RAG/context-injection is more important than model choice in 60-70% of tasks (Cody, Cursor evidence)
  2. Hook architectures (PRISM's, Claude Code's) are the de facto coordination mechanism inside a single agent
  3. Multi-vendor ensemble is rare in production; cascade and routing are common; orchestrator-worker is for high-value research only
  4. Consensus voting on diffs / generated code is increasingly standard (Cloudflare, PRISM scrutiny-3way, Sourcegraph Code Review)
  5. Idempotency keys + request-replay logs are non-negotiable above 1000 req/day

#Appendix: Decision Tree (when to use what)

Q: Single-shot or multi-shot?
├─ Single-shot if: routine task, low-stakes, latency-critical, <30k tokens
│  └─ Pick model by §6 strength table (route via AISystemRouterEngine)
└─ Multi-shot if: high-stakes OR safety-critical OR breadth-first OR ambiguous
   │
   ├─ Q: Sequential refine or parallel?
   │  ├─ Sequential (pipeline) if: stages are dependent (translate → polish)
   │  ├─ Parallel (orchestrator-worker) if: subtasks independent (research N angles)
   │  └─ Both (MoA) if: high-value single answer + cost budget allows 5-20x
   │
   ├─ Q: Need consensus on the output?
   │  ├─ Yes + cost-sensitive: cascade (qwen → kimi → claude)
   │  ├─ Yes + accuracy-critical: 3-of-3 jury (scrutiny-3way pattern)
   │  ├─ Yes + tolerant of debate: MAD with explicit agree/disagree (caution: ICLR 2025 says voting often beats debate)
   │  └─ No: single specialist + critic pass
   │
   └─ Q: Token budget?
      ├─ <1k tokens / task: cascade Tier 0-1, no ensemble
      ├─ 1k-10k: cascade with critic on uncertain cases
      ├─ 10k-100k: ensemble or orchestrator-worker
      └─ >100k context: kimi (256k) | claude (1M) | gemini (2M) only
