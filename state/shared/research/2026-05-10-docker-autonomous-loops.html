#Docker Utilization for AI Dev + Autonomous Looping Development Systems

Research card synthesizing 2026 industry patterns for containerized AI development environments and autonomous LLM agent loops, cross-referenced against PRISM's existing infrastructure (6 concurrent chats, file-claim coordination, Ollama offload, /loop + /schedule slash commands, consensus-queue).

The headline finding is that PRISM has independently arrived at most of the canonical patterns published in 2026 — Boris's /loop separation of "iteration" from "schedule," shared-state file-lock coordination over append-only logs, MCP+Ollama colocation in Docker — but is missing two specific ergonomics that the broader ecosystem has standardized: (1) mcpmon-style hot-reload proxy for MCP iteration without restarting clients, and (2) explicit per-iteration verification gates with budget-cap escalation paths (Reflexion's Evaluator + Self-Reflection arms wired to a hard termination policy). Both are 1-2 unit additions, not architectural rewrites.

#§1. Docker Compose Patterns for AI Dev

Service topology that has converged across 2026 references:

Key compose primitives (from Last9, freeCodeCamp 2026 guides):

  • condition: service_healthy on depends_on — eliminates the 30s sleep-and-pray startup race; the API container literally waits until pg_isready returns 0.
  • restart: unless-stopped is the production default; restart: always fights manual docker stop during debugging.
  • Pin image tags (ollama/ollama:0.5.7, never :latest) — silent model-format shifts are the #1 production-break vector cited.
  • One named volume per stateful service (pgdata, qdrant-storage, ollama-models); bind mounts only for source-code hot-reload.
  • Internal-only network for inter-service traffic, with only the gateway (api, ui) port-published. Ollama on a public port without auth is the most-cited footgun — Ollama has zero built-in auth.

Volume mounting for shared agent state (the PRISM use case):

volumes:
  - ./state/shared:/app/state/shared          # agent claims, chat bus
  - ./mcp-server/data/state:/app/data/state   # registries
  - ./knowledge/wiki:/app/knowledge/wiki:ro   # wiki is read-mostly

The :ro on read-mostly knowledge bases prevents accidental writes from misbehaving agents from corrupting shared memory.

PRISM cross-ref: DOCKER_RUNTIME_STATE.json already enumerates the postgres/prism-server/prometheus/ollama/qdrant set — the gap relative to the canonical 2026 stack is cAdvisor + redis-exporter + postgres-exporter for first-class metrics. Without these, Prometheus is scraping mcp-server's app metrics but not the container-level CPU/RSS/I-O signals needed to catch a runaway agent loop.

#§2. Ollama in Docker (GPU Passthrough, Multi-Model, Warm-up)

GPU passthrough (verified 85 tok/sec on Llama 3.2 8B = within 3% of bare-metal):

ollama:
  image: ollama/ollama:0.5.7
  deploy:
    resources:
      reservations:
        devices:
          - driver: nvidia
            count: all
            capabilities: [gpu]
  environment:
    - OLLAMA_HOST=0.0.0.0
    - OLLAMA_NUM_PARALLEL=4
    - OLLAMA_MAX_LOADED_MODELS=3
    - OLLAMA_KEEP_ALIVE=24h
  volumes:
    - ollama-models:/root/.ollama
  ports:
    - "127.0.0.1:11434:11434"   # bind-loopback only — no auth!
  healthcheck:
    test: ["CMD", "ollama", "list"]
    interval: 30s
    timeout: 10s
    retries: 3

Memory budget math: Required RAM ≈ OLLAMA_NUM_PARALLEL × OLLAMA_CONTEXT_LENGTH × model_param_bytes. With qwen2.5-coder:7b at Q4 (~4.5GB) and NUM_PARALLEL=4, expect ~18GB VRAM with 8K context. The PRISM-active model set (qwen2.5-coder:7b + a fallback embed model) fits in 24GB.

Multi-model serving — warm vs. lazy:

  • OLLAMA_MAX_LOADED_MODELS=3 keeps top-3 in VRAM; rest paged out on first request (~5-15s cold-start penalty).
  • OLLAMA_KEEP_ALIVE=-1 pins a model permanently in RAM (use for the always-hot router model).
  • OLLAMA_KEEP_ALIVE=24h is a sane default for "warm if used today."
  • Preload trick: curl localhost:11434/api/generate -d '{"model":"qwen2.5-coder:7b","keep_alive":-1}' at boot warms the cache before first user request — eliminates the ~3s cold start that shows up as a "first-request feels broken" complaint.

WSL2 gotcha: GPU passthrough requires sudo nvidia-ctk runtime configure --runtime=docker && sudo systemctl restart docker inside the WSL2 distro. Skipping this gives the silent "loaded on CPU only, 8x slower" failure mode.

Multi-GPU note: If a single GPU holds the model, single-GPU is more efficient (no cross-GPU tensor traffic). OLLAMA_SCHED_SPREAD is an experimental knob — not a default.

PRISM cross-ref: ollama-docker-launcher.mjs is the auto-start orchestrator; the PRISM_LOCAL_COMPUTE_AUTOSTART pattern matches the canonical preload-on-boot approach. The ollama-offload-stats.json (38% offload rate, 104/274 events as of audit 2026-05-09) is the right telemetry shape — this is exactly the metric that 2026 guides recommend tracking. The advisory threshold of 30% is consistent with industry norms.

PRISM's MCP server runs native because it needs deep filesystem access to H:/prism/JM DIE/, state/shared/, etc. Dockerizing would require -v H:/prism:/workspace and path remapping, which breaks Windows-native path strings inlined throughout the codebase.

Hot-reload pattern (from 2026 mcpmon docs):

mcpmon is a transparent stdio proxy between the MCP client and server — when server code changes, it restarts the server while keeping the client connected. This is the missing-link tool for MCP iteration: without it, every code change requires restarting Claude Desktop/Code, which loses conversation state.

# Replaces direct invocation
mcpmon node mcp-server/dist/index.js

Production Dockerfile pattern (Docker Hub mcp namespace, 300+ verified servers):

  • Multi-stage build: node:20-alpine AS builder → node:20-alpine AS runner.
  • Run as non-root (USER node).
  • Health check via HEALTHCHECK CMD wget -qO- http://localhost:3000/health || exit 1 for HTTP transport.
  • Stdio transport requires nothing — Docker just pipes stdin/stdout.

PRISM cross-ref: PRISM's MCP server is native — correct call given the filesystem-coupling. The opportunity is to add mcpmon for the dev loop (the 7-second npm run build:fast rebuild is fast, but the client-restart cycle currently kills the conversation context). Estimate: 1 unit to wire mcpmon as the dev-mode launcher, gated behind PRISM_MCP_HOT_RELOAD=1.

#§4. Autonomous Loop Architectures

Minimal loop (Oracle, 2026 canonical):

goal → plan → execute → reflect → terminate?
                ↑___________|        |
                            (loop)   N
                                     └→ output

Termination conditions (must enumerate ALL — silent loops are the #1 cost overrun):

  1. Success — verifier returns PASS.
  2. Max-iterations — hard ceiling (Reflexion paper uses 10).
  3. Budget-exceeded — token cost cap, wall-clock cap, or external API call cap.
  4. Low-progress — if last 3 iterations show <ε improvement on the eval metric, abort.
  5. Stop-condition signal — external (user interrupt, kill-switch file).
  6. Repeated-failure — same error 3x → escalate to human.

Reflexion (Shinn et al. 2023 — NeurIPS):

Three components, each is just a different prompt template against the same LLM:

  • Actor — generates the trajectory (the attempt).
  • Evaluator — scores the trajectory (PASS/FAIL + scalar).
  • Self-Reflection — converts feedback into linguistic memory ("last time I forgot to handle the empty list case").

The episodic memory buffer is the load-bearing innovation: it persists across iterations and is concatenated into the next Actor prompt. Performance on HumanEval: 91% pass@1 vs. 80% for vanilla GPT-4 — the lift comes entirely from "remember what you got wrong last time."

ReAct (Yao et al. 2022) — orthogonal pattern:

ReAct interleaves Thought → Action → Observation within a single trajectory. Reflexion happens between trajectories. They compose: ReAct as the Actor, Reflexion as the meta-loop.

AutoGPT vs BabyAGI:

  • AutoGPT — multi-step goal automation with tools and persistent memory. Production-shaped.
  • BabyAGI — three-prompt minimal loop: execute, create-followup, prioritize. Same LLM behind all three. ~150 lines of Python. Best for understanding the pattern.

Verification gates per iteration (from agent governance literature):

Every iteration MUST pass through gates before the next iteration begins:

  1. Tests — npm test on touched files (PRISM has stop_on_failing_tests hook — same idea, different layer).
  2. Lint/build — tsc --noEmit && npm run build:fast.
  3. Safety — domain-specific (PRISM: physics constants imported, no inline kc1.1, dispatcher wired).
  4. Cost cap — accumulated token spend <budget.
  5. Diff-size guard — if iteration introduces >N lines without justification, escalate.
  6. Confidence threshold — if Evaluator confidence <θ, route to human.

Failure recovery:

Failure TypeResponse
Test failureAppend to Reflexion buffer, retry
Lint failureSame — usually self-fixes in next iteration
Safety violationHARD STOP — write incident, escalate to human
Budget capSoft halt — emit partial output, notify
Repeated identical errorEscalate (the loop is stuck)
Unknown exceptionRollback the iteration's writes (transactional)

PRISM cross-ref: PRISM has the gates (25+ HARD BLOCK Stop hooks, scrutinize-before-stop, stop_on_failing_tests, etc.) but they fire at session boundaries, not per-iteration boundaries inside a /loop run. The 2026 pattern is to fire verification per-iteration so an autonomous loop can self-correct mid-run instead of building 6 broken iterations and failing the Stop gate. Estimate: 1 unit to add loop-iteration-gate.mjs that runs tsc --noEmit + vitest run --changed + stop_on_unwired_assets between each /loop iteration.

#§5. Cron + LLM Agents (Recurring Workflows)

Boris's /loop separation (the canonical 2026 pattern):

The Ralph Wiggum pattern conflated two concerns. /loop cleanly separates them:

  • Iteration toward completion — many attempts at the same task with backpressure until convergence (Reflexion-style).
  • Recurring execution — fire the same prompt on a cron schedule (cron-style).

PRISM has both: /loop (Boris) for in-session iteration, /schedule for cron-style. This is the 2026 convergent design.

OpenClaw cron pattern (most production-shaped public reference):

  • Cron expression syntax (0 9 * * 1-5 = weekday 9am).
  • Per-job session isolation — scheduled runs don't pollute the main conversation.
  • Retry with backoff if the LLM has a bad day.
  • Delivery to Slack/Telegram on completion.
  • Failure escalation policy — N consecutive failures → page operator.

Autobot cron pattern (Crystal-based, 2MB binary):

The cron service injects messages into the same message bus the agent uses for user input. The agent doesn't know if a request came from cron or from a human — the entire pipeline is reused. This is the right shape: cron is just another input source, not a special code path.

State that survives between cron runs:

StateWhereSurvives Cron Run
Conversation transcriptper-run, ephemeralN
Agent decisions/findingsshared file (e.g. state/shared/)Y
Episodic memory (Reflexion)vector store (qdrant)Y
Lock claimsfile (WORK_CLAIMS.json)Y
Telemetry countersappend-only JSONLY
Last-seen-timestampper-job state fileY

Three trigger types (the canonical taxonomy):

  1. Time-based — cron expression. Use for: daily summaries, weekly synthesis, scheduled audits.
  2. Event-based — fires on external signal (webhook, file change, message). Use for: PR opened, alarm raised.
  3. Condition-based — polls a condition, fires when threshold crossed. Use for: "if disk >90%, run cleanup."

PRISM cross-ref: PRISM has all three — /schedule (time), webhook intake in obsidian-compound (event), build-state-snapshot watching for git changes (condition-adjacent). The consensus-queue.jsonl is the canonical append-only log that survives runs — exactly the right shape per Autobot's "treat cron as another input source" principle.

#§6. Multi-Agent Autonomous Systems

Five canonical patterns (Claude blog, 2026):

PatternTopologyWhen to Use
Orchestrator-WorkerOne coordinator fans out to specialized workers, aggregatesMost production AI systems — Claude Code subagents
SwarmDecentralized peers, emergent coordination from local rulesEmbarrassingly parallel exploration
MeshDirect P2P agent communication via A2A protocolSpecialized agents that need to negotiate
HierarchicalTree-structured delegation (manager → leads → workers)Large org-style problems
PipelineSequential stages, each agent transforms then passesLinear data-processing flows

Centralized vs decentralized — when to choose:

  • Centralized (orchestrator-worker) — easier to debug, single point of state, single point of failure. Default choice. Workers don't talk to each other; coordination flows through orchestrator.
  • Decentralized (swarm/mesh) — scales horizontally, no SPOF, but coordination becomes the hard problem (deadlocks, lost updates, emergent loops).

The 2026 industry verdict: orchestrator-worker is the most-deployed in production. Swarm and mesh exist but are research-shaped or used only for specific embarrassingly-parallel workloads.

PRISM's pattern is shared-state coordination (Claude's "Pattern 5" in the 5-pattern blog post): 6 chats, no hierarchy, all coordinate through the same files (AGENT_CHAT.md, WORK_CLAIMS.json, consensus-queue.jsonl). This is the decentralized + shared-state variant — a hybrid that 2026 guides identify as "the most fragile" but also "the most scalable when done right."

The fragility comes from:

  • Write conflicts on shared state (PRISM solves with commit-ownership-guard + git-anti-clobber hooks).
  • Stale reads (PRISM solves with file-claim heartbeats — claims expire after 5min).
  • Lost updates (PRISM solves with append-only logs for chat/claims, never overwrite).
  • Deadlocks (no current PRISM mitigation — relies on the 5min claim TTL to break locks).

PRISM cross-ref: PRISM is exactly the shared-state pattern. The conflict-fork rule (work/<scope> worktrees with cherry-pick recovery) is PRISM's specific innovation — it's not in the public literature but solves the "two chats both want to edit the same file" problem cleanly without distributed locks.

#§7. Verification Gates

The minimal gate set (industry consensus 2026):

Every iteration of an autonomous loop MUST pass:

  1. Build gate — code compiles. If not, append error to Reflexion buffer, retry.
  2. Test gate — affected tests pass. If not, append failures, retry.
  3. Lint gate — style/standards pass. Usually auto-fixable.
  4. Safety gate — domain rules pass (PRISM: no inline physics constants, no stub engines, dispatchers wired). HARD STOP if violated.
  5. Cost gate — accumulated cost <budget. Soft halt if exceeded.
  6. Confidence gate — Evaluator confidence ≥θ. Route to human if low.

What happens when a gate fails:

GateFailure Action
BuildReflexion-loop (auto-retry)
TestReflexion-loop, max 3x; then escalate
LintAuto-fix attempt; if no fix, retry
SafetyHARD STOP, write incident report, page human
CostSoft halt, emit partial output
ConfidencePause, queue for human review

Agent Gate pattern (HN 2026): Every destructive action is vault-backed before execution — i.e., snapshot the file first, then act. If the action fails verification, restore from snapshot. This is git stash/git reflog for non-git files.

Rollback transactions:

For agents that mutate non-git state (database writes, API calls), wrap each iteration in a transaction:

BEGIN
  iteration N writes
  run gates
  if PASS: COMMIT
  else: ROLLBACK + append to Reflexion buffer
END

PRISM cross-ref: PRISM has the gate stack (25+ Stop hooks) but they fire at session-end, not per-iteration. The Reflexion-loop pattern needs per-iteration gates. Wiring suggestion: a loop-iteration-gate.mjs PreToolUse hook that fires when LOOP_ITERATION_BOUNDARY=1 env var is set — runs tsc --noEmit + vitest run --changed + stop_on_unwired_assets and blocks if any fails.

The 2026 pattern is layered memory:

Hot:  conversation buffer (in-context)
Warm: redis cache + recent-events JSONL
Warm: postgres for task state and claims
Cold: qdrant for episodic + semantic
Cold: knowledge graph + wiki for relational

For multi-agent specifically: append-only files are the canonical solution to "many writers, no coordination needed." consensus-queue.jsonl is the shape — every writer appends a line with their agent ID and timestamp; readers can scan or tail. No locks needed.

PRISM cross-ref: PRISM has all the layers — conversation (per-chat), JSONL (consensus-queue, per-agent-handoff history), MD files (HANDOFF, AGENT_CHAT, MEMORY), JSON (WORK_CLAIMS, BUILD_STATE), wiki (knowledge/wiki/), qdrant (QdrantMemoryEngine). The Reflexion-style episodic-memory-into-next-prompt pattern is the missing link — currently each /loop iteration starts fresh without explicit "what did I learn last iteration?" memory beyond the conversation context. Wiring suggestion: 1 unit to add loop-reflexion-memory.mjs helper that writes a per-loop reflection JSONL and prepends the last 3 entries to each iteration's prompt.

#§9. Scaling: 1 → 6 → 100 Chats

Coordination patterns at each scale (industry consensus + PRISM observation):

#1 Chat — No Coordination Needed

Single agent, single conversation, no shared state. The whole question is "did the LLM do what I asked?"

#6 Chats (PRISM's current scale) — Shared-State Coordination

The sweet spot for file-based shared state:

  • Append-only logs for events (chat bus, consensus queue).
  • Claim files with TTL for ownership (WORK_CLAIMS.json, 5min heartbeat).
  • Per-chat handoff files with topic suffix (no overwrites).
  • Conflict-fork rule: when 2 chats want the same file, fork to a sibling worktree.
  • Hard-block hooks at commit time (commit-ownership-guard, git-anti-clobber).

Why this works at 6: the contention rate is low enough that file locks rarely fire. With 6 chats and ~3000 engines, P(two chats touch same file in same minute) is small. Append-only logs eliminate write conflicts entirely.

#20-50 Chats — Hybrid: File-State + Lightweight Broker

Past ~10 chats, file-state coordination starts thrashing on hotspot files (the chat bus, the claims file). The 2026 recommendation:

  • Move the chat bus to Redis pub/sub or postgres LISTEN/NOTIFY — pub/sub eliminates polling.
  • Move claims to Redis with SETNX + TTL — atomic claim acquisition, automatic expiration.
  • Keep handoff files on disk (per-chat, no contention).
  • Add an orchestrator for high-contention work (e.g., merging to main).

#100+ Chats — Orchestrator-Worker + Work-Stealing Queue

At this scale, decentralized coordination breaks down:

  • Orchestrator owns the task queue (postgres or kafka).
  • Workers pull tasks via work-stealing — no claim files, the queue itself is the lock.
  • Specialized lanes — workers tagged by capability, orchestrator routes.
  • Mesh communication only between specialists (e.g., physics-reviewer and test-reviewer talking directly via A2A protocol) — never between workers.
  • Persistent task state in postgres with state machine (pending → in-progress → review → done).
  • Idempotent operations — workers must handle "same task assigned twice" gracefully.

Lock-free state at scale:

  • Append-only logs (immutable, scan-friendly).
  • CRDTs (commutative writes — agents can write in any order, result converges).
  • Optimistic concurrency with version vectors (agent reads version V, writes only if still V).
  • Sharded state — partition by key so different agents touch different shards.

Work-stealing:

When an idle worker has no task, it steals from the most-loaded worker's queue. Eliminates the "one worker bottlenecks while others idle" problem. Used in Tokio, Go runtime, .NET TPL.

Claim-based ownership:

PRISM's current model. An agent claims a resource with a TTL; if it doesn't heartbeat, the claim expires. Works up to ~50 agents; past that, the claim file becomes the bottleneck.

PRISM cross-ref: PRISM is solidly in the 6-chat sweet spot. The conflict-fork rule extends this to maybe ~10 chats before file-state thrashing dominates. Past that, the migration path is chat bus → Redis pub/sub + claims → Redis SETNX. Both are in DOCKER_RUNTIME_STATE already (postgres + redis present in the planned stack), so the infra is ready — what's missing is the engine layer (AgentChatBusEngine, ClaimManagerEngine) wired to use Redis instead of files when PRISM_SCALE_MODE=hybrid is set.
