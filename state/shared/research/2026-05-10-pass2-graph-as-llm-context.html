#§1 — Why this matters for PRISM

PRISM already maintains the prerequisites every "graph-as-context" paper assumes you have to build first:

  • Graph artifact exists: state/shared/system-viz/system-viz.html (rendered from system-graph.json) plus _MASTER_ENVELOPE.json, ~20 augmentation JSONs, and an HTTP server (_server.cjs, :8765). 126,441 nodes / 136,106 edges / 11 layers covers engines + dispatchers + actions + hooks + skills + memories + schemas + files.
  • MCP surface exists: 97 dispatchers / 7,244 actions already expose every capability to agents — the "graph nodes" are the same surface agents already call.
  • Memory layer exists: Karpathy LLM-Wiki adopted 2026-04-27 (722 entries at knowledge/wiki/index.md); Qdrant memory engine wired; 4,245 tribal tips indexed.
  • Multi-agent runtime exists: ~6 concurrent Claude sessions with per-chat handoffs, file-claim guard, workboard/chat bus, conflict-fork rule.

What pass-2 research asks: given all of this exists, which patterns from the 2024-2026 literature project a fixed-layout system graph into direct LLM agent context (a) without ballooning the prompt and (b) as a shared spatial coordinate system for the 6 concurrent chats? Three lenses: (1) GraphRAG retrieval, (2) code-graph projection for coding agents, (3) shared visual canvas as multi-agent coordination substrate.

The unit proposals in §4 are deliberately scoped to wrap, not rebuild — every one extends an existing PRISM substrate rather than competing with it.

#§2 — Reputable papers + docs (URLs verified)

#§2.1 — GraphRAG family (foundational)

  1. Edge et al., "From Local to Global: A Graph RAG Approach to Query-Focused Summarization" — arXiv:2404.16130 (submitted 2024-04-24, revised 2025-02-19). Authors: Darren Edge, Ha Trinh, Newman Cheng, Joshua Bradley, Alex Chao, Apurva Mody, Steven Truitt, Dasha Metropolitansky, Robert Osazuwa Ness, Jonathan Larson (Microsoft Research). Method: "constructs an entity knowledge graph from source documents, then pregenerates community summaries for all groups of closely related entities." Two-stage: LLM builds graph index → community summaries for entity groups; at query time each community summary produces a partial response, consolidated into final answer. Demonstrated "substantial improvements over a conventional RAG baseline for both the comprehensiveness and diversity of generated answers" on ~1M-token corpora. URL: https://arxiv.org/abs/2404.16130
  2. Microsoft Research GraphRAG project page + GitHub — official Microsoft Research project (https://www.microsoft.com/en-us/research/project/graphrag/) and modular reference implementation (https://github.com/microsoft/graphrag). Pipeline: extract → entities → relationships → community detection → summaries. Repo explicitly warns "GraphRAG indexing can be an expensive operation."
  3. Han et al., "Retrieval-Augmented Generation with Graphs (GraphRAG)" — survey — arXiv:2501.00309 (v1 2024-12-31, v2 2025-01-08). 18 authors led by Haoyu Han + Jiliang Tang. Proposes a holistic 5-component GraphRAG framework: query processor / retriever / organizer / generator / data source. Reviews domain-specific designs because "graphs in different domains exhibit distinct relational patterns and require dedicated designs." URL: https://arxiv.org/abs/2501.00309
  4. Peng et al., "Graph Retrieval-Augmented Generation: A Survey" — arXiv:2408.08921, also at ACM TOIS (https://dl.acm.org/doi/10.1145/3777378). Formalizes GraphRAG workflow as graph-based indexing + graph-guided retrieval + graph-enhanced generation. URL: https://arxiv.org/abs/2408.08921
  5. Awesome-GraphRAG curation — https://github.com/DEEP-PolyU/Awesome-GraphRAG. Curated list of surveys, papers, benchmarks, and open-source projects. Useful for tracking the long tail (Graph-R1, RAKG, HybridRAG, etc.).

#§2.2 — Codebase-as-graph for AI coding (the load-bearing arm for PRISM)

  1. Ouyang et al., "RepoGraph: Enhancing AI Software Engineering with Repository-level Code Graph" — arXiv:2410.14684 (submitted 2024-10-03, revised 2025-03-18). Published as conference paper at ICLR 2025. Authors: Siru Ouyang, Wenhao Yu, Kaixin Ma, Zilin Xiao, Zhihan Zhang, Mengzhao Jia, Jiawei Han, Hongming Zhang, Dong Yu. Key result: "RepoGraph boosts the success rate of existing methods for both agent and procedural frameworks by achieving an average relative improvement of 32.8%" on SWE-bench. "Agentless + RepoGraph achieved a 29.67% resolve rate, setting a new state-of-the-art for open-source methods on SWE-bench Lite." Graph is line-level: each node = one line of code, edges = definition/reference dependencies. Retrieval uses ego-graphs centered on keyword/issue nodes. Code: https://github.com/ozyyshr/RepoGraph. URL: https://arxiv.org/abs/2410.14684
  2. Chen et al., "LocAgent: Graph-Guided LLM Agents for Code Localization" — arXiv:2503.09089 (submitted 2025-03-12, revised 2025-04-29), ACL 2025 long paper (https://aclanthology.org/2025.acl-long.426/). Authors: Zhaoling Chen, Xiangru Tang, Gangda Deng, Fang Wu, Jialong Wu, Zhiwei Jiang, Viktor Prasanna, Arman Cohan, Xingyao Wang. Parses codebases into directed heterogeneous graphs: nodes = files/classes/functions; edges = imports, invocations, inheritance. Enables LLM agents to do multi-hop reasoning to locate change-sites. Fine-tuned Qwen-2.5-Coder-Instruct-32B reaches 92.7% accuracy on file-level localization at ~86% cost reduction vs SOTA proprietary. +12% Pass@10 on downstream GitHub issue resolution. URL: https://arxiv.org/abs/2503.09089
  3. Liu et al., "Prometheus: Towards Long-Horizon Codebase Navigation for Repository-Level Problem Solving" — arXiv:2507.19942. Memory-centric coding agent framework: (a) represents repo as unified knowledge graph encoding semantic dependencies, (b) context engine with working memory retains/reuses previously explored contexts across reasoning steps, (c) multi-agent split for classify / reproduce / patch / verify. Using GPT-5: 74.4% on SWE-bench Verified and 33.8% on SWE-PolyBench Verified (Top-6 / Top-1 among open-source agent systems). Solves needle-in-haystack via smarter context management, not bigger windows. URL: https://arxiv.org/html/2507.19942v2
  4. "CodexGraph: Bridging Large Language Models and Code Repositories via Code Graph Databases" — NAACL 2025 — https://aclanthology.org/2025.naacl-long.7.pdf. Exposes code graphs to LLM agents via graph database interfaces (verified via WebSearch snippet — direct PDF parse failed but reference is canonical and indexed in Awesome-Repo-Level-Code-Generation).
  5. "Code Graph Model (CGM): A Graph-Integrated LLM for Repository-Level Software Engineering Tasks" — OpenReview https://openreview.net/forum?id=b98ODdeYq5. Integrates a code graph as a first-class modality into the LLM instead of using it only at retrieval time.
  6. Stack Graphs (GitHub Engineering) — blog post 2021-12-09, updated 2024-07-23 (https://github.blog/open-source/introducing-stack-graphs/); paper "Stack graphs: Name resolution at scale" — arXiv:2211.01224 (Douglas A. Creager). DSL for declaring name-binding rules over Tree-sitter parse trees. File-incremental: per-file subgraph built without visibility into other files; merged at query time. Powers GitHub's Precise Code Navigation cross-repo. This is the structural inspiration for PRISM's per-domain envelope JSONs: each domain produces its own augmentation, merged at viz-render time. URL: https://github.blog/open-source/introducing-stack-graphs/

#§2.4 — Visualization-as-shared-context (the spatial-UI thesis)

  1. tldraw AI integrations docs — https://tldraw.dev/docs/ai. "AI models have direct access to read and manipulate shapes, allowing an agent to observe what's on the canvas, understand spatial relationships, and create or modify shapes to accomplish tasks." Agent Starter Kit (https://tldraw.dev/starter-kits/agent) captures "both visual screenshots and structured shape data from the canvas, giving the AI model context about spatial relationships, visual appearance, and semantic meaning of shapes." This is the dual-channel pattern PRISM should adopt: send the LLM (a) the screenshot of the relevant region of system-viz and (b) the structured node list — neither alone is sufficient.
  2. Latent Space podcast: "The Accidental AI Canvas — with Steve Ruiz of tldraw" — https://www.latent.space/p/tldraw. History: makereal.tldraw.com (Nov 2023, "first vibe coding tool") → realtime drawing → tldraw.computer (AI workflows) → fairies.tldraw.com (spatialized multi-agent experiment). Ruiz argues the canvas is a better UI for multi-agent than chat because agents have persistent spatial state observable by humans and other agents.
  3. Excalidraw MCP server (yctimlin/mcp_excalidraw) — https://github.com/yctimlin/mcp_excalidraw. MCP server + Claude Code skill: agents create/edit/export Excalidraw diagrams with real-time canvas sync. The verified meta-claim (Nimbalyst 2026 comparison): "Excalidraw won the canvas war, and MCP is the reason."
  4. AgentCoord: Visually Exploring Coordination Strategy for LLM-based Multi-Agent Collaboration — arXiv:2404.11943, published ScienceDirect 2025 (https://www.sciencedirect.com/science/article/abs/pii/S0097849325001797). Interactive visual interface to design, edit, debug coordination strategies. Key claim: "When users use natural language to design these strategies and communicate with LLMs, the large amount of text containing complex information hinders their ability to understand and iterate on strategies." Argues for structured visual representation of multi-agent entities and relationships. This is the closest published precedent for what PRISM's system-viz already does for 6 concurrent Claude chats.
  5. GitNexus (open-source MCP-native code-graph engine) — coverage: https://www.marktechpost.com/2026/04/24/meet-gitnexus-an-open-source-mcp-native-knowledge-graph-engine-that-gives-claude-code-and-cursor-full-codebase-structural-awareness/. KuzuDB + Tree-sitter under the hood; exposes the graph via MCP tools. This is the closest extant precedent for PRISM's intended architecture. Worth a feature-parity audit.
  6. Understand-Anything (Claude Code plugin) — https://github.com/Lum1104/Understand-Anything. Multi-agent pipeline builds a knowledge graph of every file/function/class/dependency + interactive dashboard. Works with Claude Code, Codex, Cursor, Copilot, Gemini CLI.
  7. Graphify — open-sourced 48h after Karpathy's LLM-Wiki post (Oct 2025 by community attribution). "71.5x fewer tokens per query" / "20 languages via tree-sitter" / "20.4K stars." Slash command /graphify inside Claude Code.
  8. code-review-graph (tirth8205) — https://github.com/tirth8205/code-review-graph. Local persistent codebase map for Claude Code. Reported "6.8× fewer tokens on reviews and up to 49× on daily coding tasks."

#§4 — Concrete PRISM unit proposals

Each unit names a viz_node_id slot and explicit deps/blocks so the system-viz can ingest them and the dependency oracle can sequence them. Slots are namespaced under viz_node_id: graph-as-context/*.

#U-GAC01: system-viz MCP query adapter

  • viz_node_id: graph-as-context/system-viz-mcp-adapter
  • depends_on: state/shared/system-viz/_MASTER_ENVELOPE.json (exists), scripts/system-viz-query.mjs (exists per MEMORY.md)
  • blocks: U-GAC02, U-GAC03, U-GAC07
  • description: Promote scripts/system-viz-query.mjs from CLI helper to MCP dispatcher actions under prism_session: viz_graph.get_node, viz_graph.get_neighbors(node_id, depth), viz_graph.ego_graph(node_id, depth), viz_graph.search(text), viz_graph.find_path(from, to, max_hops). Mirrors RepoGraph's ego-graph retrieval pattern (arXiv:2410.14684). Returns JSON only — never the full graph.
  • synergy: Replaces ad-hoc Glob+Grep+Agent calls with a 5-tool surface.

#U-GAC02: viz_node_id stamps on every artifact

  • viz_node_id: graph-as-context/node-id-stamping
  • depends_on: U-GAC01
  • blocks: U-GAC04, U-GAC05
  • description: Add viz_node_id: <stable-slug> to the frontmatter of every roadmap unit, wiki entry, handoff file, milestone envelope, and skill file. Stable slug derived from _MASTER_ENVELOPE.json. Wiki and handoff templates updated. Stop hook validates presence on commit. This is the "spatial coordinate" the 6 concurrent chats can share — each chat's handoff says exactly which sub-graph it touches.
  • synergy: Wires directly into existing enforce-handoff-topic.mjs and commit-ownership-guard.

#U-GAC03: agent-side graph-context injector hook

  • viz_node_id: graph-as-context/inject-on-prompt
  • depends_on: U-GAC01, U-GAC02
  • blocks: none (parallel-safe)
  • description: New UserPromptSubmit hook graph-context-inject.mjs. When the user prompt mentions a known viz_node_id (or matches a node by name fuzzy-search), inject the ego-graph at depth 1-2 as a compact YAML block (target ≤120 lines, tokens budgeted). Pattern: GitNexus/RepoGraph "pre-compute structure, send slice on demand." Keyword-gated to keep token budget bounded.
  • synergy: Slots beside existing wiki-precheck-inject, inventory-check-guard, chat-bus-inject. Reuses keyword-gating machinery.

#U-GAC04: agent file-claim with node-id resolution

  • viz_node_id: graph-as-context/claim-by-node-id
  • depends_on: U-GAC02
  • blocks: U-GAC06
  • description: Extend file-claim-guard.mjs to also claim graph sub-regions by viz_node_id. Instead of "chat A owns file X", "chat A owns sub-graph rooted at graph-as-context/lathe-engine-cluster depth 2." Conflict detection now sees overlapping sub-graphs, not just file lists. Encodes the conflict-fork rule at graph granularity.
  • synergy: Makes the conflict-fork rule (already documented in MEMORY.md feedback_conflict_fork_rule.md) graph-native instead of file-native — multi-chat conflicts surface earlier and at higher resolution.

#U-GAC05: dispatcher action prism_session:plan_with_graph

  • viz_node_id: graph-as-context/plan-with-graph
  • depends_on: U-GAC01, U-GAC02
  • blocks: none
  • description: Action takes a goal description, calls Ollama qwen2.5-coder for sub-graph retrieval (the cheap step), returns a 30-line plan with viz_node_id references and dependency chain. Mirrors LocAgent's multi-hop reasoning (arXiv:2503.09089) but on the meta-graph instead of the source-code AST graph.
  • synergy: Direct extension of prism_ai + prism_session; respects Ollama-offload policy.

#U-GAC06: graph-aware Stop hook stop-on-orphan-node

  • viz_node_id: graph-as-context/orphan-node-guard
  • depends_on: U-GAC02, U-GAC04
  • blocks: none
  • description: Stop hook fails the session if it added a new engine/dispatcher/skill/hook but did not also (a) add a viz_node_id to the file frontmatter and (b) regenerate the system-viz so the new node exists. Complement to existing stop_on_unwired_assets. Closes the "engine wired to dispatcher but invisible in viz" gap.
  • synergy: Layers on top of existing stop-auto-wire.mjs lineage.

#U-GAC07: viz screenshot tool for multimodal agent context

  • viz_node_id: graph-as-context/viz-screenshot-mcp
  • depends_on: U-GAC01
  • blocks: none
  • description: MCP action viz_graph.screenshot(node_id, depth, format=png) — uses Playwright headless against the existing :8765 server to render a focused PNG of the sub-graph around a node, then returns the file path. Mirrors tldraw's dual-channel pattern: structured JSON + screenshot. Agent can include the image inline (Claude Code reads PNGs natively). Used only when a user explicitly invokes /system-viz <topic> to keep cost bounded.
  • synergy: Extends existing _server.cjs viz server with one new endpoint.

#U-GAC08: persistent graph delta log (compounding pattern)

  • viz_node_id: graph-as-context/graph-delta-log
  • depends_on: U-GAC02
  • blocks: none
  • description: Every system-viz regeneration writes a delta (nodes added/removed/relabeled, edges added/removed) to state/shared/system-viz/graph-delta.jsonl. New unit graph-delta-summarize.mjs (Ollama, weekly) generates wiki entries documenting structural drift. Implements the Karpathy LLM-Wiki "compounding knowledge" pattern (X/karpathy/2039805659525644595) on the graph itself, not just on text docs.
  • synergy: Extends the existing wiki layer; Ollama owns ≥70% of summarization (per global directive).

Cross-cutting payoffs:

  • Token budget: Per code-review-graph claim (49x reduction on daily tasks) and Graphify (71.5x per query), sub-graph retrieval routinely cuts per-query token cost by an order of magnitude. PRISM's system-viz already exists; adapter cost is one-off.
  • 6-chat coordination: viz_node_id as shared coordinate system replaces file-path overlap detection with sub-graph overlap detection. Conflicts surface at graph granularity, not file granularity. Confirms the AgentCoord (arXiv:2404.11943) thesis that visual structure beats prose for multi-agent coordination.
  • Compounding intelligence: GAC08's delta log is the Karpathy LLM-Wiki pattern lifted from docs to structure. Every regeneration adds, never replaces.
  • Anti-duplication: GAC03's ego-graph injection front-runs duplicationGuardEngine — the LLM sees neighbors before proposing a new node, so duplicates die earlier in the loop.

Stale graph syndromeAgents act on a system-viz that hasn't been regenerated; ghost nodes / missing edges; multi-chat blame the graph for their drift.Stop hook stop-on-orphan-node (GAC06) + cron regen if mtime > 1h. Delta log (GAC08) makes staleness visible.
Graph-as-context bloatNaïve ego-graph at depth 3 dumps thousands of nodes into the prompt; defeats the token-saving purpose.Bound depth to 1-2 by default; token-budget the injected YAML to ≤120 lines (GAC03). RepoGraph (arXiv:2410.14684) uses ego-graphs precisely because they bound traversal.
Indexing costMicrosoft's own GraphRAG docs warn "GraphRAG indexing can be an expensive operation" — building the graph from scratch every session burns Claude tokens fast.PRISM already pays this cost once per regen, not per session — system-viz.html is cached. Ollama owns ≥70% of summarization per global policy.
