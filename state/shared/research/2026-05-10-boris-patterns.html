#Boris Cherny / Anthropic Claude Code Methodology — Research Card

Date: 2026-05-10 Author: researcher subagent (claude-85cedf09 dispatch) Cross-ref: H:/prism/state/shared/specs/BORIS-LOOP-AGENT-DOCTRINE.md (227 lines, our canonical version — DO NOT duplicate, EXPAND) Sibling artifact: mcp-server/data/state/BASELINE_INVENTORY.json for live PRISM counts referenced below.

#TL;DR

  1. Verification feedback loop is the #1 lever — Boris's signature claim is "give Claude a way to verify its work and it will 2-3x quality." Anthropic's official docs now codify this as "the single highest-leverage thing you can do" (Best Practices, 2026). PRISM has the gates (stop_on_failing_tests, physics-verify, /verify-loop) but the loop is not yet PER-FORGE-RUN enforced.
  2. /loop and /schedule are first-class as of Claude Code v2.1.72 — /loop is local + session-scoped (max 7 days, auto-expires); /schedule is cloud-managed via Routines. Boris personally runs /loop 5m /babysit and /loop 30m /slack-feedback. PRISM's /wiki-morning, /precompact, etc. should migrate to /loop semantics rather than ad-hoc cron.
  3. /simplify and /batch ship parallel-agent quality enforcement — /simplify runs 3 specialized review agents in parallel (reuse, quality, efficiency) on every diff; /batch orchestrates worktree-isolated agents for migrations. Combined with /go, this is the production pipeline pattern Boris uses to ship 20-30 PRs/day.
  4. Worktree isolation is now built-in — claude --worktree, isolation: worktree in agent frontmatter, automatic cleanup when no changes. PRISM's "conflict-fork rule" reinvented this manually; native support means we should make isolation: worktree the default for ANY subagent that touches >2 files.
  5. CLAUDE.md back-flow is a discipline, not a feature — Boris updates CLAUDE.md "multiple times weekly" and tags @.claude in PRs to auto-append. PRISM's error-pattern-promote.mjs covers regressions, but session-level discoveries don't auto-flow yet (gap).

#1. Verification Feedback Loop (HARD GATE)

Principle. Boris's most-quoted Claude Code claim:

"Probably the most important thing to get great results out of Claude Code — give Claude a way to verify its work. If Claude has that feedback loop, it will 2-3x the quality of the final result." — howborisusesclaudecode.com [1]

Anthropic codified this in the official Best Practices doc:

"Include tests, screenshots, or expected outputs so Claude can check itself. This is the single highest-leverage thing you can do." — Best Practices for Claude Code [2]

Mechanism. Verification is domain-specific:

  • Backend → test suite runs (bun test, vitest run).
  • Frontend → Claude in Chrome extension takes screenshot, compares against spec, iterates until matching.
  • Mobile → simulator build + automated UI test.
  • CLI → bash command + exit-code parsing.
  • Multi-step refactors → linter + typechecker + smoke test.

The official doc gives an explicit before/after framing in three rows of a table — "implement validateEmail" vs "implement validateEmail with these test cases AND run the tests after implementing"; "make dashboard look better" vs "[paste screenshot] implement this, screenshot result, list differences, fix them"; "build is failing" vs "fix the root cause and verify the build succeeds, don't suppress the error". [2]

PRISM today.

  • stop_on_failing_tests.mjs Stop hook blocks task close on red tests.
  • /scrutinize 3-of-3 (Codex + Gemini + Opus) is our de-facto verification quorum.
  • physics-verify skill exists and runs reference-value tests against engines.
  • /verify-loop skill exists.
  • Engine-named test convention enforced (commit 8639f56b5 is the canonical example: SCE engine + matching SpecificCuttingEnergyEngine.test.ts).

Gap. The verification check is per-engine and per-commit, not per-forge-run. A forge run can complete with one passing engine while another sibling engine in the same plan is unverified. Doctrine §3 #1 already calls this out as "HARD GATE" but no Stop hook enforces "EVERY unit in the plan has a green verification channel" before declaring milestone closure. → Gap unit candidate: U-FORGE7-VERIFY-PLAN-GATE (see §14).

#2. Parallel-Agent Worktree Isolation

Principle. Native worktree support shipped in Claude Code v2.1.50 [3]. Boris announced it on Threads:

"Introducing: built-in git worktree support for Claude Code. Now, agents can run in parallel without interfering with one other. Each agent gets its own worktree and can work independently." — @boris_cherny on Threads [3]

Mechanism.

  • CLI: claude --worktree feature-name (or auto-generated name).
  • Agent frontmatter: `yaml --- name: code-simplifier isolation: worktree --- `
  • Each worktree gets a separate branch + working directory + index under .claude/worktrees/.
  • Auto-cleanup: worktrees with no changes are removed when the session ends; worktrees with changes persist for review. [4]
  • Combined with /batch, "10 agents migrating 10 files each in parallel without stepping on each other." [5]

The killer scenario. From the Claude Directory worktree guide:

"Without worktree isolation, parallel sub-agents are limited to reading files or writing to non-overlapping paths, but with isolation, each agent has the entire codebase to itself — Agent A can rewrite src/auth.ts while Agent B rewrites the same file with a different approach, and you review both branches and pick the winner." [4]

PRISM today.

  • We run 6+ concurrent chats coordinated by commit-ownership-guard + git-anti-clobber + state/shared/AGENT_WORKBOARD.md.
  • The "conflict-fork rule" in H:/prism/CLAUDE.md re-invents worktree isolation manually after collisions ("fork to your own tree: git worktree add ../prism-<milestone> -b work/<milestone>").
  • Worktree commit 03586e2fa (XPROC-NEURAL-OPTIMIZE-MS0) is a recent live application of this rule — note the -WORKTREE suffix in the commit topic.
  • Most subagents launched via PRISM's forge-team STILL share the parent tree.

Gap. Doctrine §3 #3 already flags this. The fix: Doctrine §4 /forge7 Phase 4 LOOP 2 default should be isolation: worktree (override via --no-isolation for trivial units). NOT YET SHIPPED. → Gap unit candidate: U-FORGE7-WORKTREE-DEFAULT (see §14).

#3. Plan Peer-Review

Principle. Boris explicitly recommends a second-Claude as staff-engineer reviewer:

"Have Claude A draft plans, then Claude B review them as a staff engineer." (Tip #5 in anup.io's curated 35-tips list [6])

The Anthropic Best Practices doc reinforces with the Writer/Reviewer pattern (Session A writes, Session B reviews with fresh context to avoid bias toward code it just wrote). [2]

Anthropic's multi-agent research system generalizes this: a lead researcher drafts the plan, saves it to memory, then dispatches 3-5 subagents in parallel against it; if context exceeds 200K tokens it gets truncated, so the plan is what survives. [7]

PRISM today.

  • 3-of-3 scrutiny gate (Codex + Gemini + Opus) — see H:/prism/CLAUDE.md SCRUTINY GATE section. This IS plan peer-review applied to the diff post-hoc.
  • /peer-review skill exists for explicit invocation.
  • superpowers:requesting-code-review and superpowers:receiving-code-review skills available.

Gap. Plan-mode review (BEFORE code) is manual. Boris's pattern is to spawn the reviewer the moment Plan-mode emits a plan — not after the diff is written. PRISM's /peer-review is reactive, not auto-injected after /rgs6 generate. Doctrine §4 calls for Phase 4.5 of /forge7 to "Auto-spawn /peer-review against the plan emitted by /rgs6 generate" — this is not yet shipped. → Gap unit candidate: U-FORGE7-PLAN-PEER-REVIEW (see §14).

#4. CLAUDE.md Back-Flow

Principle. Boris's exact quote:

"Anytime we see Claude do something incorrectly we add it to CLAUDE.md, so Claude knows not to do it next time. We update it multiple times a week." — Pragmatic Engineer interview [8]

The Anthropic team uses the Claude Code GitHub Action to incorporate @.claude PR comments directly into the file. [6]

Anthropic Best Practices guidance:

"If Claude keeps doing something you don't want despite having a rule against it, the file is probably too long and the rule is getting lost. If Claude asks you questions that are answered in CLAUDE.md, the phrasing might be ambiguous. Treat CLAUDE.md like code: review it when things go wrong, prune it regularly, and test changes by observing whether Claude's behavior actually shifts." [2]

The doc also specifies emphasis tuning: "you can tune instructions by adding emphasis (e.g., 'IMPORTANT' or 'YOU MUST') to improve adherence." [2]

Locations supported (per Best Practices):

  • ~/.claude/CLAUDE.md — applies to all sessions.
  • ./CLAUDE.md — checked into git, shared with team.
  • ./CLAUDE.local.md — gitignored, personal overrides.
  • Parent/child directory CLAUDE.md files — pulled in on demand for monorepos.
  • @path/to/import syntax for imports. [2]

PRISM today.

  • H:/prism/CLAUDE.md (project) + ~/.claude/CLAUDE.md (user) both exist and are actively maintained.
  • error-pattern-promote.mjs Stop hook does partial back-flow.
  • Recent regressions section pattern is informally followed but no automated append.
  • MEMORY.md index in ~/.claude/projects/H--prism/memory/MEMORY.md is a parallel back-flow surface.

Gap. Doctrine §3 #7 calls for Stop hook to explicitly append regression patterns. The current error-pattern-promote writes to its own ledger, not to the project CLAUDE.md ## Recent regressions section. → Gap unit candidate: U-CLAUDE-MD-BACKFLOW (already in MS3 Track J — re-confirm priority).

#5. /loop and /schedule Recurring Workflows

Principle. Boris's launch announcement:

"Released today: /loop. /loop is a powerful new way to schedule recurring tasks, for up to 3 days at a time. eg. '/loop babysit all my PRs. Auto-fix build issues and when comments come in, use a worktree agent to fix them.' eg. '/loop every morning use the Slack MCP to give me a summary of top posts I was tagged in.'" — @boris_cherny on Threads [9]

His personal usage (from same source [9]):

  • /loop 5m /babysit — auto-address code review and auto-rebase his PRs.
  • /loop 30m /slack-feedback — automatically put up PRs for Slack feedback every 30 minutes.

Three scheduling tiers (per official doc [10]):

Runs onAnthropic cloudYour machineYour machine

Persistent across restartsYesYesRestored on --resume if unexpired
Local filesNo (fresh clone)YesYes
Min interval1 hour1 minute1 minute
Max session-scoped lifetimen/an/a7 days, then auto-expires

/loop modes [10]:

  • /loop 5m check the deploy — fixed cron, your prompt.
  • /loop check the deploy — Claude self-paces (1m to 1h based on observation).
  • /loop alone — runs the built-in maintenance prompt or custom loop.md (project: .claude/loop.md; user: ~/.claude/loop.md).
  • /loop 20m /review-pr 1234 — re-runs a packaged workflow each iteration.

Jitter [10]: "Recurring tasks fire up to 30 minutes after the scheduled time (or up to half the interval, for tasks that run more often than hourly). An hourly job scheduled for :00 may fire anywhere up to :30. One-shot tasks scheduled for the top or bottom of the hour fire up to 90 seconds early."

PRISM today.

  • We have ~440 skills but most "recurring" workflows (/wiki-morning, /precompact, /run-continuous) rely on user invocation or external cron, not /loop.
  • /schedule and /loop skills appear in the available-skills list but their wiring to PRISM cron infrastructure is incomplete.
  • We have cron-bootstrap, cron-manage, and CronCreate MCP tooling but they don't yet honor the 7-day expiry semantics.
  • forge_audit_v2 is supposed to self-schedule a 7-day re-run via /loop (Doctrine §4) — not yet shipped.

Gap. Migrate PRISM's recurring-cadence skills to /loop semantics so the 7-day auto-expiry safety bound applies. → Gap unit candidate: U-LOOP-MIGRATE-CADENCE (see §14).

#6. /go Composite Skill Chain

Principle. Boris's /go philosophy:

"Personally, many of my prompts these days look like 'claude do blah blah, go.' /go is [the composite skill that] (1) tests end-to-end via bash/browser/computer use (2) runs /simplify (3) puts up a PR — so when you come back, you know the code works." — @boris_cherny on Threads [11]

Why composite chains. Boris's framing (paraphrased from [6, 11]): /simplify was promoted to a built-in skill in Feb 2026 specifically because parallel review-agents on every change is the production discipline. The phases are spec → draft → simplify → verify, and each phase benefits from a different "mind" (i.e., different agent context).

PRISM today.

  • We have all the constituent pieces: /test, /simplify (project skill exists), /scrutinize, /handoff, auto-commit, etc.
  • Doctrine §4 /forge-go proposed but not yet shipped: `
    1. /test affected ← verification feedback (Boris #1)
    2. /simplify ← post-build cleanup
    3. /scrutinize ← multi-role review
    4. commit + push ← if all green
    5. /handoff ← write per-agent handoff
    6. (optional) /loop ← schedule re-verify in 4h
    `

Gap. No single composite chain skill exists. Each step is a separate manual invocation, which is what Boris explicitly designed /go to eliminate. → Gap unit candidate: U-FORGE-GO-CHAIN (already in MS3 Track J — re-confirm priority).

#7. isolation: worktree Default for Risky Work

Principle. Anthropic's /batch command makes isolation: worktree the default for parallel migrations:

"The orchestrator launches one background agent per unit in true parallel, each getting isolation in a 'worktree' for a clean git worktree. After implementing, each worker runs /simplify on its own changes, executes the test suite, commits, pushes, and opens a PR." [5]

Sub-agent doc states isolation should be configured per-agent in frontmatter, not at invocation time, so the agent's contract is unambiguous. [12]

When to default to isolation (synthesizing [3], [4], [5]):

  • Any subagent touching >2 files.
  • Any migration touching shared modules.
  • Any experimental refactor where you want to compare approaches.
  • Any long-running agent (>15 minutes) so it can't block your main HEAD.

When to NOT use isolation:

  • Single-file fixes where overhead isn't justified [4].
  • Read-only investigations (use subagent without isolation — context savings already comes from separate context window).
  • Short-lived edits where the worktree creation/cleanup cost exceeds the work.

PRISM today.

  • Most subagents share parent tree.
  • The xproc-neural worktree commit (03586e2fa) shows we manually invoke git worktree add AFTER hitting commit-ownership-guard — reactive, not preemptive.

Gap. Make isolation: worktree the default in our agent frontmatter for any agent class with multi_file: true. → Gap unit candidate: U-AGENT-FRONTMATTER-ISOLATION-DEFAULT (see §14).

#8. Slash-Command Discipline

Principle. Anthropic's official taxonomy (from Best Practices [2]):

SurfacePurposeLoaded
CLAUDE.mdProject conventions Claude needs every sessionAlways loaded
Skills (.claude/skills/SKILL.md)Domain knowledge / reusable workflowsOn demand (model-invoked or /skill-name)
Hooks (.claude/settings.json)Deterministic automation that MUST happenAlways-on, every matching event
Subagents (.claude/agents/*.md)Specialized task delegation with isolated contextPer-task delegation
MCP serversExternal tool integrationConnected once per session

The doc explicitly warns:

"CLAUDE.md is loaded every session, so only include things that apply broadly. For domain knowledge or workflows that are only relevant sometimes, use skills instead. Claude loads them on demand without bloating every conversation." [2]

Hooks are described as the deterministic-action layer:

"Use hooks for actions that must happen every time with zero exceptions. Unlike CLAUDE.md instructions which are advisory, hooks are deterministic and guarantee the action happens." [2]

Skills can declare disable-model-invocation: true for workflows with side effects you want to trigger manually [2].

PRISM today. We over-rotate on CLAUDE.md (project file is ~270 lines); should rotate more domain-specific guidance (e.g., per-engine cookbooks) into skills. ~440 skills currently exist but the auto-injection on UserPromptSubmit (hookify hooks) means many fire even when not needed — exactly the bloat Anthropic warns against.

Gap. Audit H:/prism/CLAUDE.md and the auto-inject hooks for "would removing this cause Claude to make mistakes? if not, cut it" — Anthropic's pruning rubric. → Gap unit candidate: U-CLAUDE-MD-PRUNE-AUDIT (see §14).

#9. Anthropic Multi-Agent Research Orchestrator Pattern

Principle. From Anthropic's "How we built our multi-agent research system" [7]:

Architecture. Lead Researcher (Opus) decomposes query → spawns 3-5 subagents (Sonnet) in parallel → each subagent does breadth-first search → returns to lead → lead synthesizes.

Key numbers:

  • 15× token consumption vs single-agent chat.
  • 90.2% breadth-first lift vs single-agent Opus on BrowseComp evaluation.
  • 80% of performance variance explained by token usage (with tool calls + model choice making up the other 15%).

Why parallel works.

"By running several agents in parallel, multi-agent systems allow breadth-first exploration, compress large search spaces into manageable insights, and reduce the risk of missing key information... reducing research time by up to 90% for complex queries." [7]

Memory pattern.

"The lead agent saves its research plan to persistent memory because if the context window exceeds 200,000 tokens it will be truncated and it is important to retain the plan." [7]

Subagent output isolation.

"Specialized agents store work in external systems (filesystem/artifacts) rather than communicating entirely through the lead agent, preventing information loss and reducing token overhead from copying large outputs through conversation history." [7]

Cost economics. This is why multi-agent orchestration is reserved for breadth-first / open-ended problems where 90% lift outweighs 15× cost. NOT for routine "fix this typo" tasks.

Five workflow patterns (from Building Effective Agents [13]):

  1. Prompt chaining
  2. Routing
  3. Parallelization
  4. Orchestrator-workers (the multi-agent research pattern)
  5. Evaluator-optimizer

PRISM today.

  • prism_orchestrate and prism_atcs dispatchers implement orchestrator-worker semantics.
  • forge-team agent (3-agent: builder + physics-reviewer + test-reviewer) is a small orchestrator-worker.
  • /forge2 through /forge7 skills increasingly leverage subagent dispatch with isolation.
  • The 3-of-3 scrutiny gate (Codex + Gemini + Opus) applied to diffs IS a 3-way evaluator-optimizer pattern.

Gap. PRISM doesn't have a published cost model for "when to spawn 3-5 parallel subagents vs. single Claude call." The 15×-cost / 90%-lift breakeven is task-class dependent and we have no telemetry for it. → Gap unit candidate: U-MULTI-AGENT-COST-TELEMETRY (see §14).

#10. TodoWrite + Plan-Mode Hygiene

Principle. From the Anthropic Best Practices doc [2]:

Plan mode (shift+tab twice):

"Letting Claude jump straight to coding can produce code that solves the wrong problem. Use plan mode to separate exploration from execution. The recommended workflow has four phases: Explore → Plan → Implement → Commit."

"Plan mode is useful, but also adds overhead. For tasks where the scope is clear and the fix is small (like fixing a typo, adding a log line, or renaming a variable) ask Claude to do it directly. Planning is most useful when you're uncertain about the approach, when the change modifies multiple files, or when you're unfamiliar with the code being modified. If you could describe the diff in one sentence, skip the plan."

TodoWrite. From the system prompt of Claude Code itself (recovered from third-party analysis [14]):

"The model is required to use TodoWrite as much as possible to manage and plan tasks such as breaking down large, complex tasks into smaller steps... It is critical that you mark todos as completed as soon as you are done with a task, and not batch up multiple tasks before marking them as completed."

The Jan 2026 upgrade added dependencies, blockers, and multi-session collaboration to TodoWrite.

The hygiene split:

  • TodoWrite = in-conversation, ephemeral, completion-tracked.
  • Handoffs = cross-session, durable (per-agent files for PRISM).
  • Plans = pre-execution, durable, peer-reviewable.

PRISM today.

  • TodoWrite used by Claude in-conversation but not surfaced in PRISM's coordination state (AGENT_WORKBOARD, etc.).
  • /handoff writes to per-agent files (HANDOFF-<id>-<topic>.md) — well-covered.
  • /plan-build, /read-plan, /write-plan (superpowers) skills exist for the plan layer.

Gap. No bridge between TodoWrite and the per-agent handoff. When a chat compacts, TodoWrite contents should serialize INTO the handoff so the resumed session sees the prior task list. → Gap unit candidate: U-TODOWRITE-HANDOFF-BRIDGE (see §14).

#11. Non-Interactive Shell Discipline

Principle. Headless mode (-p flag) requires deterministic, hang-free shell:

"With claude -p 'your prompt', you can run Claude non-interactively, without a session. Non-interactive mode is how you integrate Claude into CI pipelines, pre-commit hooks, or any automated workflow. The output formats let you parse results programmatically: plain text, JSON, or streaming JSON." [2]

Critical CI gotcha.

"PermissionRequest hooks don't fire in non-interactive mode (-p). If you're running Claude Code headlessly, use PreToolUse instead." [15]

Auto-mode for headless.

"For uninterrupted execution with background safety checks, use auto mode. A classifier model reviews commands before they run, blocking scope escalation, unknown infrastructure, and hostile-content-driven actions while letting routine work proceed without prompts. For non-interactive runs with the -p flag, auto mode aborts if the classifier repeatedly blocks actions, since there is no user to fall back to." [2]

Discipline rules (synthesizing [2], [10], [15]):

  • Always pass --no-pager to git, gh, less-piped commands.
  • Use --non-interactive flags where supported.
  • Avoid commands that prompt without explicit input (e.g., git rebase -i, npm init).
  • For shell loops, use --allowedTools to scope permissions.
  • For CI, avoid PermissionRequest hooks — convert to PreToolUse or rely on auto-mode classifier.

PRISM today.

  • We have rtk token-reduction wrapper that handles many flags (auto-injects --no-pager for git, --non-interactive for npm).
  • Headless mode rarely used; most PRISM forge runs are interactive.
  • auto-agent, automation:auto-agent, auto-fix-generate skills exist but --permission-mode auto is not the default invocation.

Gap. PRISM has no documented headless / CI-mode profile. For cron-driven background jobs to be reliable, they need to run with claude -p + auto-mode + no PermissionRequest hooks. → Gap unit candidate: U-HEADLESS-CI-PROFILE (see §14).

#12. Karpathy / Boris Cross-Pollination

Principle. Karpathy's Software 2.0 → Software 3.0 framing [16]:

"Software 1.0 = humans writing explicit code. Software 2.0 = humans creating datasets, objectives, and neural networks where the program is learned into weights. Software 3.0 = humans programming LLMs through prompts, context, tools, examples, memory, and instructions."

Claude Code embodies Software 3.0: "you describe what you want and Claude figures out how to build it. Claude explores, plans, and implements." [2]

Karpathy's CLAUDE.md. January 2026 — Karpathy posted observations on X after weeks of intensive Claude Code use; the resulting CLAUDE.md template hit GitHub trending #1 for 28 consecutive days, 110K+ stars. [17] Key principles:

  • Anti-drift checkpoints.
  • Explicit verification before claims.
  • Tool-discipline (use the right tool for the job).
  • Write code that handles edge cases from line 1.

Karpathy's LLM-Wiki. Compounding markdown wiki maintained by LLM, where each new ingestion enriches existing entries rather than appending throwaway summaries [18]. PRISM directly adopted this — see H:/prism/WIKI_SCHEMA.md and the 722-entry wiki at H:/prism/knowledge/wiki/.

Boris citing Karpathy. [no direct quote found, inference from observed behavior] — Boris's CLAUDE.md back-flow practice and his "give Claude verification" tip both echo Karpathy's "tight feedback loops shrink the slop." Anthropic's Best Practices doc explicitly cites Karpathy-style anti-drift advice in its "Avoid common failure patterns" section.

The convergence: PRISM sits at the intersection — wiki-as-compounding-knowledge (Karpathy) + verification-feedback-as-#1-lever (Boris) + 3-of-3 multi-CLI consensus (PRISM-specific evolution).

PRISM today.

  • /karpathy skill auto-fires anti-drift checkpoints.
  • Wiki at 722 entries with wiki/index.md + wiki/log.md audit trail.
  • Doctrine §1 explicitly maps the Karpathy Loop Scale 1 (MICRO, every 5 tasks) to existing skills.

Gap. None significant — this is the area where PRISM is MOST aligned with the source material. Continue compounding the wiki.

#13. Cross-Cutting Themes

  1. Compress feedback latency at every layer. Boris's "verification 2-3x quality," Anthropic's "small-sample testing detects 30-80% gains early," Karpathy's "anti-drift every 5 tasks" — all the same shape. Whatever the loop is, make it shorter.
  2. Isolate context aggressively. Subagents in their own context window, worktrees in their own filesystem, scheduled tasks in their own session — every layer of Claude Code is structured around "don't pollute the main thing." PRISM's per-chat handoff system embodies this at the session layer.
  3. Deterministic guardrails > advisory rules. Anthropic explicitly distinguishes hooks (deterministic, must-happen) from CLAUDE.md (advisory, may-be-ignored). PRISM's 25+ HARD BLOCK hooks are aligned; the warning hooks (we have ~80) are the soft layer.
  4. Plan as memory. When Anthropic's lead-researcher saves the plan to memory because context might truncate, that's the same insight as PRISM saving handoffs at compaction. The plan IS the durable artifact; the conversation is ephemeral.
  5. Cost-aware orchestration. 15× cost for 90% lift only makes sense for breadth-first / open-ended work. The discipline is knowing when NOT to spawn parallel subagents — for "rename this variable," a single Claude call is correct. PRISM lacks an explicit cost-model layer for this triage.

#15. Anti-Patterns Boris/Anthropic Warn Against

From Best Practices for Claude Code §"Avoid common failure patterns" [2]:

Anti-patternSymptomFix
Kitchen sink sessionStarted with task A, drifted to B, back to A — context full of irrelevant info/clear between unrelated tasks
Correcting over and overClaude fails, you correct, fails again — context polluted with failed approachesAfter 2 failed corrections, /clear and rewrite a better initial prompt incorporating learnings
Over-specified CLAUDE.mdLong file → important rules get lost in noise → Claude ignores themRuthlessly prune. If Claude already does it correctly without instruction, delete it or convert to a hook
Trust-then-verify gapPlausible-looking implementation that doesn't handle edge casesAlways provide verification (tests, scripts, screenshots). If you can't verify, don't ship
Infinite exploration"Investigate this" without scope → reads hundreds of files → context fullScope investigations narrowly OR use subagents (separate context window)

  • Don't share main tree across parallel agents — use worktrees. [3]
  • Don't bake domain knowledge into CLAUDE.md if it's only sometimes relevant — use skills. [2]
