#Karpathy Methodology — Research Card

Compact, source-grounded extract of Andrej Karpathy's published methodology for AI-assisted development. Each section captures: source, verbatim quote, implementation sketch, anti-pattern, and how PRISM aligns or deviates.

Scope note. Karpathy publishes in three surfaces: (a) the original "Software 2.0" Medium essay (2017), (b) X/Twitter threads (2023-2026 — LLM-OS, context engineering, vibe coding, LLM-Wiki), (c) talks (Stanford CS25, YC AI Startup School "Software 3.0", various interviews). The most recent material (Apr-May 2026) is largely the LLM-Wiki gist + agentic-engineering reframe of vibe coding.

#§1 — LLM-Wiki Pattern

Sources:

  • Karpathy original gist: https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f
  • Defileo's amplification thread (cited by PRISM WIKI_SCHEMA.md as the canonical pointer)
  • MindStudio walkthrough: https://www.mindstudio.ai/blog/karpathy-llm-wiki-knowledge-base-pattern
  • Level Up Coding "Beyond RAG" essay (Apr 2026)

Verbatim quotes (from gist):

"The wiki is a persistent, compounding artifact." (paraphrase summary of gist's core thesis — the gist itself avoids slogans)

"Everything mentioned above is optional and modular — pick what's useful, ignore what isn't."

"The tedious part of maintaining a knowledge base is not the reading or the thinking — it's the bookkeeping."

"Your wiki might be small enough that the index file is all you need, no search engine required."

Three-layer architecture (verbatim from gist structure):

  1. Raw sources — immutable. The LLM reads but never modifies. Articles, papers, transcripts, PDFs.
  2. The wiki — LLM-generated, interlinked markdown. One concept per file. Cross-references via [[wikilinks]]. Provenance/citations on every page.
  3. The schema — CLAUDE.md (or AGENTS.md for Codex). The configuration document that makes the LLM "a disciplined wiki maintainer rather than a generic chatbot."

Three operations:

  • Ingest — drop a source; LLM reads it, writes a summary page, updates index.md, and touches 10-15 existing pages in one pass to add cross-refs.
  • Query — ask questions against wiki pages (NOT raw sources). Synthesize with citations. Optionally file the answer back as a new page — this is the "compounding" step.
  • Lint — periodic health check for contradictions, stale claims, orphan pages, missing cross-refs.

Two index files (load-bearing convention):

  • index.md — content-oriented catalog with one-line summaries per page.
  • log.md — append-only chronological audit trail, grep-friendly prefix.

File conventions Karpathy actually specifies (sparse on purpose):

  • Plain .md files (no DB, no embedding store required at small scale)
  • Lowercase, hyphenated filenames
  • Maximum one folder level deep at small scale
  • Cross-links via [[page-name]] wikilink style
  • Every page should be cite-traceable to a raw source

What he explicitly skips / leaves to the implementer:

  • No prescribed page template
  • No prescribed directory taxonomy beyond "one concept per file"
  • No mandate on wikilinks vs markdown links — pick one and stay consistent
  • No prescription of vector search (cat wiki/*.md | llm is the simplest baseline)

When to query vs write:

  • Query when the question is one-off OR when no synthesis emerged that beat existing pages.
  • Write when (a) the synthesis answers a recurring class of question, (b) it resolves a contradiction, (c) it links 2+ previously-disconnected concepts.

Anti-patterns (warned against, explicit + implied):

  • Re-deriving the same answer N times (RAG-only mode)
  • Dumping raw sources into the wiki layer (violates the immutability of layer 1)
  • Schema-creep: changing the conventions silently — schema must be edited FIRST, then wiki
  • Treating the wiki as ephemeral chat output (it is the durable artifact)
  • Embedding-only retrieval without a written schema — produces inconsistent pages

Implementation sketch (PRISM-equivalent):

# Ingest
prism_wiki:ingest --source raw/articles/foo.md
  → Ollama summarize (200-500 words)
  → Ollama suggest cross-refs against index.md
  → Claude resolve contradictions / synthesize
  → WikiIndexMaintainer + WikiLogAppender file the page

# Query
prism_wiki:query "How does Kienzle constant relate to chip thinning?"
  → HNSW similarity over wiki/index.md (Ollama embed, free)
  → Read top 1-3 wiki pages
  → Claude synthesize with citations
  → Optional file-back to wiki/decisions/

# Lint
prism_wiki:lint --severity major
  → orphan pages, broken cross-refs, stale claims, contradictions
  → emit lint-reports/YYYY-MM-DD.md

PRISM alignment (HIGH):

  • H:/prism/knowledge/wiki/ exists with all 3 layers (sources/wiki/schema)
  • WIKI_SCHEMA.md codifies the three operations and 5-stage ingest pipeline (≥70% Ollama by token cost)
  • index.md (722 entries) + log.md (chronological audit trail) — both in place
  • 11 subdirectories (concepts, entities, decisions, patterns, trajectories, summaries, code-tribal, architecture, software-engineering, ux-design, lessons) — exceeds Karpathy's "one folder deep" guidance but stays semantic, not file-system rigid
  • Skills /wiki-ingest /wiki-query /wiki-lint /wiki-morning /wiki-bootstrap operationalize the three ops
  • Multi-chat coordination via prism_context:claim_file — extension Karpathy's single-user gist doesn't address

PRISM deviations (intentional):

  • 11 subdirectories vs Karpathy's "max 1 level deep" — justified by 575+ engines + 90 dispatchers needing semantic separation
  • Frontmatter spec (yaml: title, category, sources, confidence, last_verified) — Karpathy leaves this to implementer; PRISM hardened it
  • Severity scale (MINOR/MAJOR/CRITICAL/BROKEN) for lint — PRISM-specific, useful for multi-agent triage

Gap to close:

  • Karpathy's cat wiki/*.md baseline doesn't exist as a one-shot in PRISM (worth adding prism_wiki:dump_all for when context budget allows)

#§2 — Anti-Drift Checkpoint

Sources:

  • Karpathy YC AI Startup School talk ("Software 3.0", June 2025): https://www.donnamagi.com/articles/karpathy-yc-talk
  • Karpathy CLAUDE.md guidelines repo (Apr 2026): https://github.com/forrestchang/andrej-karpathy-skills

Verbatim quotes:

"The AI is kept on a leash with respect to a certain syllabus, a certain progression of projects, and so on."

"We have to keep the AI in a leash. You have to make sure that this thing is not introducing bugs."

"Less Iron Man robots, and more Iron Man suits — building partial autonomy products."

Cadence — the explicit "every N tasks" check: Karpathy does NOT publish a hardcoded N. The "every 5 tasks" cadence in PRISM's CLAUDE.md is a PRISM extension, not a Karpathy verbatim. What he prescribes is a structural mechanism (the "leash") and a question-set (below) — frequency is left to the operator.

The reset questions (derived from the four CLAUDE.md rules + leash framing):

  1. Am I still on the user's stated goal, or did I wander into adjacent improvements?
  2. Did I make any silent assumptions that should have been surfaced as questions?
  3. Is this the simplest solution, or am I building speculative flexibility?
  4. Did I touch code outside the request's scope (refactors, formatting, "while I'm in here" cleanup)?
  5. Have I defined a verifiable success criterion, or am I "looping on vibes"?

Triggers for a reset (Karpathy's framing):

  • Demo-vs-product gap widens — "Demo is works.any(), product is works.all()."
  • Verification step is being skipped under time pressure.
  • Agent is making decisions without surfacing alternatives.

Implementation sketch:

# Mental checkpoint — every ~5 tool calls or before any commit:
[ ] On goal? (re-read user's first prompt)
[ ] Surfaced assumptions, or silently chose interpretation?
[ ] Simplest path, or speculative abstractions?
[ ] In-scope edits only, or "while I'm in here" creep?
[ ] Success criterion verifiable, or just "looks good"?

# Hook-enforced (PRISM extension):
- karpathy-checkpoint hook fires on every Stop event
- Counts tool calls per session; injects checkpoint reminder at multiples of N
- Cross-references commit footprint against original prompt scope

Anti-pattern (explicit):

"Don't assume. Don't hide confusion. Surface tradeoffs."

Silent assumptions, picking one interpretation without surfacing alternatives, guessing instead of clarifying — these are the failure modes that compound into drift.

PRISM alignment (HIGH):

  • CLAUDE.md global already has "Anti-drift checkpoint (every ~5 tasks)" with the 4-question list
  • Stop hook scrutinize-before-stop.mjs enforces a 3-of-3 multi-CLI consensus before allowing task completion (deeper than Karpathy's manual checkpoint)
  • Per-chat handoff discipline (one HANDOFF per chat, topic-suffixed) is a PRISM extension that addresses the "leash" mechanism in a multi-agent setting Karpathy's gist doesn't cover

PRISM deviations (intentional):

  • PRISM hardens the cadence to "every ~5 tasks" — Karpathy leaves frequency open
  • PRISM adds the 3-of-3 multi-CLI consensus (Codex + Gemini + Opus) for Stop-time verification — Karpathy's "leash" is conceptual, PRISM's is a HARD BLOCK
  • PRISM extends the checklist to multi-chat coordination (lane discipline, conflict-fork rule)

Gap to close:

  • No automated "drift score" — could be derived from (commit-touched-files ⊖ first-prompt-keywords) symmetric difference

#§3 — Micro-Loops + Classify-Before-Coding

Sources:

  • Karpathy CLAUDE.md guidelines: https://github.com/forrestchang/andrej-karpathy-skills/blob/main/skills/karpathy-guidelines/SKILL.md
  • Luca Berton's Apr 2026 unpacking: https://lucaberton.com/blog/karpathy-claude-md-llm-coding-principles-2026/
  • The Menon Lab: https://themenonlab.blog/blog/karpathy-claude-md-four-rules-ai-coding-agents

Verbatim quotes (the four rules, exact framing):

Rule 1 — Think Before Coding:

"Don't assume. Don't hide confusion. Surface tradeoffs."

"If something is ambiguous, ask. Do not pick one interpretation and run."

Rule 2 — Simplicity First:

"Minimum code that solves the problem. Nothing speculative."

Rule 3 — Surgical Changes:

"Touch only what you must. Clean up only your own mess."

"Every changed line should trace directly to the user's request."

Rule 4 — Goal-Driven Execution:

"Define success criteria. Loop until verified."

The pre-write checklist (synthesis from Rules 1+2):

  • State assumptions explicitly; ask if uncertain.
  • Present multiple interpretations rather than choosing silently.
  • Identify simpler approaches and advocate for them.
  • Self-check: "Would a senior engineer call this overcomplicated?"
  • Exclude features beyond the request.
  • Avoid abstractions for single-use code.
  • Skip unrequested "flexibility" or configurability.
  • Omit error handling for impossible scenarios.

The "classify problem type" framing — Karpathy doesn't use these exact words; PRISM extended: The PRISM CLAUDE.md "CLASSIFY → TECHNIQUE → EDGE CASES → FAILURE MODES → THEN WRITE" 5-step is a PRISM amplification of Rule 1 (Think Before Coding), inspired by Karpathy's broader framing in his Stanford CS231n / nn-zero-to-hero material where he repeatedly drills "first identify what kind of problem this is, then pick the technique."

Implementation sketch:

# Before any non-trivial code change:
1. CLASSIFY — search/state/async/parse/cache/validate/transform?
2. TECHNIQUE — hash vs tree? FSM vs reducer? promise.all vs sequential?
3. EDGE CASES — empty, null, overflow, concurrent, NaN, unicode, timeout
4. FAILURE MODES — network, disk, OOM, race condition, invalid state
5. THEN WRITE — code handles ALL above from line 1

# Surgical-changes test (Rule 3):
git diff --stat | awk '{ if ($2 > N) flag }'
# If touched-line count > expected, audit for scope creep.

# Goal-driven success criterion (Rule 4):
- "Done" must be a verifiable check, not "looks good"
- Test must exist BEFORE implementation when feasible

Anti-patterns (explicit):

  • Silent assumption-picking (violates Rule 1)
  • Speculative abstractions ("we might need this later") (violates Rule 2)
  • "While I'm in here" refactors of working code (violates Rule 3)
  • Refactoring unbroken code (violates Rule 3)
  • Vague task definitions like "make it work" (violates Rule 4)
  • Skipping verification steps under time pressure (violates Rule 4)

Karpathy's behavioral framing (key insight):

"These aren't intelligence problems — they're behavioral defaults that structured instructions override."

The four rules work because LLMs default to helpful-overreach (suggest more, refactor more, abstract more). The CLAUDE.md inverts the defaults toward minimum-viable-change.

PRISM alignment (HIGH):

  • CLAUDE.md global has the explicit 5-step CLASSIFY→TECHNIQUE→EDGE CASES→FAILURE MODES→THEN WRITE
  • simplify skill enforces Rule 2 post-hoc on any changed code
  • superpowers:verification-before-completion skill enforces Rule 4
  • Stop hook comprehensive-build-enforce.mjs blocks stub/partial work (extends Rule 4)

PRISM deviations (intentional):

  • PRISM adds the EXHAUSTIVE classify list (search/state/async/parse/cache/validate/transform) — Karpathy stays general
  • PRISM adds the EDGE CASES enumeration (empty/null/overflow/concurrent/NaN/unicode/timeout) — Karpathy implies via Rule 1
  • PRISM enforces Rule 4 with HARD BLOCKS — Karpathy leaves it to discipline

Gap to close:

  • Could add a karpathy-rule-check slash command that runs all 4 rules against a proposed diff before commit
  • Surgical-changes diff-vs-prompt distance metric not currently computed

#§4 — Software 2.0 Implications

Sources:

  • Original essay (2017): https://karpathy.medium.com/software-2-0-a64152b37c35
  • Software 3.0 reframe (2025-2026): https://www.latent.space/p/s3
  • Context window as RAM (2026): https://www.mindstudio.ai/blog/software-3-0-explained-karpathy-context-window-ram-model-weights-cpu

Verbatim quotes:

"Software 1.0 is the code you write on the computer. Software 2.0 are basically neural networks."

"In the 2.0 stack, the programming is done by accumulating, massaging and cleaning datasets."

"When the network fails in some hard or rare cases, we do not fix those predictions by writing code, but by including more labeled examples of those cases."

"Neural networks became programmable with large libraries. It's a new kind of computer. Software 3.0."

"Your products are now programs that program people all over. Remarkably, these products are written in English."

"Modules can meld into an optimal whole. If two Software 2.0 modules that were originally trained separately interact, we can easily backpropagate through the whole."

Implications for development workflow:

Surface1.0 (code)2.0 (data)3.0 (English prompts + agents)
Programming unitfunction/classdataset + architectureprompt + tool/skill
Bug fixedit codeadd labeled examplesedit prompt or add examples
Code reviewdiff reviewdataset diff + curve diffprompt diff + eval suite diff
Testingunit/integrationheld-out eval seteval-set + verifier loop
Deploymentbinary/containerweights + runtimeprompt + tool registry + memory

Implications for code review:

  • 1.0: line-by-line readability + correctness review
  • 2.0: dataset audit (labeling quality, coverage of edge cases, bias)
  • 3.0: prompt change diff + eval-suite delta + agent trajectory replay
  • The reviewer's job shifts from "does this code do what it says" to "does this dataset/prompt produce the desired distribution of outputs"

Implications for testing:

  • 2.0 tests are statistical — accuracy, F1, coverage on a held-out distribution
  • 3.0 tests are eval-suites — task batteries with verifiable success criteria + agent-trace inspection
  • Both replace a portion of unit testing with distribution testing
  • Karpathy's "verifier loop" is the 3.0 analog of a CI pipeline — agents propose, verifier (often deterministic code OR an LLM judge) accepts/rejects

The IDE prediction (Karpathy 2017):

"Who is going to develop the first Software 2.0 IDEs, which help with all of the workflows in accumulating, visualizing, cleaning, labeling, and sourcing datasets?"

"Perhaps the IDE bubbles up images that the network suspects are mislabeled based on the per-example loss, or assists in labeling by seeding labels with predictions, or suggests useful examples to label based on the uncertainty of the network's predictions."

(This prediction is now realized as MLOps tooling — Weights & Biases, Snorkel, Encord. The 3.0 analog is in-progress: Claude Code, Cursor, Devin = Software 3.0 IDEs.)

Implementation sketch (PRISM-equivalent):

# 2.0 surface in PRISM:
- LoRA training pipeline (mill-lora, lathe-lora)
- Material database (data pipeline, not code pipeline)
- CrossDisciplinaryDeepLearningEngine (NN architecture as code)

# 3.0 surface in PRISM:
- ~440 skills = English-language prompts as "programs"
- ~60 dispatchers + ~7244 actions = the tool/skill registry
- Per-chat handoffs + wiki = persistent memory
- 3-of-3 multi-CLI verifier loop = the verification gate

Anti-pattern (explicit + implied):

  • Treating 2.0/3.0 components as "magic" — "The 2.0 stack also has some of its own disadvantages... The networks are large and difficult to interpret."
  • Dumping raw 1.0 code review practices on 3.0 prompt changes — line-diff is insufficient; need eval-suite delta
  • Assuming agent autonomy is binary — Karpathy's "autonomy slider" is the correct framing (see §5)

PRISM alignment (MEDIUM-HIGH):

  • PRISM is fundamentally a 3.0 application (skills + dispatchers + agents + wiki memory)
  • 2.0 modules (LoRA, embeddings, NN engines) are first-class
  • Verifier loop is 3-of-3 multi-CLI consensus

PRISM gaps:

  • No formal eval-suite for skill-prompt regressions (skills can drift silently if their internal phrasing changes)
  • No "labeled example" pipeline for skill-output failures (would benefit from feedback loop: agent failures → labeled-example file → next-iteration training data)
  • 2.0/3.0 boundary is not explicitly modeled in dispatcher metadata

5.1 — Context Engineering (the rename of prompt engineering)

Verbatim quote:

"+1 for 'context engineering' over 'prompt engineering'. People associate prompts with short task descriptions you'd give an LLM in your day-to-day use. When in every industrial-strength LLM app, context engineering is the delicate art and science of filling the context window."

Implementation:

  • Context engineering = selecting, compressing, ordering, isolating, formatting what the agent sees at each step
  • "Most AI failures are context failures, not model failures"
  • The context window is the LLM's RAM — "dumping your entire hard drive into RAM and expecting the CPU to find one specific byte results in thrashing and context-flooding, not reasoning"

Anti-pattern:

  • Treating prompt engineering as one-line incantations
  • Dumping all available context "just in case"
  • No isolation between subtasks — context bleed between unrelated work

PRISM alignment: HIGH — CLAUDE.md token-economy section + per-chat handoff discipline + load-on-demand skills are direct implementations.

5.2 — Vibe Coding → Agentic Engineering

Verbatim quotes:

"There should be an autonomy slider in your product. Make your product sort of more autonomous over time."

"It's both an augmentation, and twin-star mechanic driver. And it's also an agent."

"Less Iron Man robots, and more Iron Man suits — building partial autonomy products."

"Demo is works.any(), product is works.all()."

The reframe (May 2026):

  • 2025 "vibe coding" = describe-and-receive working software
  • 2026 "agentic engineering" = humans direct, supervise, orchestrate agents instead of writing code
  • The shift: developer role → editor / reviewer / system designer

Verification framing:

"Traditional software automates what can be precisely specified, while language models automate what can be verified."

Partial autonomy applications need a GUI that makes verification easier — the gap between demo and production is the verification gap.

Anti-patterns:

  • Pure vibe coding past prototype stage — leads to demo-only software
  • Maximum-autonomy agents without verification gates
  • Skipping the editor/reviewer role — "the developer who does not understand the system's failure modes cannot specify them, and the agent cannot surface what the developer did not know to require"

PRISM alignment: HIGH — PRISM has dispatcher actions + skill manifests + multi-CLI Stop-gate that operationalize the autonomy slider + verifier loop.

5.3 — Parallel Agent Work

Sourced quote (paraphrased from coverage; verbatim source not located in time window):

"You're not running enough agents in parallel. Finishing one agent task and then starting the next means working serially in a parallel world. The operators who win are learning to parallelize their judgment, not just their code."

Implementation:

  • Run multiple agents on independent subtasks in parallel
  • Verifier-gated merge — each agent's output goes through the verification step before integrating
  • The bottleneck moves from "writing code" to "judging output quality"

Anti-patterns:

  • Serial agent execution (one task at a time)
  • Merging agent output without verification
  • Treating agent runs as fire-and-forget

PRISM alignment: HIGH — 6 concurrent chats + per-chat handoff + lane discipline + conflict-fork rule + worktree-per-milestone is exactly this pattern.

5.4 — Context Window as RAM (LLM-OS extension)

Original LLM-OS quote (Sep 2023):

"LLMs not as a chatbot, but the kernel process of a new Operating System. E.g. today it orchestrates: Input & Output across modalities (text, audio, vision), Code interpreter, ability to write & run programs, browser/internet access, embeddings database for files and internal memory."

Refined 2026 framing:

  • LLM = CPU
  • Context window = RAM (small, fast, expensive)
  • Wiki / vector store = disk (large, slow, cheap)
  • Skills / dispatchers / tools = system calls
  • Agent loop = scheduler

Implementation insight:

  • Context-cache (5-min Anthropic cache) is the L1
  • Wiki summaries are the L2
  • Raw sources are L3 (only loaded on cache-miss)

PRISM alignment: HIGH — aiSystemRouterEngine + Ollama offload + RTK output filtering + load-on-demand skills + wiki layer = direct LLM-OS implementation.

Net assessment: PRISM is one of the most complete operational implementations of Karpathy's published methodology. The deviations are intentional hardenings for multi-agent, manufacturing-domain, and production-grade use. The remaining gaps are:

  1. Eval-suite for skill-prompt regressions — no automated detection if a skill's internal phrasing drifts
  2. Labeled-example pipeline — agent failures should auto-file as labeled examples for next-iteration improvement
  3. Drift-score metric — symmetric difference between commit-touched-files and first-prompt-keywords could be computed automatically
  4. One-shot wiki dump — prism_wiki:dump_all for when context budget allows full-wiki context loading
  5. Surgical-changes diff distance — automated "every line traces to request" checker on commit
