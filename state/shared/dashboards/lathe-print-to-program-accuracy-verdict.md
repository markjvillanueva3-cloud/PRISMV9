**Honest one-liner:** *PRISM's lathe physics is structurally sound and its FEED envelope (IPR) largely contains JM's real-world band; its SFM envelope runs 4-7× hotter than JM's conservative Okuma-fleet medians; and the actual print→program reading loop is not yet measurable because the lathe adapter is a stub and the JM prints have never been OCR-scored.*

### Critical caveat on the JM SFM numbers (R12 — do not over-tune)
The JM `sfm` percentiles are **G97-implied-from-diameter, not commanded surface speed**. 96.9% of programs are G97 constant-RPM (775/800); under G97 the implied SFM = π·D·RPM/12 scales with diameter, so rough passes (large OD) report higher implied SFM than finish passes (small OD) at the *same* RPM. This is why the harness shows the physically backwards "rough 250 SFM > finish 150 SFM" — it is a diameter-mix artifact, **not** a JM speed strategy. The drill `sfm` p50 of 10.5 (n=64) is the same artifact at tiny D and is **unusable**. **Calibrate against the programmed `g96sfm` literals (recurring 150/250 steel motif), NOT the implied `sfm` aggregate.** The feed band (IPR, feed-per-rev) IS diameter-invariant and trustworthy — that is why the feed verdicts are firm and the SFM verdicts are hedged.

## 4. NEXT-RUNG ROADMAP (logical/dependency order — R13)

The true loop is severed at the adapter stub. Build the verifiable core BEFORE its consumers. Steps are strictly dependency-ordered.

### (a) Wire the lathe generator adapter — the stub
**Stub:** `mcp-server/src/engines/PipelineHarnessAdaptersEngine.ts:222-226` (`makeAdapterFor` lathe branch) + `:236` (`isBound`). Contract already exists and is real: `DomainWizardPipelineTestEngine.ts:173-183` — `LATHE_CONTRACT`, 6 required stages (`cad_parse → feature_recognize → strategy_select → toolpath_synthesize → post_emit → gcode_validate`), 5000ms budget, `tool_id` handoff from `strategy_select → post_emit`.

The 6 lathe stage engines **exist as singletons** but are **never chained** (no `runFullPipeline` exists across `Lathe*.ts` — confirmed empty grep): `LathePrintIngestPipelineEngine.ingest()` → `LathePrintSequencePlannerEngine` → `LathePrintFeatureStrategySelectorEngine` → `LathePrintToolpathGeneratorEngine` → `LathePrintProgramEmitterEngine.emit()` → `LathePrintProgramSignoffEngine`.

**Therefore — correct build order (R13 — verifiable core first):**
1. **Build `LathePrintToProgramPipelineEngine.runFullPipeline()`** — the missing orchestrator that chains the 6 existing engines and threads the `tool_id` handoff. (Mirror `MillingPrintToProgramEngine.runFullPipeline()`.)
2. **Then build `makeLatheAdapter()`** in `PipelineHarnessAdaptersEngine.ts` wrapping that pipeline, mapping its output to the 6 `LATHE_CONTRACT` `StageOutput[]` stages; flip `isBound("lathe") → true`.

### (b) Connect print-reading → generator → Okuma post → diff-vs-existing harness
3. **Add a `lathe`/`turning` branch to `buildVisionPrompt`** (`ollama-vision-extract-lib.mjs:69`, parallel to the `wireEdm` branch at `:117`): diameters as features-of-revolution, OD/ID disambiguation, grooves/undercuts, OD-vs-ID threads (pitch/TPI), face-vs-turn lengths, chamfers, stock bar Ø, datum-on-axis. *Without this the reader cannot emit turning features.*
4. **Build a lathe synthetic generator** — turned-profile analog of `synthetic-print-gen.py` (half-profile of revolution with Ø callouts, grooves, threads) so the closed loop measures *lathe* reading, not plate reading. This converts the existing "100%" harness into a meaningful lathe ceiling number.
5. **Run the real-print harness** — feed the **4,173** paired rows (`blueprint-training-pairs.jsonl`, `has_program:true`) through reader → `runFullPipeline` → Okuma post, and score against the paired program + operator truth (`GroundTruthValidationEngine.validateExtractionBackend`). Emit real outcomes into the empty `blueprint-accuracy-state.json` window via the `blueprint-accuracy-guard` → `blueprint-accuracy-consumer.mjs` path.

### (c) What a real roundtrip accuracy metric looks like (NOT byte-match)
A G-code byte diff is worthless (tool numbers, comment text, block order, decimal formatting all vary legitimately). The real metric is a **two-layer structural+semantic diff** of PRISM-generated vs JM-existing program:

- **Structural layer** — parse both into a canonical op-graph (op type, feature, tool class, sequence) and score graph alignment: did PRISM recover the same operations in a valid order, with G50/G96/G97 modal correctness, drill cycle (G83/G73) where L/D demands it, threading G76 with G97 lock?
- **Semantic/parameter layer** — per matched op, compare the *physics quantities* (SFM, IPR, DOC, RPM, peck depth) as **% deviation within tolerance bands**, NOT equality. A pass = within the JM empirical p25-p75 envelope for that op/material (the bands this very harness produces). Aggregate to a per-dimension accuracy (feed-accuracy, speed-accuracy, safety-compliance, sequence-accuracy) and a weighted roundtrip score.
- **Dimension-recovery layer** (print→features) — extracted Ø/length/Ra/thread vs ground truth, scored as MAE (mm) + match precision/recall (the `ocr-closed-loop` shape, but on real lathe prints).

Only after (a)+(b) produce a number from real JM prints does a *true* print→lathe-program→post accuracy metric exist. Today: it does not.

## 5. SAFETY FINDINGS

### The 19 overspeed-risk programs (G96 without a G50 cap)
- **97.5% compliance** (740/759 G96 programs carry a cap) — JM's masters are disciplined; the 19 are a real 2.5% punch-list, not a systemic failure.
- Enumerated in harness `overspeed_risk_programs` (e.g. ITW UPSET2528, EJOT T120030271-STOP, MACOMB HD-014-02, FASTRON/CHERRY/MULTI-TECH HOLDER2185 series, RUMCO HAMMER HOLDER/CASE).
- **PRISM coverage of this exact failure mode = 0%.** PRISM *emits* G50 on 100% of generated programs but has **no validator that audits an ingested/generated G96 program for a missing cap.** The only overspeed gate (`HyperMillTurningHooks.ts:108-126`) is HyperMill-pathway-only, silently passes on missing inputs (`score:0.8`), and checks computed D_min overspeed — NOT "is a G50 line present." It would not catch any of the 19.
- **Fix = Punch #3** (`validateCSSCap` HARD-FAIL). This also resolves the phantom-pointer R12 defect: `mcp-server/src/engines/lathe/CLAUDE.md:99` claims `LatheAdvancedOperationsEngine.validateCSSCap()` exists — **it does not** (grep returns only the doctrine line). Until built, that doctrine asserts safety coverage PRISM lacks; mark it `(NOT YET BUILT)` or implement it.

### The 5000-RPM cap outlier
- `rpm_cap_distribution`: median 800, mean 906, p95 1500, **max 5000**. The 5000 sits 3.3× above p95 — an out-of-band cap (likely a large-bore/special-fixture part or a programming artifact), not a normal die-part cap.
- **Caught by Punch #9** (per-part computed cap): a diameter-driven cap would never emit 5000 for a normal die part, and **Punch #3's `validateCSSCap`** can flag any cap that exceeds machine-max as out-of-band on ingest. The static `css_max_rpm: 3500` default (`OkumaB250LatheMasterPostEngine.ts:239`) is itself the wrong posture — it under-protects the small-OD/parting work where CSS overspeed actually scraps parts.
