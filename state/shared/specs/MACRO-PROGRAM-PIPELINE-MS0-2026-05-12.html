#PRINCIPLE — the macro is the proven STARTING TEMPLATE, not a straitjacket (per the user, 2026-05-12: "make sure the programs utilize macros, hardcoded, controller-specific features/coding language, and whatever other toolpath would be more beneficial")

The fill/emit pipeline (U2 → U5) MUST:

  1. Utilize the macros. The matched macro's operation sequence, tool numbering (T010101..T101010), VC-var layout, and Okuma canned-cycle structure are the proven baseline — start there. Don't ignore the macro and freehand a program.
  2. Use controller-NATIVE features + dialect. Emit in the target machine's G-code dialect using that controller's actual canned cycles and special features — Okuma OSP (G85/G86/G87 profile cycles, G74 peck, VC1xx user vars, CALL/subprograms, G50 max-RPM, G96/G97 CSS, G41/G42, IF/GOTO); Fanuc/Fanuc-like (G70/G71/G72/G73 cycles, #-macro vars, M98/M99 subprograms, G96/G97, G50/G92 spindle clamp); Mazak (EIA or MAZATROL conversational, MAZAK cycles); Siemens 840D-style (CYCLE* calls, R-parameters). NEVER emit a lowest-common-denominator program — if the target controller has a profile-roughing cycle, use it; if it has a probing macro, use it.
  3. Emit parametric OR hardcoded — whichever is more beneficial for THAT machine/controller/part. Both are valid outputs:
    • Parametric (the macro's VC/#-variable form, IF/GOTO intact, calculated vars left as expressions) — best when the controller can hold it, the part family will recur (so the operator can re-run with new dims), and the macro overhead is negligible.
    • Hardcoded / flat (resolved variables, expanded IF/GOTO against the actual feature set, calculated vars evaluated) — best when the controller can't hold the parametric form (the known Okuma P300L/P300LA program-memory + char-count limit on 60+-var / 500+-line parametric programs — memory project_okuma_controller_limits), or the part is one-off, or the operator prefers a flat program, or the macro's conditionals all collapse to one branch anyway. MacroProgramIntelligenceEngine has the AST + var map and can do the expansion.
    The pipeline picks per a benefit heuristic (controller memory headroom, recurrence likelihood, program complexity, operator preference, cycle-time impact) and states which form it chose + why in the program header.
  4. Substitute a more-beneficial toolpath/strategy where the part warrants it. The macro's fixed toolpath is the default, not a lock. The /lathe strategy engines (LatheMultiOpPlannerEngine, TurningStrategyCatalog, LatheSequenceOptimizerEngine, LatheAdaptiveMachiningEngine, LathePartingChipClearanceEngine, the optimizers, LatheOnMachineProbeCycleEngine) may swap in a better approach — a different roughing strategy, a different tool sequence, trochoidal grooving, an in-process probe cycle, a different cutoff/parting strategy, a chip-breaking peck pattern — when it measurably improves cycle time / tool life / surface finish / process robustness for this part. **Any deviation from the macro's baseline structure must be (a) justified in the program header, (b) re-validated by the safety gate (U4) against the actual emitted toolpath — the S(x) gate scores the emitted program, not the macro template.**

All of the above is still gated: S(x) ≥ 0.70 + envelope + sim/back-plot + operator sign-off on the final emitted program (parametric or hardcoded, native dialect, with whatever toolpath was chosen). Operator-in-the-loop is unconditional. NEVER bulk-auto-emit.

#MS0-U1 — MacroLibraryEngine + non-safety-critical macro fan-out (can ship first, independently)

What: a thin engine that (a) catalogs the 4 OSP macros in JM DIE/Macro programs/ — name, family, parsed VC variable map (parse via MacroProgramIntelligenceEngine.parseMacro()), program no., controller; (b) matchFamily(part) → wafer-insert / casing / casing+counterbore / top-hat-casing / null — uses LathePartClassifierEngine + LathePartFamilyPlanningEngine + the print features (OD profile shape, has-ID-bore?, has-counterbore?, has-brim/flange?); (c) placeMacroTemplate(part, family) → copies the matching macro file into _PART LIBRARY/<customer>/<pn>/CNC PROGRAM/_MACRO-TEMPLATE_<macro-name> with a prepended header comment: (TEMPLATE — macro-derived from <macro>, family <family>, matched <date>, confidence <c>. This is just file-copying labelled reference templates — non-safety-critical. It does NOT fill any VC var, does NOT emit runnable G-code. Reuse: MacroProgramIntelligenceEngine (parse), LathePartClassifierEngine + LathePartFamilyPlanningEngine (family match), PartFolderOrganizerEngine (part-folder layout + part.json I/O), part-library-layout.json (the layout config). Do NOT create a new "macro parser" or "part classifier" — compose these. Wire: prism_cad (sits with create_part_folder — it's part-library scaffolding) AND prism_turning (it's lathe-domain): actions macro_library_list / macro_match_family / macro_place_template / macro_fanout_dry_run. #MS0-U2 — MacroFillOrchestratorEngine (thin) — fill the VC vars from print dims (SAFETY-CRITICAL)

What: a thin orchestrator: given a part (print path / part# / extracted features) + a family + a target machine → (1) extract the print dims → the VC var values (stock dia, finish OD/ID, part length, taper end dia + start Z, OD chamfer/radius size+type+angle, drill dia/SFM/feed/point-angle/peck, clearance planes, ID major dia + taper angle in Okuma 270-format, …); calculated VC vars (RPMs, point depths, total depths) are LEFT as the macro's own expressions — never pre-computed; (2) call OkumaParametricProgramEngine.generate* (extend with generateWaferInsert / generateTopHatCasing from U3) with the filled config; (3) MacroProgramIntelligenceEngine + OkumaMacroHeaderGeneratorEngine validate the macro structure + the filled header (no out-of-range var, no missing required var, the IF/GOTO flow is intact); (4) hand the candidate to U4 (the gate). Output = a candidate program object, NOT a file. Reuse: OkumaParametricProgramEngine (the generator — already wired to prism_cam), MacroProgramIntelligenceEngine (AST validate), OkumaMacroHeaderGeneratorEngine (header), PPMacroFlowValidatorEngine + PPMacroVariableValidatorEngine (flow + var validators — already exist), the lathe print-intake engines (LathePrintIngestPipelineEngine / TurningPrintIntakeEngine / LathePrintToleranceStackEngine) for the dim extraction. Do NOT re-implement the OSP code emitter or the print parser. Wire: prism_turning + prism_cam (it composes the existing prism_cam.okuma_* actions): action macro_fill_candidate (returns the candidate + the filled var table + which dim came from where). Schema + switch + zod in both. Tests: MacroFillOrchestratorEngine.test.ts — fill happy (a known wafer-insert print → the right VC100..VC144; reference values from the macro's own example header) + ≥3 negatives (a dim missing from the print → flags it, does NOT guess; a dim out of the macro's valid range → rejects with the range; a part whose family doesn't match the requested macro → refuses) + ≥2 adversarial (a print with two candidate stock dias → asks, doesn't pick; an OCR'd dim that's physically impossible — negative length, ID > OD — → rejects as material-insanity), candidate structure (calculated VC vars are still expressions, not numbers; the header is well-formed; IF/GOTO targets all exist), + dispatcher round-trip (macro_fill_candidate through prism_turning + prism_cam). HARD RULE in the test file: expect(candidate.calculatedVars.VC130).toMatch(/VC111.*VC110/) (i.e. it's still the expression [VC111 * 3.82] / VC110, not a pre-computed RPM) — if the orchestrator ever pre-computes a calculated var, the test fails.

#MS0-U4 — The safety gate around the candidate (S(x) ≥ 0.70 + envelope + sim + operator) (SAFETY-CRITICAL — the load-bearing unit)

On PASS → produce the SafetyRecord (the proof) attached to the candidate. On FAIL → return the failing checks + what must change; emit NOTHING. Then LatheReplayFrameCompilerEngine → back-plot frames for the operator. Then LatheProgramSignoffDossierEngine + LathePrintProgramSignoffEngine + LatheFirstPieceApprovalEngine → the dossier (setup sheet + physics report + S(x) certificate + first-piece checklist) with needsOperatorReview: true. The program is NOT "done" until an operator signs the dossier. Reuse: LatheProofCarryingEmitEngine, LathePrintProgramEmitterEngine (envelope-aware emit), prism_safety:validate_physics, CollisionPreventionEngine, machineLimitGuard, LatheReplayFrameCompilerEngine, LatheProgramSignoffDossierEngine, LathePrintProgramSignoffEngine, LatheFirstPieceApprovalEngine, the SafetyHooks. This unit is almost entirely wiring — the gate engines exist; this just composes them around a macro-derived candidate and threads the proof through. Wire: prism_turning + prism_safety: action macro_gate_candidate (candidate + target machine → {passed, sxScore, safetyRecord, failingChecks, dossier}). Schema + switch + zod. Tests: macro_gate_candidate round-trip — a known-good candidate → passed: true, sxScore >= 0.70, a safetyRecord with a valid GateSignature, a dossier with needsOperatorReview: true; a candidate with a deliberately-out-of-envelope feature → passed: false, the machineLimitGuard failure named, dossier null, NOTHING emitted; a candidate with a physically-insane param (negative DOC) → passed: false, materialSanity failure; an S(x) = 0.69 candidate → passed: false (the HARD BLOCK actually blocks — no off-by-one at the threshold). HARD RULE in the test file: there is NO code path where macro_gate_candidate returns an emitted program file with passed: false or sxScore < 0.70 — assert it directly.

#MS0-U5 — Per-machine post-resolution + labelled .MIN emit

What: given a gated candidate → ShopConfigurationEngine enumerate the lathe-capable JM machines (21 machines; filter by: turning-capable, swing ≥ part dia, between-centers ≥ part length, turret stations ≥ tools used, sub-spindle if needed, bar feeder if bar stock) → for each fitting machine: re-resolve the post (the macro is Okuma OSP VC-variable — if the target machine is an Okuma model, keep OSP but tune the G-codes/cycles to that model's OSP variant + apply its G50 max-RPM + travel limits; if the target machine is a Fanuc/Mazak/etc. lathe, translate the OSP macro to that controller's dialect via PostProcessorPipelineEngine → LathePostProcessorEngine + LathePostProcessorDialectValidatorEngine) → memory/character-limit check — known constraint: some Okuma OSP controllers (e.g. P300L / P300LA) have a program-memory + character-count ceiling that cannot hold a large parametric macro (60+ VC vars + IF/GOTO branching + 500+ lines) — see memory project_okuma_controller_limits. So per machine: if the machine's controller can hold the parametric form → emit it parametric; if not → expand the macro (resolve the IF/GOTO branches against the actual feature set + evaluate the calculated VC vars → a flat, non-parametric program with the same toolpath) via MacroProgramIntelligenceEngine (it has the AST + the var map — it can do the expansion) and emit the expanded form, noting in the header "EXPANDED from parametric macro <name> — controller can't hold the parametric form". ShopConfigurationEngine must carry each controller's memory/char limit (add it if missing — this is a real machine capability, like travel limits). → re-run U4's gate against THAT machine's envelope (each machine is independently gated — a program that's safe on machine A may breach machine B's travel) → on PASS, emit <part>__<MACHINE-ID>.MIN (parametric or expanded) with a header noting: macro source, family, VC vars filled from print rev (or "expanded"), S(x) score for THIS machine, controller dialect, "OPERATOR REVIEW REQUIRED — prove-out mode on for first run". Write into _PART LIBRARY/<customer>/<pn>/CNC PROGRAM/. Update part.json (perMachinePrograms: [{machineId, file, sxScore, controller, form: "parametric"|"expanded", needsOperatorReview: true}]). Reuse: ShopConfigurationEngine (the 21 machines), PostProcessorPipelineEngine + LathePostProcessorEngine + PPOkumaTurningPostEngine + OkumaB250LatheMasterPostEngine + LathePostProcessorDialectValidatorEngine (post + dialect), LathePrintProgramEmitterEngine + LatheProofCarryingEmitEngine (envelope-aware gated emit), PartFolderOrganizerEngine (write into the part folder + part.json), LatheEnvelopeBreachReplayEngine. Wiring + composition — the per-machine config + the posts + the gate all exist. Wire: prism_turning + prism_cam + prism_dev (post): action macro_emit_per_machine (gated candidate + part-ref → {machines: [{machineId, file, sxScore, controller, passed}], dossier}). Schema + switch + zod. Tests: macro_emit_per_machine round-trip — a gated wafer-insert candidate + a part-ref → ≥1 machine with passed: true + a file written into a temp CNC PROGRAM/ dir named <part>__<MACHINE-ID>.MIN + part.json updated + the header has the S(x) for that machine + needsOperatorReview: true; a candidate whose part dia > every lathe's swing → machines: [], no files, a clear "no machine fits" message; a candidate that fits machine A but breaches machine B's Z-travel → A passed: true with a file, B passed: false with NO file + the breach named; a non-Okuma target machine → the emitted file is in that machine's dialect (assert a dialect marker) + LathePostProcessorDialectValidatorEngine passes it. #MS0-U6 — Bulk fan-out into _PART LIBRARY/ (gated, operator-confirmed, NEVER auto)

What: the bulk path — over _PART LIBRARY/ (25,028 part folders) + the join table: for each part with macroNeedsFill: true (set by U1) and a confident family match → run U2 (fill) → U4 (gate) → U5 (per-machine emit). This is the dangerous one. It is NOT a phase18-style fire-and-forget batch. It runs in BATCHES of N (default 25), each batch produces a review report (_PART LIBRARY/_MACRO_BATCH_<n>_REVIEW.md — per part: family, S(x) per machine, the filled var table, any flagged dims, the dossier path), and the operator must sign off on each batch before the next runs (MACRO_PROGRAM_PIPELINE_BATCH_APPROVED=<n> env / a _BATCH_<n>_APPROVED marker file / an explicit "approve batch n" from the operator). Any part where the fill flags a dim, or the gate fails on every machine, or S(x) is borderline (0.70–0.75) → goes to a _MACRO_NEEDS_HUMAN.md queue, NOT emitted. Resumable. Writes _PART LIBRARY/_MACRO_BULK_LOG.md. A Stop hook (macro-bulk-emit-guard) blocks the session if a bulk batch ran without a recorded operator approval for it. Reuse: U1 (MacroLibraryEngine), U2 (MacroFillOrchestratorEngine), U4 (the gate), U5 (per-machine emit), PartFolderOrganizerEngine. New: the batch-orchestrator script (scripts/macro-bulk-emit.mjs) + the macro-bulk-emit-guard Stop hook (modelled on the existing safety Stop hooks). Wire: prism_turning: action macro_bulk_emit_batch (batch n → runs U2→U4→U5 for that batch's parts, returns the review report; refuses if batch n-1 isn't approved). Schema + switch + zod. + the new Stop hook in H:/.claude/settings.json (in MINIMAL_ALLOWLIST so it can't be profile-disabled — it's safety). Tests: macro_bulk_emit_batch — batch 0 on a temp library of 3 known parts → 3 dossiers, per-part S(x), the review report written, NOTHING emitted-as-final (everything needsOperatorReview: true); batch 1 requested before batch 0 approved → refused with the reason; a part that flags a dim → in _MACRO_NEEDS_HUMAN.md, not in the batch's emitted set; the Stop-hook test — a session that ran macro_bulk_emit_batch for batch 0 without _BATCH_0_APPROVED → the hook blocks Stop with the explanation; with the approval marker → Stop clears.
