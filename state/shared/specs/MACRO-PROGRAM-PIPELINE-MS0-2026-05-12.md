### PRINCIPLE — the macro is the proven STARTING TEMPLATE, not a straitjacket (per the user, 2026-05-12: "make sure the programs utilize macros, hardcoded, controller-specific features/coding language, and whatever other toolpath would be more beneficial")

The fill/emit pipeline (U2 → U5) MUST:
1. **Utilize the macros.** The matched macro's operation sequence, tool numbering (`T010101..T101010`), VC-var layout, and Okuma canned-cycle structure are the *proven baseline* — start there. Don't ignore the macro and freehand a program.
2. **Use controller-NATIVE features + dialect.** Emit in the *target machine's* G-code dialect using *that controller's* actual canned cycles and special features — Okuma OSP (`G85/G86/G87` profile cycles, `G74` peck, `VC1xx` user vars, `CALL`/subprograms, `G50` max-RPM, `G96/G97` CSS, `G41/G42`, `IF/GOTO`); Fanuc/Fanuc-like (`G70/G71/G72/G73` cycles, `#`-macro vars, `M98/M99` subprograms, `G96/G97`, `G50`/`G92` spindle clamp); Mazak (EIA or MAZATROL conversational, `MAZAK` cycles); Siemens 840D-style (`CYCLE*` calls, `R`-parameters). **NEVER emit a lowest-common-denominator program** — if the target controller has a profile-roughing cycle, use it; if it has a probing macro, use it.
3. **Emit parametric OR hardcoded — whichever is more beneficial for THAT machine/controller/part.** Both are valid outputs:
   - *Parametric* (the macro's `VC`/`#`-variable form, `IF/GOTO` intact, calculated vars left as expressions) — best when the controller can hold it, the part family will recur (so the operator can re-run with new dims), and the macro overhead is negligible.
   - *Hardcoded / flat* (resolved variables, expanded `IF/GOTO` against the actual feature set, calculated vars evaluated) — best when the controller **can't** hold the parametric form (the known Okuma P300L/P300LA program-memory + char-count limit on 60+-var / 500+-line parametric programs — memory `project_okuma_controller_limits`), or the part is one-off, or the operator prefers a flat program, or the macro's conditionals all collapse to one branch anyway. `MacroProgramIntelligenceEngine` has the AST + var map and can do the expansion.
   The pipeline picks per a benefit heuristic (controller memory headroom, recurrence likelihood, program complexity, operator preference, cycle-time impact) and **states which form it chose + why in the program header**.
4. **Substitute a more-beneficial toolpath/strategy where the part warrants it.** The macro's fixed toolpath is the *default*, not a lock. The `/lathe` strategy engines (`LatheMultiOpPlannerEngine`, `TurningStrategyCatalog`, `LatheSequenceOptimizerEngine`, `LatheAdaptiveMachiningEngine`, `LathePartingChipClearanceEngine`, the optimizers, `LatheOnMachineProbeCycleEngine`) may swap in a better approach — a different roughing strategy, a different tool sequence, trochoidal grooving, an in-process probe cycle, a different cutoff/parting strategy, a chip-breaking peck pattern — when it measurably improves cycle time / tool life / surface finish / process robustness for this part. **Any deviation from the macro's baseline structure must be (a) justified in the program header, (b) re-validated by the safety gate (U4) against the actual emitted toolpath — the S(x) gate scores the *emitted program*, not the macro template.**

All of the above is still gated: S(x) ≥ 0.70 + envelope + sim/back-plot + operator sign-off on the *final emitted program* (parametric or hardcoded, native dialect, with whatever toolpath was chosen). Operator-in-the-loop is unconditional. NEVER bulk-auto-emit.
