## §4 — The 6 brief checks, one by one

### Check 1 — resolve all 94 `(TBD-create)` viz_node_ids → **FAIL (74/94 use invented namespaces)**

Of the **94 `(TBD-create)` ids** (+ a handful of `(TBD-add)`/`(TBD)` = 108 viz_node_id lines total): **3 resolve** to live nodes (`eng.ai.aisystemrouterengine` ✓, `disp.devdispatcher`/`disp.sessiondispatcher` ✓), **23 are TBD-OK** (the prefix matches the graph taxonomy — e.g. `eng.knowledge.reputablesourcemonitorengine`, `eng.ai.kimitransportengine`, `fs.deep.…`, `state.adoptlog.…`, `wire.dispatcher.…`), **74 are TBD-BAD-NS** (the prefix is invented — full list in §0 F1 and the META artifact stdout), **2 are EXISTS-MISLABEL** (engine already live — F4), and **6 are UNRESOLVED** (tagged "existing/extend" but the graph has no matching node — `core.hooks.posttoolbatchbudget`, `core.hooks.ollamaroute`, `core.engine.opcuaconnector` → should be `eng.sensor.opcuaconnectorengine`, `core.registry.skill-registry` → graph uses `reg.<name>`, `core.dispatch.prism_dev.skill_test` → graph uses `disp.devdispatcher.action.skill_test`, `fs.deep.prism.state.shared.specs.f.vault-schema-doc.md` → the path is fine but the node doesn't exist yet because the doc isn't written).

**Root cause:** the atomization pass *invented* node ids from the engine names instead of *looking them up* in `system-graph.json` (which the mega §13 said it would do).
