(d) AGENTIC-LOOP / AUTONOMOUS-BUILD MECHANICS
---

There are TWO separate loop structures in this codebase. They are architecturally distinct.

LOOP STRUCTURE 1: AgenticLoopEngine.ts (H:/prism/mcp-server/src/engines/AgenticLoopEngine.ts)
This is a general manufacturing-domain agent loop. It is NOT the Hermes fleet orchestration loop. It implements the classic Observe-Think-Act-Learn pattern:

  OBSERVE (line 266): IntentRouterEngine.route() + classifyIntent() + extractEntities(); builds context factors from conversation history and working memory.
  THINK (line 285): ManufacturingReasoningEngine.reason() builds a reasoning chain; IntentRouterEngine routes to a primary action + up to 2 alternatives; risks identified (hardness, low confidence); overall confidence = (routingConfidence + reasoningConfidence) / 2.
  ACT (line 314): Only fires if confidence >= requireConfidence (default 0.5). Executes primary-priority (priority==1) PlannedActions via ToolExecutionEngine. Returns aggregated results.
  LEARN (line 335): If autoLearn=true, captures successful patterns, entity facts, and error patterns as MemoryUpdate objects. Does NOT write to Obsidian or Qdrant directly - writes to in-memory workingMemory (type: "fact" | "preference" | "correction").

How it decides next actions: routing match (dispatcher + action) from IntentRouterEngine; alternatives added at priority 2+; confidence gate blocks ACT if below threshold. maxIterations=5 but the loop runs exactly ONCE per input in the current implementation (iterationCount=1 always, line 351). It does not loop back on low-confidence results - it generates a low-confidence response string instead.

This engine does NOT connect to Obsidian, Qdrant, Ollama, or the fleet orchestration layer. It is a standalone PRISM MCP engine for single-request manufacturing AI (speed/feed, quoting, tool selection).
Source: AgenticLoopEngine.ts:208-392.

LOOP STRUCTURE 2: The Hermes closed-loop skill-building pipeline (the actual autonomous-build)
This is the real autonomous-build mechanism. It runs across sessions as a persistent pipeline:

  S1 OBSERVE (per Stop): scripts/lib/skill-candidate-detect.mjs + stop hook skill-candidate-observe.mjs. On every session Stop, extracts tool-call sequences from the transcript (pattern: Read|Edit|Bash:vitest|Bash:git), detects outcome via git HEAD age, classifies the session window, appends one JSONL line to state/shared/skill-candidates.jsonl. 60-second throttle against Stop-storm.
  S2 CLUSTER (scripts/lib/skill-loop-pipeline.mjs::clusterCandidates): buckets eligible entries by tool-call signature; emits clusters with >= CLUSTER_THRESHOLD (default 5) occurrences, sorted newest-first.
  S3 PROPOSE (skill-loop-pipeline.mjs::buildStubBody): renders a staged skill spec at state/shared/specs/SKILL-CANDIDATE-<id>.md (after G5 fix; was .claude/commands/ pre-fix).
  S4 DEDUP (skill-loop-pipeline.mjs::gateCandidate): Jaccard over frontmatter trigger keywords against existing skill catalog (~700 skills). If overlap > 0.4 = CONFLICT.
  S5 GATE / PROMOTE: AUTO-PASS if medianCallCount >= 6 AND >= 2 slots independently observed the pattern. AUTO-FAIL on conflict/low-leverage. NEEDS-REVIEW -> operator-dispatched subagent. shipDraft writes to .claude/commands/<id>.md on PASS.
  S6 DISPATCH: The shipped /skc-xxxx skill is invocable. Natural invocations are re-observed at S1, compounding the loop.
  S7 LEARN: Stop hook feeds new memory files back to Obsidian (auto-feed). Soul evolution candidates written to state/shared/slot-souls/<slot>.draft.md (U-HRP05, UNVERIFIED if shipped).

How it decides next actions: the /loop pattern driven by hermes-workflow-planner.mjs (scripts/lib/hermes-workflow-planner.mjs). Given a task string, it returns: workflow-vs-session verdict, pattern composition (drift->fan-out, self-preference->adversarial-verify, open-ended->loop, hard-to-score->tournament), per-stage model/isolation/barrier, token-budget/goal/loop shape. Output: --emit flag produces a runnable PRISM Workflow harness skeleton.

ZULU ORCHESTRATION LOOP (the fleet-level autonomous build driver):
The Zulu orchestrator (ZuluFleetGovernorEngine, wired as prism_session:zulu_authority_check) acts as the meta-loop controller:
