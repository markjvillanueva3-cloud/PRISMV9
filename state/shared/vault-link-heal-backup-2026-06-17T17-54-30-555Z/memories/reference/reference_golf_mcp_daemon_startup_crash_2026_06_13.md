**Incident (2026-06-13 ~07:58Z, slot golf, session 02a2de10):** MCP server on `127.0.0.1:3100` genuinely DOWN fleet-wide (curl + raw-socket probe both `ECONNREFUSED`). This was REAL — distinct from the load-induced FALSE "mcp-down" banners earlier the same session (consolidate-graph "operation aborted" + a "port DOWN" banner that `singleton-service-guard` + `curl` both contradicted). **Always verify a down-banner with `singleton-service-guard` + `curl` before acting; most are false under load, this one wasn't.**

**Diagnosis (golf runtime-hygiene lane):**
- `node scripts/singleton-service-guard.mjs --fix` → daemon WEDGED ("port DOWN with 1 daemon(s)"), reaped pid 58048, restart FAILED health-check → "post-fix port DOWN".
- `node .claude/helpers/mcp-server-daemon.mjs start` → spawns child (pid 34748), waits 30s, "WARNING: Daemon started but health check failed"; child then dies (`process.kill(pid,0)` → ESRCH).
- Daemon log `H:/prism/.claude/cache/mcp-daemon.log`: the server registers EVERY dispatcher (prism_doc, prism_memory 30 actions, prism_atcs, prism_intelligence, …) then **`[ERROR] Server startup failed {}`** — error serializes to EMPTY, no stack/message. Crash is AFTER full init, at the HTTP listen/transport step.
- `mcp-server/dist/index.js` present + fresh (built 02:56). Port NOT held by another process (`ECONNREFUSED`, not `EADDRINUSE`).
- Daemon helper config is CORRECT (`.claude/helpers/mcp-server-daemon.mjs:149-171`): spawns `node dist/index.js` with `env.TRANSPORT="http"`, `PORT=3100`, `NODE_OPTIONS` heap floor ≥24576MB. **NOT a missing-TRANSPORT bug.**

**Conclusion — NOT golf-fixable by config/hygiene.** Root cause is in the **mcp-server startup code** (post-dispatcher-registration listen/transport throw, or OOM under fleet load — the helper comment L160-171 documents a prior OOM-under-multi-agent-:3100-load). Daemon + manual both use the same `dist`, so a manual `TRANSPORT=http node dist/index.js` hits the SAME crash. **Owner: backend / mcp-server (papa).** Two asks: (1) the "Server startup failed" handler logs `{}` — fix it to log `err.stack`/`err.message` so the real cause is visible; (2) diagnose the post-init listen crash / OOM.
